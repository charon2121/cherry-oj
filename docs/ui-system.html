Cherry OJ · UI System

清晰胜过装饰

面向题目阅读、代码编辑和异步判题的开发工具型界面。用稳定规则替代临场审美，让每个页面都自然属于同一个产品。

Linear-inspired Focused Workspace

冷静的灰阶、蓝紫交互、退后的导航与紧凑层级；借鉴原则，不复制 Linear 的品牌资产。

01

设计原则

当两个方案都能工作时，用这些原则做决定，不靠个人偏好。

01

任务优先

主操作始终最清楚，装饰不能抢过题面、代码和判题结果。

02

状态可恢复

刷新后能从 URL、草稿和 Submission ID 恢复用户现场。

03

语义稳定

同一颜色、组件和文案在所有页面表达同一种含义。

04

键盘完整

核心链路无需鼠标；焦点可见，操作顺序符合阅读顺序。

05

渐进揭示

先显示结论和下一步，再按需展开测试点与诊断细节。

06

判题语义

生命周期和 verdict 是两套不同概念。此处严格覆盖 contracts/submission.json 与 contracts/verdict.json。

Submission lifecycle

Pending提交已创建，等待送判
Judging判题机正在编译或运行
Done已有终态结果，包括 CE / SE

Verdict vocabulary

AC

答案正确

唯一的通过结论。绿色之外始终显示 AC 与中文名称。

WA

答案错误

优先展示首个差异位置；是否展示标准答案由服务端策略决定。

TLE

时间超限

展示实际耗时和题目限制，单位在展示层转换。

MLE

内存超限

展示峰值内存和题目限制，不改变原始 bytes 模型。

OLE

输出超限

说明输出被截断，避免用户把它误解为普通 WA。

RE

运行错误

在安全范围内展示 stderr 摘要与退出信息。

CE

编译错误

编译器输出使用等宽字体，保留换行并支持复制。

PE

格式错误

答案接近正确，但输出格式不符合题目要求。

SE

系统错误

明确说明不是用户代码结论，并提供 Request ID 便于排查。

RAN

已运行

自定义测试没有 expected，只展示程序输出，不冒充 AC。

09

实施约束

这些规则进入代码评审和 Storybook。UI System 是可执行约束，不是只供浏览的展示稿。

应该

  • 业务组件只使用 background、primary、danger 等语义 token。
  • 每个共享组件覆盖 light、dark、focus、disabled、loading 和 error。
  • verdict 使用穷尽映射，新增契约值时让 TypeScript 编译失败。
  • 使用语义 HTML、可见 label 和清楚的键盘焦点。
  • 页面先套模板，再为真实业务差异增加局部模式。

不要

  • 在 feature 中出现任意品牌色、随机圆角或复制的大段 class。
  • 把所有内容都包成外观相同的 Card。
  • 仅靠红绿颜色表达成功、失败或难度。
  • 为了一次性页面修改基础组件默认行为。
  • 用 Toast 承载用户必须阅读或处理的关键错误。
