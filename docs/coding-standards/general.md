# Coding Agent General Directives

1. **必须遵循现有项目约定。**
   优先保持现有目录结构、命名、架构、错误处理、日志、测试、格式化和依赖管理方式。
   除非任务明确要求，不得进行无关重构、批量重命名、公共 API 调整或依赖升级。

2. **必须优先写简单、自解释的代码。**
   使用清晰命名、短函数、明确职责和显式控制流。
   优先使用 early return、guard clause 和辅助函数降低复杂度。
   不得通过复杂抽象掩盖简单问题。

3. **不得为假设中的未来需求提前设计。**
   仅当存在真实重复、明确边界或当前扩展需求时，才创建抽象层、接口、基类、Factory 或通用框架。
   形式相似但语义不同的代码，不得强行抽象。

4. **注释必须提供代码本身无法表达的信息。**
   注释优先解释 Why、约束、风险、取舍和外部限制。
   不得逐行翻译代码，不得解释显而易见行为，不得编造业务、历史、性能或兼容原因。
   不得保留被注释掉的废弃代码。

5. **必须正确处理错误和真实边界。**
   不得吞掉异常或错误。
   必须保留有助于定位问题的必要上下文。
   对外部输入、空值、边界值、时间、精度、并发、超时、重试和幂等问题，只处理真实存在或合理可能发生的场景。
   不得机械添加无意义防御逻辑。

6. **必须默认保证安全。**
   不得硬编码 secret、password、token 或 private key。
   不得在日志中输出敏感信息。
   不得信任未经校验的外部输入。
   权限校验不得仅依赖客户端。
   必须避免常见注入、越权、路径遍历和不安全反序列化问题。

7. **测试必须稳定、独立并表达行为。**
   测试名称必须尽量体现条件、行为和预期结果。
   优先使用确定性测试。
   不得无必要依赖真实时间、随机执行顺序、任意 sleep、外部网络或共享可变状态。
   修复缺陷时，应补充能够覆盖该问题的回归测试。
   不得通过删除断言、降低覆盖或放宽条件来让测试通过。

8. **性能优化必须有依据。**
   优先优化算法复杂度、数据库查询、网络往返、I/O、重复计算和大对象复制。
   不得进行没有明确收益依据的微优化。
   存在重要性能取舍时，应通过结构或必要注释明确表达原因。

9. **新增依赖必须有必要性。**
   添加依赖前，必须先检查标准库和项目现有依赖是否已经能够满足需求。
   不得为了极小功能引入重量级依赖。
   不得无理由升级与当前任务无关的依赖。

10. **Migration、脚本和配置必须考虑运行风险。**
    对数据迁移、一次性脚本、基础设施和配置代码，必须考虑重复执行、部分失败、恢复方式、影响范围、环境差异和破坏性操作。
    高风险操作必须具有明确保护条件。

11. **必须控制修改范围。**
    只修改完成当前任务所必需的代码。
    不得顺带格式化无关文件、重写无关模块、改变无关行为或扩大任务范围。

12. **完成前必须自检。**
    提交前确认：

    * 功能满足需求；
    * 与项目现有风格一致；
    * 命名和结构清晰；
    * 没有不必要复杂度；
    * 错误和重要边界已正确处理；
    * 没有明显安全问题；
    * 注释有效且不过度；
    * 必要测试已新增或更新；
    * 没有无关修改；
    * 没有废弃代码、过时注释或隐藏失败。

## Priority Rules

发生规则冲突时，按以下优先级处理：

1. 当前明确任务要求
2. 当前项目已有约定
3. 语言和框架专属规范
4. 本通用规范
5. 通用最佳实践

不得为了遵循较低优先级规则而破坏较高优先级要求。

## Core Directive

> **优先生成简单、正确、自解释、可维护、可测试，并与现有项目一致的代码。只有在真实问题需要时，才允许增加复杂度。**
