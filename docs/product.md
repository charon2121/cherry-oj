### 已确认的 MVP 基线

- 单工作空间。
- 单管理员，允许作者自审发布。
- 支持两种 P0 代码模式：ACM 模式提交完整程序并自行处理输入输出；CORE（LeetCode）模式只提交
  题目要求的核心代码，由平台把它合并进该题目版本、该语言预先配置的完整源码模板。
- C++ 优先，先跑通单语言端到端链路。
- 题目版本需要存在；发布后不可变，修改时创建新版本。
- 每次提交必须绑定实际使用的题目版本。
- 时空限制保存为「题目版本 × 语言 × 判题环境」对应的绝对值。
- MVP 暂不接入 AI；先完成传统 OJ 链路和确定性的题目工厂。

## 一、产品定义

### 1.1 一句话定位

**cherry-oj 是一个面向教学与专业题库运营团队的 AI 原生 Online Judge：既为用户提供稳定、完整的做题与判题体验，也为运营者提供从题目生产、测试数据构建、正确性验证、语言标定、审核发布到持续维护的完整工作台。**

它不是「传统 OJ 加一个聊天框」。真正的差异在于把过去散落在本地脚本、终端、文件夹和人工经验中的出题流程，变成一条可重复、可审计、可自动重跑的生产流水线，再让 Agent 负责生成草稿、调用工具、解释结果和提出建议。

### 1.2 两条同等重要的产品链路

```text
用户链路：找题 → 阅读 → 编码 → 自测 → 提交 → 查看结果 → 复盘

运营链路：构思 → 编写题面 → 准备解法 → 生成数据 → 验证题目
          → 标定限制 → 审核发布 → 观察运行 → 迁移/扩语种/修订
```

传统 OJ 主要解决第一条链路和运营链路的最后一步「上传并发布」。cherry-oj 的产品机会，是补齐第二条链路。

### 1.3 产品判断

1. **用户端完整是准入条件，运营端高效才是差异化。** 用户不能因为平台强调 AI 就失去成熟 OJ 应有的稳定体验。
2. **AI 负责提效，不负责定义真相。** 标准答案、测试数据和时空限制必须经过可执行程序与规则验证，不能因为模型说“应该正确”就直接发布。
3. **自动化优先于智能化。** 先把生成、运行、比对、压测、记录做成确定性工具，Agent 再调用这些工具；这样失败可定位、任务可重跑、结果可审计。
4. **题目是一组可版本化资产，不是一张题面表。** 题面、样例、参考解、数据生成器、输入校验器、测试数据、语言实现、限制策略和验证报告共同组成一个可发布题目版本。
5. **发布是显式的人类决策。** Agent 可以创建草稿和提交发布建议，但不能静默修改已发布题目、测试数据或限制。

## 二、目标用户与核心任务

### 2.1 普通答题用户

核心任务：

- 快速找到适合自己的题目并理解题意。
- 在浏览器中编写、保存和运行代码。
- 使用自定义输入调试，不污染正式提交记录。
- 提交代码并看到明确、可信的判题结果及测试点信息。
- 回看历史提交，比较不同实现的正确性与性能。

### 2.2 出题人 / 高校教师

核心任务：

- 把一道题的想法可靠地变成可发布题目。
- 让 Agent 协助补全题面、参考解、生成器、校验器和多语言实现。
- 证明样例与隐藏数据符合约束，标准答案能够复现。
- 用预期正确、错误和低效的程序检验数据区分度。
- 审阅 Agent 的产物和报告，而不是手工搬运大量文件。

### 2.3 题库运营人员 / 审核者

核心任务：

- 审核题面、数据、解法、版权和发布范围。
- 查看每一步的执行记录、失败原因、产物版本和修改人。
- 批量发现缺少语言支持、限制已过期或验证失败的题目。
- 在服务器迁移、工具链升级或新增语言后安全地批量重标定。

### 2.4 系统管理员

核心任务：

- 管理用户、角色、工作空间、语言工具链和判题环境。
- 监控判题队列、失败率、资源容量及异常提交。
- 控制 Agent 可访问的数据、模型、预算和执行权限。

## 三、产品目标与非目标

### 3.1 产品目标

- **G1：完整答题闭环。** 用户能在 ACM 与 CORE 两种代码模式下完成登录、浏览题目、编码、自测、
  提交和查看结果。
- **G2：题目生产闭环。** 运营者能在平台内完成 ACM 或 CORE 题目从草稿到发布的全过程。
- **G3：结果可复现。** 任一已发布题目都能追溯到题目版本、数据版本、生成参数、参考程序、语言工具链、判题环境和限制版本。
- **G4：限制有依据。** 每门启用语言的时空限制来自保留原始样本的基准测试与明确策略，而不是只保存一个人工填写的最终数字。
- **G5：变化可维护。** 服务器迁移、镜像升级和新增语言会触发明确的影响分析与待办，而不是让旧题静默沿用未经验证的配置。
- **G6：AI 可控。** Agent 的每个任务都有输入、步骤、产物、日志、状态、权限边界和人工检查点。

### 3.2 当前非目标

- 首个版本不覆盖交互题、输出题、代码补全题、分布式程序等复杂题型；CORE 函数题属于 P0，
  不在此排除范围内。
- 首个版本不追求竞赛、社交、讨论区、课程管理、作业防作弊等所有传统 OJ 扩展能力。
- 不让大模型直接给出 AC/WA/TLE/MLE；正式 verdict 仍由 judge 与 sandbox 产生。
- 不让 Agent 绕过审核直接修改已发布版本，或直接操作生产判题机文件系统。
- 不把 cherry-oj 做成通用 LMS、通用 IDE 或通用 Agent 平台。
- 不承诺 AI 一次生成的题目、解法或数据必然正确；产品价值在于降低制作成本并系统化验证。

## 四、核心产品概念

### 4.1 题目与题目版本

- `Problem` 是长期稳定的题目标识、归属和可见性容器。
- `ProblemVersion` 是一次可判题的逻辑快照，包含题面、测试数据、checker 和允许语言；环境相关的实际限制由独立的 `LanguageCalibration` 版本管理。
- 草稿可反复修改；已发布版本不可原地改写。修改题面、checker、测试数据或允许语言时产生新的题目版本。
- 修改题面、checker、测试数据或允许语言时创建新的 `ProblemVersion`；仅因服务器迁移重新标定限制时，不复制整道题，而是为原题目版本生成新的 `LanguageCalibration`。
- `Problem` 保存当前发布版本的引用，便于用户默认访问最新版本；历史版本仍可追溯。
- 每次提交必须绑定实际判题的 `ProblemVersion`、`LanguageCalibration` 和 `JudgeEnvironment`，并保存本次生效限制的快照，避免后来改题或迁移后无法解释旧提交。

#### 4.1.1 代码模式

每个 ProblemVersion 必须选择且只能选择一种 `CodeMode`：

- `ACM`：用户提交包含程序入口的完整源码，自行读取标准输入并写出标准输出。
- `CORE`：用户只提交题目要求的函数等核心代码，不提交 `main`；平台把用户源码替换到该题目版本、
  该语言预先配置的模板占位符中，得到包含入口和输入输出处理的完整程序后再判题。

CORE 模板按 `ProblemVersion × Language` 配置，模板中必须有且只能有一个固定的用户代码占位符。
平台只做确定性的文本替换，不需要理解函数签名、参数类型或返回值类型，也不提供一套通用编解码
框架。代码模式和模板都属于题目版本内容；修改模板必须创建新的 ProblemVersion，不能原地改变已
发布题目对历史源码的解释方式。

### 4.2 题目资产

一个题目版本可以包含：

- 题面、输入输出说明、约束、样例、提示、标签、难度和来源信息。
- 一份或多份参考解；标明语言、预期复杂度和用途。
- 测试数据生成器及随机种子。
- 输入校验器，用来证明生成数据满足题目约束。
- 输出生成程序（oracle，通常由参考解担任）。
- 已知正确解、常见错误解、边界错误解和超预期复杂度解。
- 分组后的测试点、分值、可见性、用途标签及内容摘要。
- 构建报告、验证报告、基准测试记录与发布审核记录。

### 4.3 判题环境

`JudgeEnvironment` 代表会影响结果的执行环境，至少记录：

- CPU 型号或可比较的性能标识、架构和核心配置。
- 操作系统、内核、容器/沙箱镜像版本。
- 编译器、解释器、运行时及编译参数版本。
- judge、sandbox 和语言配置版本。
- 环境指纹与生效时间。

环境指纹变化后，平台必须能够判断哪些基准测试和语言限制已经过期。

### 4.4 语言标定

`LanguageCalibration` 不是简单的一个倍率，而是一组可追溯结论：

- 对应的题目版本、语言、判题环境和参考程序版本。
- 多次运行的原始 CPU、墙钟和内存样本。
- 统计结果、离群值处理方式、安全余量、最小/最大限制。
- 最终建议值、人工批准值与两者差异。
- `Uncalibrated / Running / Valid / Stale / Failed` 状态。

### 4.5 Agent 任务

`AgentTask` 是运营工作台中的一等资源，而不是一次不可追踪的聊天：

- 有明确目标、输入资产、可使用工具和权限范围。
- 状态至少包含 `Queued / Running / NeedsReview / Completed / Failed / Canceled`。
- 输出不是一段自然语言，而是结构化产物、验证报告和下一步建议。
- 任务支持取消、失败后重试；确定性步骤应幂等，避免重复生成或覆盖资产。
- 关键决策必须停在 `NeedsReview`，等待运营者确认。

## 五、功能需求

优先级定义：

- **P0**：产品 MVP 必须具备；缺少就无法证明核心产品价值。
- **P1**：首个可运营版本需要；可在 P0 跑通后补齐。
- **P2**：规模化与差异化增强。

### 5.1 用户端

#### P0

- 注册/登录或由管理员创建账号；身份由 server 统一管理。
- 题库列表：分页、关键字、难度、标签和状态筛选。
- 题目详情：安全渲染题面、约束、样例、提示、代码模式和支持语言。
- 代码工作台：语言选择、Monaco 编辑器、本地草稿保存和恢复；ACM 显示完整程序起始代码，CORE
  显示该题该语言的核心代码起始模板，不要求用户编写入口程序。
- 自定义测试：两种模式都输入测试用 stdin 并查看 stdout；CORE 在运行前先合并题目语言模板。两者
  都返回 stderr、耗时、内存和运行状态，不计入正式通过记录。
- 正式提交：创建提交记录、展示排队/判题生命周期、轮询直至终态。
- 提交详情：展示 verdict、总时间、总内存、编译错误和允许公开的测试点结果。
- 我的提交：按题目、语言、verdict 和时间筛选历史提交。
- 题目通过状态：未尝试、尝试未通过、已通过；不得仅靠颜色表达。

#### P1

- 收藏、最近浏览、个人做题统计和代码模板。
- 管理员可配置测试点明细的公开粒度，避免隐藏数据泄漏。
- 对同一题的历史提交进行性能对比。

#### P2

- 排行榜、竞赛、班级、课程、作业与讨论能力。
- 在不泄漏答案的前提下提供分层提示或 AI 复盘。

### 5.2 题目生命周期与协作

#### P0

- 创建、编辑、预览和删除未发布草稿。
- 生命周期至少包含 `Draft / Validating / ReadyForReview / Published / Archived`。
- 发布前检查清单必须覆盖题面、样例、测试数据、参考解、支持语言和有效限制。
- 已发布版本不可原地覆盖；变更通过创建新版本完成。
- 题目支持公开、私有两种可见性；MVP 可先使用单工作空间。
- 保存创建人、修改人、审核人、发布时间及关键操作记录。

#### P1

- `Author / Reviewer / Admin` 角色分权。
- 评论、审核意见、退回修改和版本差异。
- 批量标签、批量归档和批量分配审核人。

### 5.3 题面与解法资产

#### P0

- 题面使用 Markdown 编辑与预览，输入/输出/约束/样例使用结构化字段管理。
- 创建题目版本时必须选择 ACM 或 CORE，发布后不可切换。
- 两种模式的样例 stdin/stdout 都必须成对，能够直接送入最终合并后的完整程序验证。
- CORE 必须为每门允许语言配置用户可见的起始代码和服务端使用的完整源码模板；完整模板负责入口、
  输入解析、函数调用和输出，且必须包含唯一的用户代码占位符。
- 上传或在线编辑至少一份参考解，并记录语言与预期复杂度。
- 参考解必须能在目标环境编译/运行；失败时保留完整诊断。

#### P1

- Agent 可以根据题意生成题面、参考解和讲解草稿，但所有产物默认进入草稿区。
- 多份等价参考解与跨语言版本。
- 题面一致性检查：约束、样例、输入格式和参考实现之间的矛盾提示。
- 从现有 OJ 常见格式导入题面与测试数据，减少迁移成本。

### 5.4 测试数据工厂

#### P0

- ACM 与 CORE 共用原始文本 `.in/.out` 测试数据：`.in` 作为最终完整程序的 stdin，`.out` 作为
  期望 stdout。CORE 的题目语言模板自行完成输入解析、函数调用和结果输出。
- 支持手工上传 `.in/.out`，也支持通过生成器批量构建。
- 生成器必须记录源码、运行时、参数、随机种子和输出清单；相同版本与种子应可复现。
- 输入校验器逐点验证格式和范围，不合格数据不得进入待发布数据集。
- 通过指定 oracle 批量运行 `.in` 生成 `.out`，并保留程序版本与产物摘要；CORE 参考实现使用与
  用户提交相同的题目语言模板合并后执行。
- 测试点可标记为 `sample / normal / edge / stress / regression`，并支持分组和分值。
- 每次构建产生不可变的 `TestDataVersion`、内容哈希和构建报告。
- 构建失败不得部分覆盖上一版可用数据。
- 运营者可以下载完整数据包，也能在平台内查看受控预览和统计摘要。

#### P1

- Agent 根据约束和参考解生成数据生成器、输入校验器与测试计划草稿。
- 自动检查重复测试点、空数据、超大数据、非法编码、缺失输出和不稳定输出。
- 根据分支、边界值和复杂度生成覆盖建议；允许运营者接受、修改或拒绝。
- 支持多个生成器组合构建同一数据集。

#### P2

- 属性测试、变异测试和覆盖率反馈，自动寻找不能区分正确解与错误解的数据缺口。
- 对历史错误提交聚类，并将有代表性的反例沉淀为回归测试点。

### 5.5 正确性验证

#### P0

- 所有参考解必须通过全部正式测试点。
- ACM 参考解必须包含完整程序；CORE 参考解必须经过与用户提交相同的题目语言模板合并后验证。
- 多份参考解存在时，平台应执行差分验证；输出不一致则阻止发布。
- 样例必须使用与正式 checker 相同的规则验证。
- 支持录入已知错误解；验证报告必须说明每个错误解被哪些测试点拦截。
- 支持录入低效但结果正确的程序，验证数据规模和限制是否能区分预期复杂度。
- 验证报告按检查项给出通过、失败、警告和证据，不只给一个总分。

#### P1

- Agent 生成常见错误解、边界错误解和复杂度更差的候选程序，再由真实判题验证。
- 自动检测非确定性参考解，同一输入多次输出不一致时阻止发布。
- 对 checker、生成器或参考解变更执行受影响范围内的回归验证。

### 5.6 多语言基准测试与限制建议

#### P0

- 运营者为题目版本选择要支持的语言；未完成标定的语言默认不可提交。
- 每种语言至少绑定一份已验证正确的基准实现。
- 在目标判题环境中对每份实现重复运行，保留每次 CPU、墙钟、内存、退出状态和环境指纹。
- 基准任务必须区分预热、正式样本与异常样本；不得只取一次运行结果。
- 平台根据可配置策略提出 CPU 与内存限制建议，展示计算依据和安全余量。
- 运营者可以批准、调整或拒绝建议；人工调整必须填写原因。
- 生效限制按「题目版本 × 语言 × 判题环境」管理，server 在送判前解析为一次请求的确定限制。
- 预期正确解必须稳定通过，指定的低效解应在预期位置失败；两者无法分离时不得把标定标为有效。

#### P1

- 比较不同语言、不同实现与不同环境的性能分布。
- 支持策略模板，例如教学宽松型、竞赛严格型，而不是每题从零填写规则。
- 发现测量抖动过大、内存贴线或墙钟异常时自动要求复测。
- 批量执行标定任务，并按失败原因分类重试。

### 5.7 服务器迁移、工具链升级与新增语言

#### P0

- 新判题环境注册后生成环境指纹；环境指纹改变时，相关标定变为 `Stale`，但不得静默改变线上值。
- 提供受影响题目清单，显示当前值、旧环境数据、待执行任务和风险等级。
- 支持在新环境批量重跑基准测试，生成新旧对比报告。
- 新限制必须经批准后才生效；保留回滚到上一有效配置的能力。
- 新增语言后，每道题显式选择支持或不支持。选择支持后必须提供/生成正确实现并完成标定。

#### P1

- 灰度环境验证：新环境先接收内部验证任务，再承接正式提交。
- 对迁移后的代表性历史提交执行回放，检测 verdict 漂移。
- 展示语言覆盖率、过期标定数量和迁移完成度。

### 5.8 Agent 运营工作台

> Agent 不属于 MVP。本节保留的是确定性题目工厂完成后的产品需求，避免当前实现提前依赖任何模型或 AI 服务。

#### P1

- 运营者从明确任务模板发起 Agent，例如「补全题面」「生成参考解」「生成数据计划」「构建并验证数据」「为启用语言生成实现」「重新标定限制」。
- Agent 必须先展示计划和所需输入；缺少题目约束等关键事实时暂停并请求补充，不能自行臆造后直接发布。
- 每个步骤显示正在调用的确定性能力、输入资产版本、执行状态、日志摘要和输出产物。
- Agent 生成的代码只能在受限 sandbox 中执行，不能直接运行在 server 或宿主机。
- 失败报告必须区分模型生成问题、代码编译问题、数据验证问题、判题环境问题和平台故障。
- 运营者能逐项接受、编辑、拒绝产物，并从任一步重新运行。
- 涉及发布、覆盖有效配置、扩大数据访问范围或高成本批量任务时必须人工确认。

#### P2

- 任务队列、并发和预算控制；展示模型与执行资源消耗。
- 保存模型、提示词模板、工具版本及关键输入摘要，便于解释为什么两次结果不同。
- Agent 根据失败证据自动修复草稿并再次验证，但需遵守最大尝试次数。
- 运营者可以保存团队级任务模板和审核规则。

#### 后续

- 批量题库健康巡检 Agent：发现数据薄弱、限制过期、语言缺失和异常通过率。
- 根据生产统计提出回归测试与限制复测建议。

### 5.9 管理与可观测性

#### P0

- 用户与基本角色管理。
- 语言启停、工具链版本、编译命令和运行命令的只读查看；修改走受控配置流程。
- 判题/构建/标定任务状态、耗时、失败原因和重试入口。
- 关键操作审计日志。

#### P1

- 队列长度、判题延迟、各 verdict 分布、SE 比例和资源容量仪表盘。
- 对异常通过率、连续 SE、环境漂移和任务积压告警。
- 工作空间级配额、Agent 预算和数据保留策略。

## 六、关键工作流与验收场景

### 6.1 从 A + B 草稿到发布

本场景使用 ACM 模式；CORE 模式的独立验收见 §6.5。

1. 出题人创建草稿，填写题意、输入输出和约束。
2. 上传参考解，或让 Agent 生成参考解草稿。
3. 上传/生成输入校验器、数据生成器和测试计划。
4. 以固定种子构建数据，校验全部输入，再用 oracle 生成输出。
5. 运行参考解、已知错误解和低效解，生成验证报告。
6. 为所有计划启用的语言准备正确实现并执行多次基准测试。
7. 系统提出语言级时空限制，出题人确认或调整。
8. 发布检查全部通过后提交审核；审核者批准一个不可变题目版本。
9. 用户看到题目、提交代码并获得可追溯的判题结果。

P0 验收要求：

- 从空白草稿到发布全过程不需要运营者在平台外手工复制粘贴测试数据内容。
- 任一步失败都能定位到具体资产、测试点、语言、运行记录和错误信息。
- 重新使用相同资产版本和种子构建，测试数据内容哈希一致。
- 发布版本能够回答「由谁、在什么环境、用什么程序、依据哪些样本设置了当前限制」。

### 6.2 服务器迁移

1. 管理员注册新判题环境，系统生成新环境指纹。
2. 受影响标定进入 `Stale`，线上仍使用旧环境或保持原配置，不静默切换。
3. 运营者批量运行代表性题目或全部题目的基准与历史提交回放。
4. 平台给出性能比率、verdict 漂移、失败题目和新限制建议。
5. 审核通过后发布新环境配置并保留回滚点。

P0 验收要求：迁移过程不能要求运营者逐题手工运行终端命令；失败项可单独重试，已通过项不重复执行。

### 6.3 新增一门语言

1. 管理员注册并验证语言工具链。
2. 题库健康页显示该语言对所有题目的 `Unsupported / Uncalibrated / Valid / Failed` 状态。
3. 运营者选择要支持的题目，上传实现或让 Agent 生成实现草稿。
4. 系统验证正确性、执行标定并提出限制。
5. 经批准后，该语言只对通过全部检查的题目开放。

P0 验收要求：新增语言不会自动出现在所有题目的提交选项中，也不会套用未经验证的统一倍率。

### 6.4 用户答题

1. 用户登录并筛选题目。
2. 阅读题面、确认代码模式、选择允许的语言并编写代码。
3. 使用自定义 stdin 运行代码并查看 stdout/stderr；CORE 在运行前自动合并题目语言模板。
4. 正式提交后看到 `Pending → Judging → Done`，终态展示 verdict 与允许公开的明细。
5. 之后修改并再次提交，历史记录都绑定当时的题目版本与语言环境。

### 6.5 ACM 与 CORE 代码模式

ACM P0 验收：

- 管理员创建 ACM A+B，配置原始文本样例与 `.in/.out` 隐藏数据。
- 用户提交包含 `main` 的完整 C++ 程序，程序自行读取 stdin、写出 stdout，并能获得 AC。
- 缺少入口或输出错误的提交分别得到 CE/WA 等真实 verdict。

CORE P0 验收：

- 管理员创建 CORE 加法题，为 C++ 配置核心代码起始内容和包含唯一占位符的完整源码模板。
- C++ 编辑器只要求用户提交 `int add(int a, int b)` 的实现，不展示或要求编写 `main`。
- 完整源码模板已经包含 `main`、stdin 解析、`add` 调用和 stdout 输出；平台只把用户源码替换到
  占位符中。
- 同一组隐藏测试能够判断正确实现为 AC、错误返回值为 WA、签名不匹配为 CE。
- Submission 绑定当时的 ProblemVersion 和语言，因此能追溯到实际使用的 CORE 模板。

## 七、AI 的能力边界与安全要求

### 7.1 Agent 可以做什么

- 从结构化约束生成题面、解法、生成器、校验器和候选错误解草稿。
- 调用 sandbox 编译和运行这些程序。
- 编排测试数据构建、差分验证、基准测试和报告生成。
- 根据真实运行数据提出限制建议、风险说明和修复方案。
- 对大量机械任务进行批处理，并把例外留给人处理。

### 7.2 Agent 不能做什么

- 不能把自然语言推断当成正式正确性证明。
- 不能直接签发 verdict、伪造运行结果或修改原始测量值。
- 不能跳过输入校验、参考解验证和发布检查。
- 不能在未经确认时发布、删除、覆盖题目资产或切换生产环境。
- 默认不能把隐藏测试数据、用户源码或私有题目全文发送给未获授权的外部模型。

### 7.3 数据与执行安全

- Agent 生成和用户上传的所有代码都视为不可信，只能进入 sandbox。
- 隐藏测试数据默认只向执行工具开放；提供给模型的应是约束、统计摘要和受控失败片段。
- 日志和报告不得包含完整隐藏输出、凭证或宿主机路径。
- 高成本任务设置运行次数、并发、CPU、内存和预算上限。
- 审计记录应能区分用户操作、Agent 建议、Agent 工具执行和系统自动策略。

## 八、非功能需求

### 8.1 正确性与可复现性

- 发布流程中的生成、校验、验证和标定均应使用版本化输入并产生不可变结果记录。
- 同一提交的判题输入应能追溯到题目版本、数据版本、限制和环境。
- 运行失败与用户程序失败严格区分；系统故障不能伪装成 WA/TLE。

### 8.2 可靠性

- Agent 或构建任务失败不得影响用户正式判题链路。
- 长任务支持取消、超时、有限重试和断点续跑；重复请求不得创建无法识别的重复资产。
- 发布采用原子切换，不能暴露构建到一半的数据集。

### 8.3 安全

- Web 不能直接访问 judge/sandbox；所有业务权限由 server 校验。
- 最小权限、角色隔离、审计日志和不可信代码沙箱是上线前置条件。
- 题面 Markdown、编译日志和用户输出在前端展示时必须安全转义/净化。

### 8.4 性能与容量

- 用户判题、运营构建、标定和 Agent 任务使用可区分的队列与优先级，运营批任务不能挤占正式提交。
- 大型数据包使用对象/文件存储和流式传输，不塞进 JSON 或数据库大字段。
- 具体延迟和吞吐 SLO 在部署规模明确后制定；PRD 不提前虚构指标。

### 8.5 可用性

- 运营者能从任务页面看懂当前卡在哪一步、为什么失败、该怎么继续。
- 所有批量任务都提供进度、成功/失败数量、过滤和失败项重试。
- 对用户展示的 verdict 同时使用文字与视觉符号，满足键盘操作和基本无障碍要求。

## 九、成功指标

首轮内部使用先建立基线，再确定目标值，避免在没有真实数据时设伪精确 KPI。

### 9.1 运营效率

- 从创建草稿到发布首个有效版本的中位耗时。
- 每道题需要在平台外执行的手工步骤数量。
- 单题生成/上传/重跑的人工操作次数。
- 服务器迁移后完成全部关键题目标定的耗时。

### 9.2 题目质量

- 发布前被自动检查发现的数据、题面和限制问题数量。
- 已知错误解被测试数据拦截的比例。
- 上线后因错题、弱数据或不合理限制触发修订/重判的比例。
- 有效语言覆盖率与过期标定占比。

### 9.3 Agent 有效性

- Agent 产物一次通过验证、经修改通过和被放弃的比例。
- 运营者处理一道题时节省的活跃操作时间。
- Agent 任务失败原因分布、平均重试次数和人工接管率。
- 单道题/单次迁移任务的模型与执行资源成本。

### 9.4 用户体验

- 提交成功率、判题系统错误率和判题等待时间分布。
- 用户从打开题目到首次提交、从首次提交到通过的转化。
- 自定义测试使用率和重复提交率。

## 十、MVP 边界与产品路线

### 阶段 0：判题基础设施（当前方向）

- sandbox、judge、跨语言契约和基础判题链路。
- 目标是证明不可信程序能够被执行、计量和正确映射为 verdict。

### 阶段 1：传统 OJ 端到端

- server、web、用户、题目、提交和基础管理后台。
- 分别跑通一个 C++ ACM 题和一个 C++ CORE 函数题的创建、发布、提交与返回结果。

### 阶段 2：确定性的题目工厂（产品 P0 核心）

- 题目版本、资产管理、生成器、校验器、oracle、数据构建、验证报告。
- 多语言基准测试、限制建议、环境指纹和发布检查。
- 即使没有大模型，这套流水线也能由运营者手动触发并可靠运行。

### 阶段 3：Agent 编排

- Agent 调用阶段 2 的工具，生成草稿、迭代修复、批量执行并解释异常。
- 人工审核、权限、预算、数据安全和可观测性同步上线。

### 阶段 4：持续运营与规模化

- 环境迁移、新语言覆盖、历史提交回放、健康巡检、回归数据沉淀。
- 多工作空间、协作审核、批量导入和运营仪表盘。

### 阶段 5：教学与竞赛扩展

- 班级、课程、作业、竞赛、排行榜、讨论与面向用户的 AI 学习能力。

> 阶段顺序表达依赖关系，不代表每一阶段必须一次性做完。开发仍应采用纵向切片：先让一题、一个生成器、一组数据、一个环境和若干语言跑完整闭环，再扩规模。

## 十一、对现有技术设计的直接影响

本节只记录 PRD 对架构提出的新需求，不在 PRD 中提前决定具体表结构和 API。

1. 当前测试数据按 `problemId` 定位；产品化后需要不可变的 `ProblemVersion / TestDataVersion`，正式判题必须能精确定位数据版本。
2. `Submission` 需要记录实际使用的题目版本、语言标定版本、有效限制快照和判题环境标识；不能只记录一个会随时间改变含义的 `problemId`。
3. 当前题目限制随 `JudgeRequest` 下发的边界仍然成立；未来由 server 根据题目版本、语言和环境解析出本次确定限制，judge 不负责选择策略。
4. 数据生成、验证和标定都可以复用 sandbox 的「安全运行并返回资源事实」能力，但属于运营任务，不应伪装成用户 Submission。
5. 大测试数据、生成产物和报告需要独立的资产存储；数据库保存元数据、关系、哈希和版本，不保存所有大文件内容。
6. Agent 不直接调用生产文件系统。它通过 server 暴露的受权任务接口编排生成、trial、benchmark 和发布检查。
7. 用户正式判题与运营批任务需要资源隔离、优先级和独立可观测性。
8. contracts 仍是跨语言边界唯一真源；实现上述能力时应先补产品数据模型和契约，再改 server/judge。
9. ProblemVersion 和 Submission 必须携带可追溯的代码模式；CORE 的完整源码模板保存在
   ProblemVersionLanguage。submission-service 在冻结 JudgeInput 时合并模板，Go judge 与 sandbox
   收到的始终是普通完整源码，不需要理解 ACM/CORE。

## 十二、已确认的产品决策

1. MVP 使用单工作空间，不做多租户。
2. MVP 使用单管理员，允许作者自审；数据模型仍保存创建人、审核人与操作记录。
3. MVP 支持 ACM 与 CORE 两种代码模式；CORE 用户只提交核心代码，平台将其合并到该题该语言的
   预设完整源码模板。不引入 SPJ、部分分和交互题。
4. C++ 优先。传统 OJ 端到端链路先用 C++ 验收；题目工厂的多语言价值在后续加入第二门语言时验证。
5. `Problem` 与 `ProblemVersion` 分离。发布版本不可变，提交必须绑定具体版本。
6. 环境相关限制以「题目版本 × 语言 × 判题环境」的绝对值保存，并保留标定版本和原始测量记录。
7. MVP 暂不接 AI。先完成传统 OJ 链路和可手动触发的确定性题目工厂，Agent 只在后续编排已有工具。

## 十三、未来工作触发条件

以下问题不属于当前已确认规则。相关阶段开始前必须在 `development/` 建立工作项并显式解决，不能由
实现者根据本文自行假设：

1. 首批付费/核心客户优先服务高校教学团队，还是商业题库与培训机构？两者对班级、协作、版权和私有部署的优先级不同。
2. 题目生产的主要入口是从零创建，还是从 HustOJ/HOJ/Polygon 等现有格式批量迁移？
3. C++ 之后优先加入 Python、Java 还是其它语言？缺少可靠参考实现的语言仍默认不对该题开放。
4. AI 使用云模型、私有模型还是可插拔提供方？私有题面、用户源码和隐藏数据分别允许发给哪些模型？该问题不影响 MVP。
5. 已发布题目产生新版本后，旧提交默认只保留原结果、后台自动重判，还是由运营者按场景选择？无论采用哪种，旧结果都必须保留原题目版本和标定信息。
6. 何时引入 SPJ、部分分、子任务、交互题和 hack 数据？这些能力会改变资产模型和验证流水线，
