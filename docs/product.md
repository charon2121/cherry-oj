## 一、产品定位

### 1.1 一句话定位

**cherry-oj 是一个面向学习者、教师和专业题库运营者的 Online Judge：先提供可信、完整的答题与
判题闭环，再把题目生产、验证、标定和长期维护变成可重复、可审计、可由 Agent 协助的运营流水线。**

“AI 原生”描述长期运营方式，不表示当前 MVP 依赖模型。产品必须先用确定性程序证明题目、测试数据、
判题结果和资源限制，再允许 Agent 调用这些能力提效。

### 1.2 两条产品链路

```text
答题链路：找题 → 阅读 → 编码 → 自测 → 提交 → 查看结果 → 再次改进

运营链路：定义题目 → 准备版本与数据 → 验证 → 配置环境与限制
          → 发布 → 观察 → 迁移、扩语种或修订
```

当前 MVP 首先证明答题链路，并提供支撑它所需的最小运营能力。完整题目工厂与 Agent 编排属于后续
方向，不能反向扩大当前 MVP。

### 1.3 产品原则

1. **用户闭环是准入条件。** 平台必须先具备成熟 OJ 的基本可靠性，不能用未来 AI 能力掩盖登录、
   题目、编辑、提交和结果体验的缺口。
2. **确定性先于智能化。** verdict、测试数据、限制和发布状态来自可执行规则与证据，不来自模型判断。
3. **版本与快照优先。** 已发布题目和正式提交的含义不能随未来改题、迁移或换环境而变化。
4. **系统错误不能伪装成用户错误。** WA、TLE、MLE、CE 描述用户程序；平台故障必须有独立语义。
5. **发布是显式决策。** 自动化和 Agent 可以生成草稿、报告与建议，但不能静默覆盖已发布事实。
6. **状态与证据同在。** 一个结果必须能追溯到输入版本、执行环境、限制和实际运行证据。

## 二、用户与核心任务

当前 MVP 只有两个业务角色，不建立多工作空间或完整 RBAC。

### 2.1 普通用户（USER）

普通用户需要：

- 登录后浏览和筛选可用题目；
- 阅读题面、样例、代码模式和支持语言；
- 编写并恢复代码草稿；
- 使用自定义输入调试，不污染正式提交记录；
- 正式提交并理解排队、判题、完成和失败状态；
- 查看自己的历史提交，区分代码错误、答案错误和平台故障。

### 2.2 管理员（ADMIN）

MVP 使用单管理员。管理员同时承担最小题目运营职责，可以自行创建、检查和发布版本，但系统仍保留
创建、修改与发布事实，不能因为“自己审核自己”而放弃版本和审计边界。

管理员需要：

- 维护账号和最小访问权限；
- 创建题目草稿、样例、语言模板、测试数据版本和限制；
- 在发布前完成必要的可判题检查；
- 发布不可变题目版本，并能追溯实际生效的环境与配置；
- 查看判题任务和平台故障，但不能通过浏览器直接操作 judge 或 sandbox。

后续是否拆分 Author、Reviewer、Operator 等角色，必须由新的产品 WORK 定义，不属于当前基线。

## 三、当前 MVP

### 3.1 目标

当前 MVP 的目标是证明：

> 管理员能够准备并发布一道可判题题目；普通用户能够从浏览器完成读题、自测、正式提交和结果回看；
> 任一正式结果都能解释“提交了什么、针对哪个题目版本、使用什么数据、限制和环境、为什么得到这个
> verdict”。

MVP 使用单工作空间、USER/ADMIN、C++、文本 `.in/.out` 数据、默认 checker、单个当前 ACTIVE 判题
环境和 Web 轮询。不引入多租户、完整审核分权或实时推送。

### 3.2 两个交付切片

完整 MVP 支持两种代码模式，但按纵向切片交付：

1. **首个切片：C++ ACM。** 用户提交包含 `main` 的完整程序，自行读取 stdin、写出 stdout。它必须
   先跑通管理员发布、题库、编辑、自测、正式提交、异步判题、结果详情和历史记录。
2. **第二个切片：C++ CORE。** 用户只提交题目要求的核心代码，平台按题目版本和语言使用预先发布的
   完整源码模板合并后判题。

首个切片的定义、待确认项和交付状态以
[WORK-002：交付 C++ ACM 答题闭环](../development/works/WORK-002/00-work.md) 为准。
PRD 不复制其进度，也不替它回答账号开通方式、WA 明细公开粒度和内部发布环境口径。

### 3.3 MVP 必备能力

#### 身份与访问

- 用户必须经过 server 统一认证；账号如何开通由当前产品 WORK 明确。
- 浏览器只访问 Gateway，不直接访问内部 Java 服务、Go judge 或 sandbox。
- 普通用户只能读取公开题目和自己的提交；管理能力只对 ADMIN 开放。

#### 题目与发布

- 管理员能够创建、编辑、预览和删除未发布且未被引用的草稿。
- 题目列表和详情展示标题、题面、样例、难度/标签、代码模式和当前允许语言。
- 发布前必须存在可用测试数据、语言配置、目标环境部署和有效绝对限制。
- 发布后的 ProblemVersion 不可原地修改；任何会改变判题含义的调整都创建新版本。

#### 编辑与自定义测试

- 代码工作台提供 C++ 编辑、题目/语言起始代码和本地草稿恢复。
- 自定义测试接收用户 stdin，返回 stdout、stderr、运行状态以及允许公开的资源事实。
- 自定义测试不创建正式 Submission，不改变题目通过状态。
- CORE 自测和正式提交使用同一版本的模板合并规则。

#### 正式提交与结果

- 创建正式提交必须具备幂等边界，页面刷新或请求重试不能制造重复记录。
- 用户能看到 Pending、Judging、Done 等生命周期，并在暂时查询失败后继续恢复。
- 终态至少正确区分 AC、CE、WA、TLE、MLE、OLE 和系统错误；合法 verdict 不能被前后端遗漏。
- 提交详情展示安全处理的编译诊断、总时间、总内存和产品允许公开的测试点摘要。
- “我的提交”能够按题目、语言、verdict 和时间回看历史记录。

#### 可追溯性

- 每个 Submission 绑定实际 ProblemVersion、TestDataVersion、语言、JudgeEnvironment、
  LanguageCalibration 和有效绝对限制。
- Submission 保存用户原始源码；不可变 JudgeInput 保存实际送判的完整源码。CORE 的模板合并结果
  只进入 JudgeInput，不向普通用户暴露完整 judgeTemplate。
- 发布新版本、替换标定或切换环境不能改变已有 Submission/JudgeInput 的含义。

### 3.4 MVP 完成基线

以下场景都具备实际验证证据时，才可以声明完整 MVP：

1. 管理员分别发布 C++ ACM 与 C++ CORE A+B 的不可变版本。
2. 普通用户完成找题、读题、编辑、自测、正式提交、结果查看和历史回看。
3. 正确代码得到 AC；编译错误得到 CE；错误输出得到 WA；平台故障不会被映射成用户错误。
4. CORE 用户只编写核心函数，服务端完成唯一占位符替换，Go judge 仍只接收普通完整源码。
5. 隐藏输入、标准答案、judgeTemplate、凭证和内部 JWT 不经页面、日志或 Kafka 泄漏。
6. 每次结果都能追溯题目版本、数据版本、环境指纹、标定和限制快照。

首个 C++ ACM 切片完成不等于完整 MVP，也不自动证明 CORE 或后续运营流水线已经交付。

## 四、核心产品概念

### 4.1 Problem 与 ProblemVersion

- Problem 是长期稳定的题目标识、归属、可见性和当前发布版本入口。
- ProblemVersion 是一次不可变的可判题内容快照，包含题面、代码模式、样例、checker、测试数据版本
  和允许语言。
- 草稿可以修改；已发布版本只能被新版本替代，不能原地覆盖。

### 4.2 代码模式与语言配置

每个 ProblemVersion 必须选择且只能选择一种 CodeMode：

- **ACM**：用户提交完整程序，自行处理标准输入输出。
- **CORE**：用户提交核心代码；平台使用 ProblemVersionLanguage 中该语言的 judgeTemplate 合并完整
  程序。模板必须包含且只包含一个字面量 `{{USER_CODE}}`。

starterCode 是用户可见的编辑起点；judgeTemplate 是内部判题资产，两者不能混为一份公开内容。

### 4.3 TestDataVersion

ACM 与 CORE 都使用原始文本 stdin/stdout 测试数据。TestDataVersion 是不可变数据内容与 hash 的
版本标识；大文件不进入数据库或 Kafka。

当前 MVP 允许管理员手工准备数据。生成器、输入校验器、oracle、差分验证和自动构建报告属于后续
确定性题目流水线。

### 4.4 JudgeEnvironment 与 LanguageCalibration

- JudgeEnvironment 表示会影响判题结果的系统、工具链、容器与配置基线，并提供环境指纹。
- LanguageCalibration 保存“题目版本 × 语言 × 判题环境”的绝对 CPU、时钟和内存限制。
- 当前 MVP 可以人工标定，但必须保存明确的绝对值与版本关系；未完成有效标定的组合不可提交。
- 迁移环境或替换标定产生新事实，不能回写历史提交。

### 4.5 Submission 与 JudgeInput

- Submission 是用户可见事实：用户原始源码、生命周期、verdict 和允许公开的结果。
- JudgeInput 是内部执行事实：完整源码、不可变版本引用、环境指纹和限制快照。
- 两者一对一并在同一 submission-service 本地事务中创建。源码不进入 Kafka，judging-service 使用
  受服务身份保护的内部 API 拉取 JudgeInput。

## 五、核心流程

### 5.1 管理员发布题目

```text
创建草稿
  → 填写题面、样例和代码模式
  → 配置 C++ starterCode / judgeTemplate（CORE 时）
  → 关联不可变测试数据版本
  → 确认目标环境已部署数据且存在有效限制
  → 预览并执行发布检查
  → 发布不可变 ProblemVersion
```

发布失败必须保留草稿和具体原因，不能产生半发布版本。当前 MVP 可以由同一 ADMIN 完成检查与发布，
但动作和版本仍需留痕。

### 5.2 用户答题

```text
登录
  → 浏览并打开公开题目
  → 确认代码模式和 C++
  → 编辑并恢复草稿
  → 可选：使用自定义 stdin 调试
  → 正式提交
  → 查看 Pending / Judging / Done
  → 查看安全结果并在历史提交中回看
```

加载、空数据、网络错误、未登录、无权限、提交中和成功都必须有独立界面状态。查询失败不能把已经
存在的 Submission 变成失败，也不能自动重建一条提交。

### 5.3 正式判题

正式提交由 server 冻结版本化输入并通过 Kafka 异步推进。Go judge 只负责编译、逐测试点运行、比对
和汇总 verdict；sandbox 只负责安全执行一条命令并返回资源事实。

HTTP 或消息传输是否成功描述平台交互，RunResult/JudgeResult/Submission 状态描述用户程序结果。
用户程序失败可以是正常的 2xx 业务响应，平台通信失败不能冒充 WA、TLE 或其它 verdict。

## 六、产品规则

以下规则是所有功能 WORK 的上游约束：

- **PRD-RULE-001：单一写入者。** 每类业务事实只有一个拥有服务，其它服务通过契约读取。
- **PRD-RULE-002：发布版本不可变。** 题面、模式、样例、checker、数据和语言模板的语义变化创建新版本。
- **PRD-RULE-003：提交输入不可变。** 正式 Submission 创建后冻结 JudgeInput，后续配置变化不得回写。
- **PRD-RULE-004：限制使用绝对值。** 生效限制按题目版本、语言和环境解析，单位为 ns/bytes；倍率
  只能作为未来建议策略，不能替代最终绝对值。
- **PRD-RULE-005：环境可验证。** judge 返回的 environmentFingerprint 必须与冻结输入一致。
- **PRD-RULE-006：用户错误与系统错误分离。** 平台故障不能判成 WA/TLE/MLE，未知情况向严格方向处理。
- **PRD-RULE-007：敏感数据最小暴露。** 隐藏数据、标准答案、模板、源码、密码和令牌不得越过必要边界。
- **PRD-RULE-008：不可信代码只进 sandbox。** 用户代码以及未来 Agent 生成代码都不能直接在 server
  或宿主环境执行。
- **PRD-RULE-009：状态可恢复且幂等。** 重试、重复消息和租约过期不能产生重复提交或让终态回退。
- **PRD-RULE-010：视觉不是唯一语义。** verdict、状态和错误必须有文字或符号，支持键盘和基本无障碍。

## 七、质量与安全基线

### 7.1 正确性与可复现性

- 同一提交必须能重建当时的完整判题输入和解释最终 verdict。
- 数据版本、题目版本、环境、标定和限制都使用稳定标识。
- 契约是跨服务/跨语言字段唯一真源，不能由某个实现私自扩展后再反推。

### 7.2 可靠性

- 正式提交创建、JudgeInput、幂等记录和 Outbox 必须保持原子边界。
- Kafka 至少一次投递下，重复事件不得重复执行有效任务或覆盖更新结果。
- 长任务有超时、有限重试和 fencing；迟到 Worker 不能覆盖当前 Attempt。
- 用户可以在页面刷新或短暂网络失败后恢复查询。

### 7.3 安全

- 浏览器使用 Session Cookie；内部服务身份、JWT 和敏感模板不暴露给前端。
- 题面 Markdown、编译日志和用户输出在展示前必须净化。
- 日志和事件不包含密码、Cookie、JWT、完整隐藏数据、标准答案或不必要的源码。
- 公网运行不可信代码前，sandbox 隔离必须达到明确的安全验收标准。

### 7.4 可用性与可访问性

- 题库、题目、编辑器、提交列表和详情都有 loading、empty、error、unauthorized 与 success 状态。
- 键盘可以完成核心答题流程；焦点、标签和错误信息可被辅助技术理解。
- verdict 不只依赖颜色；窄屏下关键提交与结果信息仍可访问。

### 7.5 指标

内部 MVP 先记录而不虚构目标值：

- 正式提交创建成功率、系统错误率和从创建到终态的耗时分布；
- 各 verdict 分布、判题队列等待和执行耗时；
- 自定义测试与正式提交的失败原因；
- 题目版本、环境和标定无法解析导致的拒绝数量。

目标值只有在获得稳定基线和部署规模后，由独立改进 WORK 确认。

## 八、当前非目标

以下能力不属于当前 MVP，不能因为旧 PRD 曾列为 P0/P1/P2 就直接进入实现：

- Agent、模型供应商、提示词、AgentTask、模型预算和自动发布；
- 自动数据生成器、输入校验器、oracle、差分/变异测试和完整题目工厂；
- 自动多语言基准测试、限制建议、批量迁移和历史提交回放；
- C++ 以外的语言；
- 多工作空间、完整 RBAC、多人审核协作和复杂运营后台；
- 竞赛、排行榜、班级、课程、作业、讨论和面向用户的 AI 复盘；
- SPJ、部分分、子任务、交互题、输出题和 hack 数据；
- 自动重判、WebSocket/SSE 判题推送以及用户可见的复杂计分；
- 通用 CORE 函数签名、类型系统和值编解码框架。

非目标表示“当前不承诺”，不是永久禁止。启动其中任一能力前必须建立 product WORK，重新定义使用者、
体验、数据、安全、兼容和验收边界。

## 九、已确认的演进方向

演进顺序表达依赖关系，不表达当前完成度：

1. **C++ ACM 纵向闭环。** 先证明传统 OJ 的最小用户与管理员链路。
2. **C++ CORE。** 在不改变 Go judge/sandbox 的前提下，证明服务端模板合并和版本追溯。
3. **确定性题目运营流水线。** 再引入生成器、校验器、oracle、验证报告、真实基准样本、限制建议、
   环境迁移和新增语言；即使没有模型也必须可独立运行。
4. **受控 Agent 编排。** Agent 只能调用已经确定、可审计、可重跑的工具，默认产出草稿和建议；发布、
   删除、覆盖配置、扩大数据访问或高成本任务必须人工确认。
5. **规模化与教学扩展。** 多角色、多工作空间、批量运营、课程或竞赛等能力在真实需求出现后分别立项。

长期运营方向必须保持以下边界：

- AI 不能签发 verdict、伪造运行结果或把推断当正确性证明；
- Agent 生成的代码仍是不可信代码，只能进入 sandbox；
- 隐藏测试数据、用户源码和私有题面是否可发送给外部模型必须单独做数据与隐私决定；
- 新语言或新环境不能套用未经真实验证的统一倍率；
- 已发布事实的变化继续通过新版本、显式批准和可回退切换完成。

## 十、已确认决定与待决入口

### 10.1 已确认决定

1. 单工作空间；MVP 不做多租户。
2. MVP 业务角色只有 USER 与 ADMIN；单管理员允许自行发布。
3. 完整 MVP 支持 C++ ACM 与 C++ CORE，先交付 ACM 纵向切片。
4. CORE 使用题目版本语言级模板的唯一占位符替换，不建立通用函数类型系统。
5. Problem 与不可变 ProblemVersion 分离，正式提交绑定实际版本。
6. 数据、环境、标定和绝对限制都进入可追溯链；历史提交不被后续配置改写。
7. 正式判题使用 Kafka 异步推进，Web 先轮询 Submission。
8. Go judge 不理解用户、CORE 模板、Submission、Kafka 或标定；sandbox 不理解判题。
9. 当前 MVP 手工准备测试数据和标定；自动题目工厂在基础闭环后建设。
10. Agent 不属于 MVP；先建立确定性工具，再让 Agent 受控编排。
