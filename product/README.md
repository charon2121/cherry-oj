# cherry-oj 产品文档中心

`product/` 是产品需求、产品决策与版本验收的唯一真源，并随 Git 提交。它位于 `PRD.md` 与
`tasks/` 之间：产品负责人围绕用户结果审核 `REQ`，研发人员围绕实现工作执行 `TASK`。

## 快速入口

- 当前产品需求：[`requirements/`](./requirements/)
- 产品决策：[`decisions/`](./decisions/)
- 版本验收：[`releases/`](./releases/)
- 可复制模板：[`templates/`](./templates/)
- 元数据约束：[`schema/`](./schema/)

产品负责人审核一项需求时，先读对应 REQ 的“一句话结果、用户流程、产品规则、范围、产品验收场景
和未决问题”。技术实现和验证证据需要下钻时，再打开关联 TASK 或技术设计。

## 文档分层

```text
PRD / 产品路线图
        │ 定义方向、用户、优先级和阶段目标
        ▼
REQ / 产品需求
        │ 定义一项可独立演示、可由产品验收的用户能力
        ├──────────────┐
        ▼              ▼
TASK / 研发任务     PD / 产品决策
        │              │
        └──────┬───────┘
               ▼
       REL / 产品版本验收
```

各类文档只回答自己负责的问题：

- `PRD.md`：产品为谁服务、总体范围、路线图和成功指标；
- `REQ`：本次为哪类用户交付什么能力、产品规则和验收场景；
- `PD`：长期影响产品行为的方案选择及理由；
- `TASK`：具体研发工作、依赖、技术验证和执行状态；
- `docs/`、`contracts/`：架构、数据、接口和实现边界；
- `REL`：里程碑实际交付了哪些 REQ、验收结论和遗留问题。

同一事实只写在一个真源中。REQ 可以链接技术设计，但不复制接口、表结构或实现步骤。

## REQ 的粒度

一份 REQ 表示“一项可以独立演示和验收的用户能力”，不表示一个页面、接口、数据库表或服务。

合适的例子：

- 用户可以完成 C++ ACM 题的自测、提交和结果查看；
- 管理员可以创建并发布一个不可变的 CORE 题目版本；
- 运营者可以重跑失效标定并审核新的语言限制。

以下内容通常属于 TASK：新增提交按钮、创建 submission 表、实现 Kafka consumer、初始化某个服务、
不改变产品行为的重构和测试补强。

判断粒度时问两件事：

1. 产品负责人能否通过一段连续操作演示它？
2. 不理解内部实现的人能否判断它是否完成？

任一答案为“不能”，说明它更适合作为 TASK，或需要重新切分。

## 什么时候创建 REQ

满足以下任一条件时创建或更新 REQ：

- 新增或改变用户能够完成的事情；
- 改变用户流程、权限、可见信息或业务规则；
- 同一产品结果需要多个技术领域共同交付；
- 需要产品负责人确认范围或执行产品验收；
- PRD 中的阶段能力开始进入实际研发。

纯技术治理可以没有 REQ。它仍需在 TASK 中说明风险、目标和技术验收标准。

## 产品需求状态

```text
draft
  → product_review
  → ready
  → delivering
  → product_acceptance
  → accepted
  → released
```

另有 `paused` 和 `cancelled`。

- `draft`：需求正在澄清，允许存在未决问题；
- `product_review`：审核用户、问题、范围、流程、规则和验收场景；
- `ready`：产品定义已就绪，可以正式拆解和交付；
- `delivering`：至少一项直接交付 TASK 已开始；
- `product_acceptance`：完整用户链路可演示，等待产品验收；
- `accepted`：产品验收人确认用户能力符合 REQ；
- `released`：能力进入目标使用环境，并纳入 REL。

TASK 的 `review` 只表示技术审核。所有 TASK 完成不会自动把 REQ 变成 `accepted`。

## 进入 ready 的条件

- 目标用户和使用场景明确；
- 本次包含和不包含的范围明确；
- 主流程、关键异常、权限和版本规则明确；
- 产品验收场景可以实际执行；
- 没有会导致方案完全不同的未决产品问题；
- 已指定产品负责人和验收人。

## 进入 product_acceptance 的条件

- 阻塞产品验收的 TASK 已完成技术审核；
- 演示环境、账号和必要数据已经准备好；
- 每条产品验收场景都有实际结果；
- 已知限制、风险和延期项已经汇总；
- 范围变化已经写回 REQ，而不是只存在于任务或聊天中。

## 产品审核方式

需求审核依次回答：

1. 这是哪个用户在什么场景下的问题？
2. 交付后用户能完整完成什么？
3. 主流程、入口和结果是否明确？
4. 权限、版本、可见性和失败处理是否符合预期？
5. 哪些内容明确不在本次范围？
6. 验收场景是否足以证明用户能力成立？
7. 是否还有会改变范围的未决问题？

产品验收以场景演示为主：先按目标用户完成主流程，再演示关键失败场景，最后核对版本、权限、
可追溯证据、已知限制和延期项。底层测试作为关联证据保留，不要求产品负责人逐条阅读。

## REQ 与 TASK 的追踪关系

REQ 通过 `delivery_tasks` 引用直接支撑它的 TASK；TASK 通过 `requirement_ids` 引用对应 REQ。
两边必须同时记录，`scripts/product check` 会拒绝单边关系。

新建 TASK 时可以直接关联：

```bash
scripts/task new \
  --title "实现正式提交创建接口" \
  --type feature \
  --area submission/api \
  --priority P0 \
  --requirement REQ-0001 \
  --milestone M1-traditional-oj
```

历史任务和纯技术治理允许 `requirement_ids: []`、`milestone: null`，不强制回填虚假关系。

## 产品决策

只有以下决策建立 PD：

- 候选方案会产生长期不同的用户行为；
- 影响多个 REQ；
- 涉及权限、数据可见性、发布规则或兼容策略；
- 将来很可能追问“为什么这样定”。

实现方案选择继续写技术 ADR 或设计文档，不进入 PD。

## 需求变更

- `draft`、`product_review`：可以直接修改，重要结论写入变更记录；
- `ready`、`delivering`：改变流程、范围、规则或验收口径时，必须记录原因、受影响 TASK，并由产品
  负责人重新确认；必要时退回 `product_review`；
- `accepted`、`released`：不得静默改写历史验收事实。改变已接受的产品行为时创建新 REQ 或新版本。

技术实现调整但产品行为不变时，只更新 TASK 或技术设计。

## Agent 边界

Agent 可以整理 REQ 草稿、发现遗漏场景、建议 TASK 拆解、维护链接、汇总验证证据和检查一致性。

Agent 不能自行决定目标用户、产品优先级或重大范围变化，不能因 TASK 全部完成就宣布产品验收通过，
也不能为了填满模板虚构用户数据或成功指标。

## 文件与 ID

- 产品需求：`requirements/REQ-0001-short-slug.md`；
- 产品决策：`decisions/PD-0001-short-slug.md`；
- 版本验收：`releases/REL-0001-short-slug.md`；
- ID 创建后永不修改、复用或因归档而变化；
- front matter 每行一个字段，值使用 JSON 兼容写法，不使用缩进对象或 YAML 特有类型；
- 时间使用带时区的 ISO 8601；
- 正文从 [`templates/`](./templates/) 复制，不删除必需章节。

## 检查与产品视图

```bash
scripts/product list
scripts/product check
python3 scripts/product_test.py
```

`list` 只展示产品需求、里程碑、负责人和研发任务摘要，不默认展示分支、租约、DTO 或测试命令。
`check` 校验字段、状态、ID、文件名、日期、引用和 REQ/TASK 双向关系，不改变任何文档状态。
