# 智能体协作开发文档系统规范

版本：0.1
状态：草案

---

# 1. 目标

本规范用于定义一套适合人和智能体共同开发软件的项目文档体系。

系统需要解决以下问题：

1. 不同层级的信息不能混在一起。
2. 不同类型的开发工作需要走不同流程。
3. 智能体需要知道当前应该读取哪些信息。
4. 智能体需要知道当前允许修改哪些内容。
5. 开发过程中产生的未知、风险和改动必须显式记录。
6. 功能、设计、任务、代码、测试之间需要能够追踪。
7. 文档必须能够被脚本自动生成、检查和管理。
8. 项目不能因为引入流程而产生大量无意义文档。
9. 完成状态必须由验证结果支撑。
10. 项目中的重要历史信息必须能够长期保留。

本规范同时作为后续“项目文档管理工具”的需求依据。

---

# 2. 核心模型

所有开发工作统一抽象为：

# 工作项

一个工作项代表一次需要被跟踪、设计、开发或验证的工程工作。

例如：

```text
新增项目搜索
增加 Redis 缓存
修复登录失败问题
重构订单模块
升级数据库版本
优化接口性能
增加安全审计
```

工作项进入系统后，需要依次完成：

```text
创建工作项
    ↓
判断工作类型
    ↓
判断风险
    ↓
判断影响面
    ↓
识别额外关注
    ↓
生成开发流程
    ↓
生成所需文档
    ↓
开发
    ↓
复核
    ↓
验证
    ↓
上线
    ↓
线上观察
    ↓
记录项目记忆
```

# 3. 基本原则

## 3.1 别混层

以下内容必须分开表达：

```text
为什么做
做什么
怎么使用
怎么实现
怎么开发
怎么验证
```

产品定义不能直接夹杂技术实现。

技术方案不能重新定义产品行为。

开发任务不能重新决定产品需求或整体架构。

---

## 3.2 冲突时知道听谁的

项目中的信息按以下优先级处理：

```text
人工确认的决定
↓
功能定义 / 能力定义 / 问题说明 / 改动说明
↓
体验设计 / 技术方案 / 技术决策
↓
开发计划
↓
开发任务
↓
代码与测试
↓
代码注释
↓
智能体自己的推断
```

上层和下层发生冲突时，默认以上层为准。

代码不能反向覆盖已经确认的需求。

---

## 3.3 状态必须明确

禁止：

```text
差不多完成
基本好了
应该没问题
```

统一使用明确状态。

---

## 3.4 只改该改的

每个开发任务都必须明确：

```text
可以看什么
可以改什么
不要动什么
```

发现需要超出当前范围时，必须先提出改动升级。

---

## 3.5 不要偷偷脑补

所有重要未知必须显式记录。

未知分为：

```text
已确认

可以暂时按某个假设继续

必须确认后才能继续
```

最后一种状态会让当前流程卡住。

---

## 3.6 上游有问题就往上提

开发过程中如果发现：

```text
功能定义有问题
技术方案不可行
任务范围不足
```

不能偷偷修改原定义。

必须提出对应改动。

---

## 3.7 每个重要要求都能往下追

系统需要支持：

```text
要求
↓
设计
↓
开发任务
↓
代码
↓
测试
↓
验证结果
```

---

## 3.8 别只说“好了”

智能体不能仅声明：

```text
完成
已修复
已经实现
```

必须同时提供验证结果。

---

## 3.9 人只看值得看的东西

人工主要处理：

```text
关键决定
待确认项
高风险
产品行为变化
重大技术变化
不可逆操作
```

普通实现细节尽量交给智能体和自动检查。

---

## 3.10 能自动检查的就自动检查

以下规则尽量通过程序完成：

```text
文档格式
必填字段
编号唯一性
引用关系
任务范围
状态变化
测试结果
代码检查
流程完整性
```

---

## 3.11 不同工作走不同流程

产品功能、基建、问题修复和重构维护不能强制走同一套流程。

---

## 3.12 不需要的流程别硬走

流程用于减少：

```text
不确定性
工程风险
```

而不是为了生产文档。

---

# 4. 工作类型

系统支持五种主要工作类型。

---

## 4.1 产品功能

用户能够直接感受到的新能力或行为变化。

例如：

```text
搜索
登录
支付
个人资料
项目管理
页面功能
交互变化
```

类型标识：

```text
product
```

---

## 4.2 基建

主要给系统、开发者、运维人员、智能体或其他模块使用。

例如：

```text
缓存
消息队列
日志系统
任务调度
权限底座
构建系统
发布系统
数据库基础设施
内部开发工具
公共服务
```

类型标识：

```text
infra
```

---

## 4.3 问题修复

系统实际行为与预期行为不一致。

例如：

```text
页面报错
接口异常
数据错误
回归问题
边界问题
```

类型标识：

```text
fix
```

---

## 4.4 重构维护

外部行为原则上保持不变，主要改善内部工程状态。

例如：

```text
代码重构
模块拆分
依赖升级
技术债
删除旧代码
测试整理
```

类型标识：

```text
maintenance
```

---

## 4.5 工程改进

主要用于改善系统性的工程指标或控制工程风险。

例如：

```text
性能
稳定性
安全
隐私
成本
质量
合规
```

类型标识：

```text
improvement
```

---

# 5. 额外关注

工作类型决定主流程。

额外关注决定是否增加专项检查。

标准关注项包括：

```text
security        安全
privacy         隐私
data            数据
performance     性能
reliability     稳定性
observability   可观测
compatibility   兼容性
accessibility   无障碍
cost            成本
release         上线风险
```

一个工作项可以拥有多个额外关注。

例如：

```yaml
type: product

concerns:
  - security
  - privacy
  - data
```

---

# 6. 风险级别

风险分为四级：

```text
low
medium
high
critical
```

对应：

```text
低
中
高
关键
```

---

## 6.1 低风险

特点：

```text
影响有限
容易发现问题
容易回退
数据风险低
```

---

## 6.2 中风险

特点：

```text
可能影响多个模块
需要明确验证
需要明确回退方式
```

---

## 6.3 高风险

特点：

```text
影响核心业务
可能影响重要数据
可能影响大量用户
可能影响关键基建
```

需要正式技术方案和独立复核。

---

## 6.4 关键风险

包括但不限于：

```text
不可逆数据变化
权限模型变化
登录认证体系变化
严重安全风险
核心数据库变化
生产发布体系变化
可能造成大面积服务不可用
无法快速回退
```

关键风险必须人工确认。

---

# 7. 风险自动升级规则

满足以下情况时，不允许直接标记为低风险：

```text
修改数据库结构
修改持久化数据格式
修改公共接口
修改登录或权限
修改公共基础模块
引入新的外部依赖
涉及用户隐私
涉及计费或资金
涉及并发、事务或数据一致性
修改发布基础设施
无法快速回退
```

满足以下情况时，应至少评估为高风险：

```text
不可逆数据迁移
权限模型整体变化
登录认证模型变化
核心数据库结构变化
大规模数据迁移
核心业务链路变化
生产基础设施变化
密钥或凭证机制变化
多个核心服务同时受影响
```

---

# 8. 影响面

影响面分为：

```text
local
multi-module
system
```

对应：

```text
局部
跨模块
系统级
```

---

## 8.1 局部

通常满足：

```text
仅修改单个模块
无公共接口变化
无共享数据变化
```

---

## 8.2 跨模块

满足以下任意情况：

```text
多个模块需要配合
公共接口发生变化
共享组件发生变化
共享数据发生变化
```

---

## 8.3 系统级

通常包括：

```text
登录体系
权限体系
核心数据库模型
全局配置
公共基础库
发布系统
网络层
多个服务之间的协议
```

---

# 9. 流程选择规则

流程按以下顺序生成：

```text
WORK Type 基础流程模板
→ 风险级别增量规则
→ 影响面增量规则
→ concern 专项规则
→ 当前未知与人工确认卡点
→ 当前 WORK 的实际 workflow
```

主流程由 WORK Type 决定，不由 TASK 决定。TASK 是流程确定后拆出的执行单元，继承所属 WORK 的
类型、范围和上游定义。

各项输入分别回答：

```text
工作类型
→ 走哪条主流程

额外关注
→ 还需要检查什么

风险级别
→ 检查要多严格

影响面
→ 检查要覆盖多远

当前未知
→ 现在能不能继续
```

风险、影响面和 concern 可以把可选阶段升级为必做、插入阶段、要求额外文档、向阶段增加检查门禁、
增加人工确认或要求上线与观察。它们不能把所有 WORK 改造成同一条流程；系统必须保留各 WORK Type
的基础顺序和语义。

---

# 10. 流程、阶段与文档

流程是控制面，描述顺序、必需性、进度、卡点和检查门禁；文档是产物面，记录定义、方案、决定和
证据。流程阶段与文档不是一一对应关系。

必须支持：

```text
一个阶段没有独立文档
一个阶段关联一份文档
一个阶段关联多份文档
同一份文档支撑多个阶段
一份文档内部覆盖多个细分步骤
```

例如开发、复核、上线和观察可以没有独立 Markdown；多个 TASK 可以共同支撑开发；同一 TASK 同时
关联“开发任务”和“开发”阶段；重构的当前问题、目标状态、不变条件和影响检查可以合并在一份
CHANGE 中。

每个阶段至少包含：

```yaml
stage: definition
label: 功能定义
requirement: required
status: ready
status_source: derived
artifacts: [FEATURE-001]
checks: [definition, scope]
source: profile:product
reason: product 基础流程
```

`artifacts` 只能引用本 WORK 的受管理文档，也可以为空。

---

## 10.1 阶段必需性

阶段必需性只能是：

```text
required
optional
```

对应：

```text
必做
可选
```

必做阶段不完成不能跨过对应的 WORK 状态边界。可选阶段可以明确跳过。不适用于该 WORK Type 的阶段
不写入实际 workflow，而不是统一生成 `not-needed` 占位节点。

## 10.2 阶段进度

阶段实际进度只能是：

```text
pending
ready
doing
done
skipped
blocked
```

对应待推进、可推进、进行中、已完成、已跳过、已卡住。`status_source` 使用 `derived` 或 `manual`，
区分事实推导与显式操作。`skipped` 只适用于 optional 阶段，并必须保留原因；`blocked` 表示阶段适用
但缺少决定、信息、权限或依赖。

阶段状态优先根据 artifacts、TASK、VERIFY 和 WORK 的事实推导：定义文档确认后定义阶段完成，TASK
进入 ready 后任务拆分完成，所有 TASK done 后开发完成，approved/pass VERIFY 使复核与验证完成，
WORK released / confirmed 分别推进上线和观察。无法可靠推导的价值判断仍由负责人确认。

```text
↓
技术方案
↓
开发计划
↓

↓
开发
↓
复核
↓
验证
↓
上线
↓
线上观察
↓

```

```text
↓

↓

↓

↓

↓

↓
```

# 13. 问题修复默认流程

```text
问题说明
↓
问题复现与确认预期
↓
原因与修复方案
↓
修复任务
↓
开发
↓
复核
↓
回归验证
↓
上线
↓
观察
```

低风险问题修复可以不生成独立技术方案。

但必须有：

```text
实际是什么
应该是什么
怎么复现
怎么确认修好了
```

问题说明、复现、实际结果和预期结果合并在 ISSUE。复杂修复使用独立 DESIGN；TASK 同时支撑修复任务
和开发阶段；回归证据写入 VERIFY。高风险或系统级修复增加 PLAN、DECISION 和 MEMORY。

# 14. 重构维护默认流程

```text
改动说明
↓
技术方案
↓
开发计划
↓
开发任务
↓
开发
↓
复核
↓
回归验证
```

重构维护最重要的定义是：

```text
哪些东西不能变
```

改动说明使用 CHANGE，并在同一文档内依次记录当前问题、目标状态、不变条件、影响检查和回归要求。
默认 artifacts 为 CHANGE、DESIGN、PLAN、TASK 和 VERIFY。上线、观察和 MEMORY 默认可选，由风险、
影响和 concern 增量规则升级。

# 16. 快速流程

满足以下所有条件时，可以进入快速流程：

```text
低风险
局部影响
无安全问题
无数据迁移
无公共接口变化
容易回退
完成标准明确
```

快速流程仍然保留 WORK Type 的定义语义，不统一成一种文档：

```text
对应类型的简短定义
↓
开发任务
↓
开发
↓
自动验证
↓
完成
```

产品和基建仍保留 EXPERIENCE；可以跳过的只是标记为 `fast_skippable` 的独立 DESIGN、PLAN 等产物。
重构维护可以缩短为 CHANGE + TASK + VERIFY；低风险局部修复使用 ISSUE + TASK + VERIFY。跳过的可选
阶段必须记录 `source=overlay:fast` 与原因。

---

# 17. 强制完整流程

满足以下任意条件时，不允许使用快速流程：

```text
关键风险
系统级影响
不可逆操作
重大数据迁移
权限体系变化
登录体系变化
核心架构变化
核心基建变化
无法可靠回退
重大业务规则变化
```

完整流程不是另一种 WORK Type，而是在原类型流程上增加严格性。高风险或系统级工作至少增加：

```text
影响面检查
↓
技术方案
↓
技术决策
↓
开发计划
↓
独立复核
↓
完整验证
↓
回退检查
↓
项目记忆
```

`critical` 或安全敏感工作再增加人工确认。数据、公共接口、安全、用户可见或 release 关注使上线与
观察成为必做；性能、可靠性、可观测和成本关注使观察成为必做。系统级影响增加跨模块回归，但内部
维护工作不会仅因为 `impact=system` 就被错误认定为必须业务上线。

# 18. 文档类型

系统需要支持以下核心文档。

```text
工作项
产品说明
功能定义
能力定义
问题说明
改动说明
改进说明
体验设计
技术方案
技术决策
开发计划
开发任务
验证结果
项目记忆
```

并非每个工作项都必须生成所有文档。

文档类型不是流程阶段类型。阶段通过 `artifacts` 引用零份、一份或多份上述文档；目录中的 00–80
前缀只排序实际文档产物，不表示流程是否必做或是否完成。

# 19. 工作项

工作项是整个文档体系的入口。

建议文件标识：

```text
WORK
```

基础字段：

```yaml

title:

work_type:
status:
risk:
impact:
concerns:

```

还需要记录：

```text
为什么要做

成功标准

当前流程

待确认项

关联文档
```

# 20. 工作项状态

工作项统一使用：

```text
todo
ready
doing
implemented
verified
released
confirmed
cancelled
```

对应：


# 41. 文档关系

系统必须支持以下关系：

```text
belongs_to
depends_on
related_to
implements
verifies
supersedes
blocks

artifacts
```

语义：

```text
belongs_to
属于某个工作项

depends_on
依赖另一个对象

related_to
有关联但不是强依赖

implements
实现某个要求或设计

verifies
验证某个要求或任务

supersedes
替代旧文档

blocks
阻止另一个对象继续

artifacts
某个流程阶段使用哪些本工作项文档作为产物或证据；允许零到多份，同一文档也可支撑多个阶段
```

# 47. 改动升级

开发过程中发现需要扩大改动时，只允许三种结果。

---

## 47.1 普通实现调整

```text

```

可以在任务范围内处理。

---

## 47.2 技术方案变化

技术实现路线发生明显变化。

必须：

```text

必要时更新开发计划
```

## 47.3 产品行为变化


# 48. 实现偏差

复核和开发应尽量分离。

```text
有没有实现偏差

有没有明显安全问题

有没有缺测试
```

复核智能体默认只报告问题，不直接修改代码。

# 55. 文档目录

开发过程文档统一保存在 `development/`。一个工作项必须对应一个独立目录，工作项入口和它的所有
附属文档必须聚合在该目录内，不允许再按 FEATURE、EXPERIENCE、DESIGN、TASK 等文档类型拆到
不同的全局目录。

```text
development/
├── README.md
├── SPECIFICATION.md
├── index.json
├── schema/
├── templates/
└── works/
    └── WORK-001-example/
        ├── 00-work.md
        ├── 10-feature-FEATURE-001.md
        ├── 20-experience-EXPERIENCE-001.md
        ├── 30-design-DESIGN-001.md
        ├── 40-decision-DECISION-001.md
        ├── 50-plan-PLAN-001.md
        ├── 60-task-TASK-001.md
        ├── 70-verify-VERIFY-001.md
        └── 80-memory-MEMORY-001.md
```

工作项目录名必须是：

```text
WORK-<永久编号>-<语义化短名>
```

目录内文件必须按信息层级使用固定前缀：

```text
00  WORK 工作入口
10  PRODUCT / FEATURE / CAPABILITY / ISSUE / CHANGE / IMPROVEMENT 定义
20  EXPERIENCE 体验
30  DESIGN 技术方案
40  DECISION 技术决策
50  PLAN 开发计划
60  TASK 开发任务
70  VERIFY 验证证据
80  MEMORY 长期记忆
```

`WORK` 入口固定命名为 `00-work.md`。其他文档固定命名为
`<层级>-<小写类型>-<永久 ID>.md`，例如 `30-design-DESIGN-002.md`。同一层的文件按类型名和永久
ID 获得稳定顺序，不额外表达上下级关系。层级前缀只表达信息层次和阅读顺序，不替代永久 ID，也
不能用于重新编号。它排序的是实际文档产物，不是 workflow stage；开发、复核、上线和观察等无文档
阶段不会为了填满编号而创建空 Markdown。

已归档、废弃或被替代的文档仍保留在原工作项目录中，只改变元数据状态。这样可以持续保留一个工作
项的完整上下文、历史关系和目录内顺序。

项目根目录保留：

```text
AGENTS.md
```

用于告诉智能体：

```text
项目总规则

文档系统入口

开发规则

禁止事项

脚本命令入口
```

---

# 56. 文档合并

小型工作不需要生成所有文档类型，但必须保留能独立表达定义、执行范围和验证证据的最小 artifacts：

```text
WORK
+ 对应类型定义（FEATURE / CAPABILITY / ISSUE / CHANGE / IMPROVEMENT）
+ TASK
+ VERIFY
```

一份文档可以覆盖同一信息层的多个细分步骤。例如 CHANGE 可以同时包含：

```text
当前问题
目标状态
不变条件
影响检查
回归要求
```

这些章节必须明确分开。不能把拥有不同状态机和责任边界的定义、TASK、VERIFY 全部塞入
`00-work.md`，否则 artifact 状态、任务权限和验证证据无法独立追踪。是否生成 DESIGN、PLAN、MEMORY
等独立文件由类型模板和增量规则决定。

---

# 57. 文档拆分

满足以下情况时应考虑拆成独立文档：

```text
内容较长

多人或多个智能体共同使用

会被多个工作项复用

需要独立版本管理

属于长期技术决策

需要独立审批

需要长期维护
```

拆分只改变工作项目录内的文件数量，不改变文档归属。不得为拆分后的文档建立按类型划分的全局
`features/`、`designs/`、`tasks/` 等目录。

---

# 58. 文档状态

文档可以使用：

```text
draft
review
approved
deprecated
superseded
archived
```

对应：

```text
草稿
待确认
已确认
已废弃
已替代
已归档
```

只有已经确认的上游文档可以作为稳定开发依据。

低风险快速流程可以省略独立 review 状态，直接将已补全的定义从 draft 确认为 approved；TASK 进入
ready 前依赖仍必须满足，不能把带占位内容的草稿直接当成开发依据。

---

# 59. 文档生成规则

脚本系统需要能够根据工作项：

1. 创建独立工作项目录与 `00-work.md` 入口。
2. 判断工作类型。
3. 生成基础元数据。
4. 根据流程在同一工作项目录内生成所需文档。
5. 根据模板生成标准章节。
6. 自动建立引用关系。
7. 自动分配编号。
8. 自动填写创建和更新时间。
9. 自动生成当前流程状态。
10. 避免生成不适用文档。
11. 按信息层级生成固定文件名前缀。
12. 先应用 WORK Type 基础模板，再叠加风险、影响面和 concern 规则。
13. 为每个阶段生成 requirement、progress、status_source、artifacts、checks、source 和 reason。
14. 允许一个阶段没有文档、关联多份文档，以及一份文档支撑多个阶段。

# 60. 文档校验规则

脚本系统至少需要检查：

```text
元数据格式是否合法

编号是否唯一

文档类型是否合法

状态是否合法

工作项目录名是否与 WORK 永久 ID 一致

附属文档是否与所属 WORK 位于同一目录

文件名层级前缀是否与文档类型一致

文件名中的类型和永久 ID 是否与元数据一致

工作项是否存在

引用对象是否存在

依赖是否形成循环

必填字段是否存在

流程要求的文档是否存在

workflow 是否匹配 WORK Type 基础模板

风险、影响面和 concern 增量是否已经进入 workflow

阶段顺序、必需性、检查项和规则来源是否合法

阶段 artifacts 是否存在且属于当前 WORK

必需文档是否至少关联一个流程阶段

阶段进度是否与文档、任务、验证和 WORK 状态一致

卡点是否已经解决

要求是否存在对应任务

重要要求是否存在验证

已验证任务是否存在验证结果

已上线工作是否通过验证

文档状态和工作项状态是否冲突

development 顶层是否重新出现按文档类型划分的目录

工作项目录是否保持扁平且只包含受管理的 Markdown 文档
```

# 61. 内容级校验

除了结构校验，智能体可以进行语义检查。

例如：

```text
功能定义中是否混入大量技术实现

技术方案是否擅自改变产品行为

开发任务是否超出技术方案

代码是否和功能定义冲突

验证是否真的覆盖验收要求

是否存在没有声明的关键假设
```

这类检查可以由智能体完成，不要求纯脚本规则完成。

# 62. 文档管理能力

脚本系统需要支持以下管理动作：

```text
创建
查看
更新
查询
列出
关联
检查
归档
废弃
替代
追踪
生成流程
刷新状态

按当前分类与风险重建流程

推进没有独立 artifact 的操作阶段
```

有 artifacts 的阶段只能由文档、TASK 或 VERIFY 的事实推进；`clarify` 由 blocking_items 推进。复核、
上线、观察等没有独立 artifact 的阶段可以显式推进，必做阶段不得标记为 skipped，每次变化必须记录
理由并检查前置 required 阶段。

归档、废弃和替代不得把文档移出所属工作项目录；查询和追踪必须从工作项目录内的聚合结构发现文档。

# 64. 流程状态计算

工作项状态不应完全依赖人工填写。

脚本可以根据实际情况推导部分状态。

例如：

```text
存在 blocking 待确认
→ 首个适用阶段 blocked，WORK 保持 todo

所有 ready 边界前的必做阶段完成，TASK 已可执行
→ ready

存在 doing 任务
→ doing

所有任务 done
→ implemented

所有必要验证通过
→ verified

记录上线成功
→ released

线上验证通过
→ confirmed
```

阶段状态与 WORK 状态必须同时刷新。WORK 进入 `ready / implemented / verified / released / confirmed`
时，对应任务、开发、验证、上线或全部流程边界之前的 required 阶段必须为 `done`。人工价值判断不能
由脚本代签；人工改变可推导事实时必须同时提供证据和理由。

# 73. 流程选择器输出

至少输出：

```yaml
workflow:
  - stage: definition
    label: 功能定义
    requirement: required
    status: ready
    status_source: derived
    artifacts: [FEATURE-001]
    checks: [definition, scope]

    reason: product 基础流程

required_checks: []
```

选择器先输出没有 ID 的阶段和所需文档类型；文档创建完成后再把永久 ID 绑定到 `artifacts`，并根据
文档、TASK、VERIFY 与 WORK 事实同步阶段 `status`。重建流程必须保留文档永久 ID，只重新计算阶段、
门禁和 artifact 绑定。

# 77. 文档系统最终目标

项目文档不能只是给人看的说明文件。

它们同时需要成为：

```text
开发输入

智能体上下文

任务约束

流程状态

验证依据

项目记忆
```

因此整套系统最终应形成：

```text
人的意图
    ↓
工作项
    ↓
结构化文档
    ↓
流程选择
    ↓
任务上下文
    ↓
智能体开发
    ↓
复核
    ↓
验证结果
    ↓
上线
    ↓
项目记忆
```

文档不应是开发结束后的记录。

文档本身就是开发系统的一部分。

# 78. 最终要求

任何由该体系管理的工作，都应该能够回答以下问题：

```text
这是什么工作？

为什么做？

现在处于什么状态？

接下来应该干什么？

哪些步骤必须做？

哪些步骤不需要？

谁会受到影响？

风险有多大？

会波及哪里？

还有什么没确认？

当前智能体能改什么？

它不能改什么？

依据哪些定义开发？

对应哪些任务？

每个要求在哪里实现？

怎么证明它已经完成？

上线后怎么确认没问题？

以后的人或智能体为什么能理解当初的决定？
```

如果这些问题可以通过文档、脚本和智能体稳定回答，这套协作开发体系才算真正建立起来。
