# 智能体协作开发文档系统规范

版本：0.1

状态：草案

本规范定义一套适合人和智能体共同开发软件的项目文档系统，也作为后续文档管理工具的需求依据。

它关注的不是“怎样多写几份文档”，而是怎样把人的意图、工程设计、智能体执行、验证证据和长期记忆连成一套可管理、可检查的开发系统。

全文按九个主题展开：先说明系统的核心定位，再从工作项出发解释流程如何选择；随后明确不同信息层之间的边界与决策权，给出五类工作的差异化流程；在此基础上定义文档、状态、追踪、角色和工具。

这些章节共同描述同一个闭环，不应被理解成九套彼此独立的规则。

---

# 1. 核心定位：文档本身就是开发系统的一部分

## 1.1 要解决的问题

人和智能体共同开发时，真正困难的通常不是生成代码，而是让每个参与者在正确的时间看到正确的信息，并且只在获得授权的范围内推进工作。如果产品目标、技术方案、开发任务和验证结果混在一个文件里，智能体很容易把假设当成决定、把实现细节当成需求，或者在完成代码后过早宣布整个工作已经完成。

这套系统需要稳定解决十类问题：

1. 不同层级的信息必须分开表达，产品定义不能与技术实现混为一谈。
2. 产品功能、基建、问题修复、重构维护和工程改进需要走适合自己的流程。
3. 智能体需要知道当前应该读取哪些上下文，而不是无差别读取整个项目。
4. 每个开发任务都要明确允许修改和禁止修改的范围。
5. 未知、假设、风险、实现偏差和范围变化必须显式记录。
6. 要求、设计、任务、代码、测试与验证结果之间需要能够追踪。
7. 文档结构、状态、编号、引用和流程应尽量由脚本生成与检查。
8. 流程不能为了形式完整而制造大量没有实际用途的文档。
9. “完成”必须有验证证据支撑，不能只依靠智能体或开发者的口头声明。
10. 重要决定、失败方案和线上经验必须能被未来的人或智能体理解。

因此，项目文档不只是给人阅读的说明文件。它同时承担开发输入、智能体上下文、任务约束、流程
状态、验证依据和项目记忆六种职责。文档不是开发结束后的补记，而是开发系统运行时的一部分。

## 1.2 统一闭环

所有工作从人的意图开始，经由结构化文档和流程选择进入开发，最后以验证与长期记忆收束：

```text
人的意图
    ↓
工作项
    ↓
结构化定义与设计
    ↓
流程选择
    ↓
任务上下文
    ↓
智能体或开发者实施
    ↓
独立复核
    ↓
验证结果
    ↓
上线与线上观察
    ↓
项目记忆
```

这个闭环里，“工作项”是统一入口，“流程”负责控制先后顺序和门禁，“文档”保存定义、方案与证据，“状态”反映已经发生的事实。它们互相联系，但不能互相替代：有一份技术方案不代表方案阶段已经通过检查，代码已经合并也不代表验证已经完成。

## 1.3 流程的目的

流程只用于减少不确定性和工程风险，而不是用于生产文档。

低风险、局部、容易回退的工作应当使用更短的流程；关键风险、系统级影响和不可逆操作则必须留下更充分的定义、决策、复核和回退证据。

系统应始终坚持两个约束：

- 不同工作不能被强制塞进同一条流程；
- 不需要的阶段和文档不能为了“看起来完整”而生成。

复杂度应当来自工作本身，而不是来自管理工具。

## 1.4 基本行为准则

整个系统建立在几条贯穿所有章节的行为准则上。

第一，状态必须明确。禁止使用“差不多完成”“基本好了”“应该没问题”一类无法检查的描述。工作项、任务、文档和流程阶段都使用有限、明确的状态集合。

第二，不允许偷偷脑补。所有重要未知都必须记录为已经确认、可以按明确假设继续，或者必须确认后才能继续。最后一种情况会阻塞受影响的流程阶段。

第三，上游有问题就向上升级。如果开发中发现功能定义不合理、技术方案不可行或任务范围不足，不得直接改写上游定义来适配当前实现，而要暂停相关工作并发起相应变更。

第四，不能只说“好了”。智能体声称完成、修复或实现时，必须同时给出实际验证方式与结果。验证失败或尚未执行时，状态应如实保留。

第五，人的注意力只用于值得人工负责的事情。关键决定、待确认项、高风险、产品行为变化、重大技术变化和不可逆操作需要集中呈现；普通格式、编号、引用和状态一致性应交给脚本，常规内容分析与实现交给智能体。

能够稳定判断的格式、必填字段、编号唯一性、引用关系、任务范围、状态变化、测试结果、代码检查和流程完整性，都应尽量进入自动检查。自动化的价值不是减少思考，而是把人的注意力从重复核对转移到真正需要判断的地方。

# 2. 工作项：统一入口与流程决策

## 2.1 什么是工作项

系统把所有需要跟踪、设计、开发或验证的工程工作统一抽象为工作项（WORK）。新增项目搜索、增加Redis 缓存、修复登录失败、重构订单模块、升级数据库版本、优化接口性能和增加安全审计，都可以作为一个独立工作项。

工作项不是一张只记录标题和负责人的工单。它至少要回答：为什么做、成功标准是什么、属于哪种工作、风险有多大、会波及哪里、有哪些额外关注、当前走什么流程、还有哪些待确认和风险点，以及关联了哪些定义、任务和验证文档。

一个工作项进入系统后，通常经历以下过程：

```text
创建工作项
    ↓
判断工作类型
    ↓
评估风险与影响面
    ↓
识别额外关注与当前卡点
    ↓
生成实际流程和所需文档
    ↓
定义、设计与任务拆分
    ↓
开发、复核与验证
    ↓
上线、观察与项目记忆
```

## 2.2 五种工作类型

工作类型决定主流程。系统支持五种类型，每个 WORK 必须选择其中一种；TASK 只继承所属 WORK 的类型与边界，不能重新决定主流程。

### 2.2.1 产品功能（product）

产品功能是用户能够直接感受到的新能力或行为变化，例如搜索、登录、支付、个人资料、项目管理、页面功能和交互变化。它的主定义文档是 FEATURE，流程通常需要用户体验设计，并且对业务规则、边界情况和失败状态有明确要求。

### 2.2.2 基建（infra）

基建主要服务于系统、开发者、运维人员、智能体或其他模块，例如缓存、消息队列、日志系统、任务调度、权限底座、构建与发布系统、数据库基础设施、内部开发工具和公共服务。它的主定义文档是CAPABILITY，不默认要求用户界面设计，但需要考虑开发体验、运维要求、接入方式和失败恢复。

### 2.2.3 问题修复（fix）

问题修复用于实际行为与预期行为不一致的情况，例如页面报错、接口异常、数据错误、回归问题和边界缺陷。它的主定义文档是 ISSUE。即使使用快速流程，也必须说清楚实际是什么、应该是什么、如何复现，以及如何确认已经修好。

### 2.2.4 重构维护（maintenance）

重构维护原则上保持外部行为不变，主要改善内部工程状态，例如代码重构、模块拆分、依赖升级、技术债处理、删除旧代码和测试整理。它的主定义文档是 CHANGE，最重要的不是新功能，而是明确哪些行为和边界绝对不能改变。

### 2.2.5 工程改进（improvement）

工程改进用于提升系统性指标或控制工程风险，例如性能、稳定性、安全、隐私、成本、质量与合规。它的主定义文档是 IMPROVEMENT，需要同时记录当前数据、目标指标、验证方法和上线后的持续观察项。

## 2.3 额外关注（concerns）

工作类型决定主流程，额外关注决定还要增加哪些专项检查。一个工作项可以同时包含多个 concern：

| 标识 | 含义 | 常见增量 |
|---|---|---|
| `security` | 安全 | 威胁检查、人工确认、上线门禁 |
| `privacy` | 隐私 | 数据范围、授权与保留策略 |
| `data` | 数据 | 数据一致性、迁移与回退检查 |
| `performance` | 性能 | 基线、目标指标、性能验证与观察 |
| `reliability` | 稳定性 | 故障、恢复、回退与持续观察 |
| `observability` | 可观测 | 日志、指标、告警与定位能力 |
| `compatibility` | 兼容性 | 旧接口、旧数据与升级路径 |
| `accessibility` | 无障碍 | 键盘、语义、提示和辅助技术检查 |
| `cost` | 成本 | 资源与费用基线、上线后观察 |
| `release` | 上线风险 | 灰度、停止条件、回退和线上确认 |

例如，一个涉及账户数据的新产品功能可以声明：

```yaml
work_type: product
concerns:
  - security
  - privacy
  - data
```

这不会把它变成另一种工作类型，只会在产品功能基础流程上增加相应门禁。

## 2.4 风险级别

风险分为 `low`、`medium`、`high` 和 `critical` 四级。

低风险工作影响有限，问题容易发现、容易回退且数据风险低。中风险工作可能影响多个模块，需要明确验证并写清回退方式。高风险工作会影响核心业务、重要数据、大量用户或关键基建，必须有正式技术方案和独立复核。

关键风险包括不可逆数据变化、权限模型或登录认证体系变化、严重安全风险、核心数据库变化、生产发布体系变化、可能导致大面积服务不可用以及无法快速回退的操作。关键风险必须留下人工确认，脚本或智能体不能自行代签。

### 2.4.1 风险自动升级

风险不能完全依赖创建者主观填写。满足下列任一情况时，不允许直接标为低风险：

- 修改数据库结构或持久化数据格式；
- 修改公共接口、登录、权限或公共基础模块；
- 引入新的外部依赖；
- 涉及用户隐私、计费或资金；
- 涉及并发、事务或数据一致性；
- 修改发布基础设施；
- 无法快速回退。

以下情况应至少评估为高风险：

- 不可逆或大规模数据迁移；
- 权限模型或登录认证模型整体变化；
- 核心数据库结构、核心业务链路或生产基础设施变化；
- 密钥或凭证机制变化；
- 多个核心服务同时受到影响。

管理工具应根据这些事实提高最低风险，不能因为调用者传入 `low` 就忽略客观风险。

## 2.5 影响面

影响面分为 `local`、`multi-module` 和 `system`。

局部影响通常只修改一个模块，不改变公共接口或共享数据。跨模块影响表示多个模块需要配合，或者公共接口、共享组件、共享数据发生变化。系统级影响通常涉及登录或权限体系、核心数据库模型、全局配置、公共基础库、发布系统、网络层或多个服务间协议。

风险和影响面回答不同问题：风险决定检查需要多严格，影响面决定检查需要覆盖多远。一个修改范围很小但不可逆的数据操作可能风险很高；一个覆盖多个内部模块、可快速回退的整理也可能是系统级影响但不要求业务上线。二者不能互相替代。

## 2.6 当前未知与流程输入

流程是否能够继续，还取决于当前未知。未知统一记录为待确认项，而不是隐藏在聊天记录或智能体
推断中。待确认项可以处于：

- `open`：问题尚未确认；
- `assumed`：已经记录当前假设，可以按该假设继续；
- `resolved`：已经得到确认；
- `blocking`：缺少结论会影响后续工作，受影响阶段必须卡住。

因此，实际流程由以下信息共同决定：

```text
工作类型
+ 风险级别
+ 影响面
+ 额外关注
+ 当前卡点
```

它们分别回答“走哪条主流程”“检查多严格”“覆盖多远”“增加什么专项检查”和“现在能不能继续”。

## 2.7 流程生成顺序

流程必须按稳定顺序生成：

```text
WORK Type 基础流程模板
→ 风险级别增量规则
→ 影响面增量规则
→ concern 专项规则
→ 当前未知与人工确认卡点
→ 当前 WORK 的实际 workflow
```

风险、影响面和 concern 可以把可选阶段升级为必做、插入阶段、要求额外文档、增加阶段检查门禁、增加人工确认，或者要求上线与观察。它们不能抹掉 WORK Type 的基础顺序与语义，更不能把所有工作改造成同一条“完整流程”。

# 3. 信息分层：内容边界、决策权与改动升级

## 3.1 六个问题必须分开

同一个工作项会产生多种信息，但这些信息不能混在同一层里。系统要求分别回答六个问题：

| 信息层 | 回答的问题 | 典型产物 |
|---|---|---|
| 背景与目标 | 为什么做 | PRODUCT、WORK 背景 |
| 定义 | 做什么 | FEATURE、CAPABILITY、ISSUE、CHANGE、IMPROVEMENT |
| 体验 | 怎么使用、接入和运维 | EXPERIENCE |
| 设计 | 怎么实现、为什么这样选 | DESIGN、DECISION |
| 执行 | 怎么开发、范围和依赖是什么 | PLAN、TASK |
| 证据 | 怎么验证、怎样证明完成 | VERIFY、上线记录、MEMORY |

产品定义不能直接夹杂具体数据库字段、框架、代码文件或函数实现；技术方案不能借实现便利重新定义产品行为；开发任务也不能重新决定产品需求或整体架构。章节可以放在同一个工作项目录中，但信息责任必须保持清楚。

## 3.2 信息优先级

发生冲突时，项目按以下优先级处理信息：

```text
人工确认的决定
↓
功能定义 / 能力定义 / 问题说明 / 改动说明 / 改进说明
↓
体验设计 / 技术方案 / 技术决策
↓
开发计划
↓
开发任务
↓
代码与测试
↓
代码注释
↓
智能体自己的推断
```

上层与下层冲突时默认以上层为准。代码不能反向覆盖已经确认的需求，智能体也不能因为现有实现比较方便，就把实现现状解释成新的产品规则。若上游确实有问题，应使用改动升级流程修正，而不是悄悄改变权威顺序。

## 3.3 任务读写边界

每个 TASK 都必须明确三类范围：

```text
可以看什么
可以改什么
不要动什么
```

它们在元数据中对应 `read_paths`、`write_paths` 和 `forbidden_paths`。任务进入 `ready` 之前，
这些范围必须具体到足以约束单个智能体独立执行。发现需要修改禁区或超出允许范围时，不能只扩大路径列表；应先判断它是普通实现调整、技术方案变化还是产品行为变化。

## 3.4 三种改动升级

### 3.4.1 普通实现调整

如果调整不改变功能或能力定义、不改变技术方案的重要决定，也不改变外部行为，可以在现有 TASK
范围内处理。实现细节仍要符合任务的读写边界。

### 3.4.2 技术方案变化

技术实现路线发生明显变化时，必须暂停相关任务、更新 DESIGN，重新检查影响面，并在需要时更新
DECISION 与 PLAN。TASK 不能通过“实现记录”取代方案层的正式变化。

### 3.4.3 产品行为变化

用户可观察行为或业务规则发生变化时，必须暂停实现、更新 FEATURE 或 PRODUCT、获得人工确认，并根据新定义重新生成后续流程。产品变化不能隐藏在代码评审或任务备注里。

## 3.5 实现偏差

如果代码行为与上游定义不一致，应建立实现偏差记录，至少写清：

- 应该是什么；
- 现在是什么；
- 影响哪里；
- 可能原因；
- 建议怎样处理。

不得通过直接修改需求来“消除”偏差。偏差可能最终促成产品变更，也可能要求代码回到原定义，但这
必须经过对应层级的判断。

## 3.6 人工注意力的聚合

系统应把所有需要人负责的内容集中显示，包括关键决定、待确认项、高风险、产品行为变化、重大技术变化和不可逆操作。人工不应为了寻找三处关键问题而逐篇阅读所有文档；普通实现细节、格式和引用关系应由智能体与工具处理。

# 4. 差异化流程：从基础模板到实际 workflow

## 4.1 流程是控制面，文档是产物面

流程描述阶段顺序、必需性、实际进度、卡点和检查门禁；文档记录定义、方案、决定和证据。两者不是一一对应关系，系统必须支持：

- 一个阶段没有独立文档；
- 一个阶段关联一份或多份文档；
- 同一份文档支撑多个阶段；
- 一份文档内部覆盖多个同层细分步骤。

例如，开发、复核、上线和观察可以没有独立 Markdown；多个 TASK 可以共同支撑开发阶段；同一份
TASK 可以同时支撑“开发任务”和“开发”阶段；重构维护的当前问题、目标状态、不变条件和影响检查
可以合并在一份 CHANGE 中。

每个实际阶段至少包含以下字段：

```yaml
stage: definition
label: 功能定义
requirement: required
status: ready
status_source: derived
artifacts: [FEATURE-001]
checks: [definition, scope]
source: profile:product
reason: product 基础流程
```

`artifacts` 只能引用当前 WORK 的受管理文档，也允许为空。`source` 与 `reason` 用来解释阶段来自基础模板还是某条增量规则，避免工具生成无法追溯的流程。

## 4.2 阶段必需性与阶段进度

阶段必需性只使用：

- `required`：必做，未完成不能跨过对应的 WORK 状态边界；
- `optional`：可选，可以在说明原因后跳过。

不适用于当前 WORK Type 的阶段不会进入实际 workflow，而不是统一生成 `not-needed` 占位节点。

阶段实际进度只使用：

- `pending`：前置条件尚未满足；
- `ready`：当前可以推进；
- `doing`：正在进行；
- `done`：已经完成；
- `skipped`：可选阶段被明确跳过；
- `blocked`：阶段适用，但缺少决定、信息、权限或依赖。

`skipped` 只适用于 optional 阶段，并且必须记录原因。`status_source` 使用 `derived` 或 `manual`，
区分由事实推导的状态和显式操作。

阶段状态应优先根据 artifacts、TASK、VERIFY 和 WORK 的事实推导：定义文档确认后定义阶段完成；TASK 进入 ready 后任务拆分完成；所有 TASK done 后开发完成；approved 且 `result=pass` 的 VERIFY使复核与验证阶段完成；WORK 的 released 和 confirmed 分别推进上线与观察。不能可靠推导的价值判断仍由负责人确认。

## 4.8 快速流程

只有同时满足低风险、局部影响、无安全问题、无数据迁移、无公共接口变化、容易回退和完成标准明确时，才可以进入快速流程：

```text
对应类型的简短定义
↓
开发任务
↓
开发
↓
自动验证
↓
完成
```

快速流程仍然保留 WORK Type 的定义语义。产品和基建仍保留 EXPERIENCE；可以跳过的是标记为`fast_skippable` 的独立 DESIGN、PLAN 等产物。低风险局部维护可以使用 CHANGE + TASK + VERIFY，低风险局部修复可以使用 ISSUE + TASK + VERIFY。被跳过的可选阶段必须记录`source=overlay:fast` 和具体原因。

## 4.9 强制完整流程

关键风险、系统级影响、不可逆操作、重大数据迁移、权限或登录体系变化、核心架构或基建变化、无法可靠回退以及重大业务规则变化，都不允许使用快速流程。

完整流程不是另一种 WORK Type，而是在原类型流程上增加严格性。高风险或系统级工作至少增加：

```text
影响面检查
↓
技术方案
↓
技术决策
↓
开发计划
↓
独立复核
↓
完整验证
↓
回退检查
↓
项目记忆
```

`critical` 或安全敏感工作还要增加人工确认。数据、公共接口、安全、用户可见或 release concern 会使上线与观察成为必做；性能、可靠性、可观测和成本 concern 会使观察成为必做。系统级影响会增加跨模块回归，但纯内部维护不会仅因为 `impact=system` 就被错误认定为必须进行业务上线。

# 5. 文档体系：从定义到证据的结构化产物

## 5.1 文档类型总览

系统支持以下核心文档：

```text
WORK         工作项
PRODUCT      产品说明
FEATURE      功能定义
CAPABILITY   能力定义
ISSUE        问题说明
CHANGE       改动说明
IMPROVEMENT  改进说明
EXPERIENCE   体验设计
DESIGN       技术方案
DECISION     技术决策
PLAN         开发计划
TASK         开发任务
VERIFY       验证结果
MEMORY       项目记忆
```

并非每个工作项都要生成所有类型。文档类型也不是流程阶段类型：阶段通过 `artifacts` 引用零份、一份或多份文档，目录中的层级前缀只负责排列实际产物，不能表示阶段是否必做或已经完成。

## 5.2 WORK：整个体系的入口

WORK 的文件标识是 `WORK`。它的基础元数据包括：

```yaml
id:
title:
type: work
work_type:
status:
risk:
impact:
concerns:
owners:
created_at:
updated_at:
```

正文记录为什么做、成功标准、当前流程、待确认项、风险点和关联文档。具体定义、任务和验证拥有自己的文档与状态，WORK 不复制它们的完整正文，而通过关系和 workflow 聚合当前事实。

## 5.3 定义层文档

### 5.3.1 PRODUCT：产品说明

PRODUCT 说明产品层面的背景，包括问题是什么、谁遇到问题、为什么值得做、目标和成功标准、这次不做什么、有哪些限制以及还有什么没确认。它不得包含具体技术实现。

### 5.3.2 FEATURE：功能定义

FEATURE 说明用户可见功能，包括功能名称、为什么做、谁会用、从哪里进入、正常流程、业务规则、边界情况、失败情况、完成标准、性能或安全要求、本次不做什么和待确认项。

具体数据库字段、框架、代码文件和函数实现不属于 FEATURE。把这些内容写进功能定义，会让产品行为与某个实现方案错误绑定。

### 5.3.3 CAPABILITY：能力定义

CAPABILITY 用于基建，说明能力名称、为什么需要、谁会使用、提供什么、怎样接入、输入输出、限制、失败行为、性能与稳定性要求、兼容要求、升级与迁移要求，以及本次不做什么。

### 5.3.4 ISSUE：问题说明

ISSUE 用于修复，至少包含问题现象、复现方式、实际结果、预期结果、影响、发生条件、已知原因、修复方向和回归检查。根因尚未确认时应明确标为未知，不能把猜测写成事实。

### 5.3.5 CHANGE：改动说明

CHANGE 用于重构维护，说明当前状态、哪里不好、希望变成什么样、哪些行为必须保持不变、影响哪里、风险是什么，以及如何确认改动没有破坏旧行为。

### 5.3.6 IMPROVEMENT：改进说明

IMPROVEMENT 用于性能、稳定性、安全等工程改进，记录当前问题和数据、希望改善的指标、目标值、影响范围、主要风险、验证方式与持续观察项。

## 5.4 体验与设计层文档

### 5.4.1 EXPERIENCE：体验设计

EXPERIENCE 可以描述用户体验、开发体验、运维体验或明确的混合类型。

用户体验根据实际功能考虑入口、主流程和其他流程、页面结构、交互行为、加载、空、错误、无权限和提交状态、移动端表现、键盘操作、无障碍与提示文案。

开发体验适用于 SDK、内部接口、CLI 和平台能力，重点说明如何接入、接口是否易懂、怎样配置、错误是否清楚、如何调试、本地怎样运行、是否有示例以及失败后如何恢复。

运维体验适用于长期运行的系统能力，重点说明部署、健康判断、指标、日志、异常发现、定位、恢复、回退、扩容、升级和负责人。

### 5.4.2 DESIGN：技术方案

DESIGN 说明背景、目标、限制条件、整体方案、模块拆分、数据和接口、状态管理、安全、失败处理、监控、部署、迁移、旧系统兼容、备选方案、最终选择、取舍、代价、风险和重新考虑条件。

重要方案必须记录备选项。只写最终方案而不写为什么未选其他方案，会丢失未来判断是否应重做决定所需要的上下文。

### 5.4.3 DECISION：技术决策

DECISION 用于长期保留重要技术选择，回答要决定什么、背景是什么、有哪些方案、最后选择什么、为什么这样选、为什么没选其他方案、影响和风险是什么、什么条件下应重新考虑。

不是每一个实现选择都值得单独建立 DECISION；它适用于会长期约束多个任务或未来工作项的决定。

## 5.5 执行与证据层文档

### 5.5.1 PLAN：开发计划

PLAN 说明要做什么、修改哪些区域、开发阶段和先后顺序、哪些可以并行、依赖什么、是否涉及迁移、怎样上线、有哪些风险、如何验证以及出问题怎样回退。

### 5.5.2 TASK：开发任务

TASK 是单个智能体可以独立完成并验证的最小工作单位。它包含任务目标、依据文档、可读范围、可改范围、禁止范围、依赖、产出、完成标准、验证方式和当前风险。TASK 不重新定义上游需求或架构。

### 5.5.3 VERIFY：验证结果

VERIFY 保存可检查的证据，包括验证对象、对应要求、执行了哪些检查、环境与命令、每项结果、未通过项、修改范围检查、遗留问题、剩余风险与最终结论。只有实际通过的验证才能使用 `result=pass`。

### 5.5.4 MEMORY：项目记忆

MEMORY 保存未来仍有参考价值的信息：为什么当时这样做、尝试过和失败过哪些方案、踩过什么坑、已知问题和技术债、线上发生过什么、何时应该重新考虑。它不是开发流水账，也不复制每次状态变化。

## 5.6 统一元数据

所有受管理文档顶部必须使用统一 YAML front matter。一个 FEATURE 示例：

```yaml
---
id: FEATURE-001
type: feature
title: 项目搜索
status: draft
work: WORK-001
owners:
  - product
depends_on: []
related: []
created_at: 2026-08-24
updated_at: 2026-08-24
---
```

核心字段是 `id`、`type`、`title`、`status`、`work`、`owners`、`depends_on`、`related`、
`created_at` 和 `updated_at`。根据文档类型还可以使用 `risk`、`impact`、`concerns`、
`implements`、`verifies`、`supersedes`、`deprecated` 与 `tags`。

WORK 使用 `type: work` 和独立的 `work_type` 区分“文档类型”与“工作类型”，避免同一个 `type`
字段承担两套语义。

## 5.7 永久编号

每个受管理对象必须拥有稳定且唯一的编号，例如：

```text
WORK-001
PRODUCT-001
FEATURE-001
CAPABILITY-001
ISSUE-001
CHANGE-001
IMPROVEMENT-001
EXPERIENCE-001
DESIGN-001
DECISION-001
PLAN-001
TASK-001
VERIFY-001
MEMORY-001
```

编号一旦创建就不允许复用，文档删除、废弃、替代或归档后也不回收。永久 ID 用来维持历史链接；
文件名中的层级前缀只负责排序，不能替代 ID。

## 5.8 文档关系

系统支持以下关系：

- `belongs_to`：属于某个工作项；
- `depends_on`：依赖另一个对象；
- `related_to`：有关联但不是强依赖；
- `implements`：实现某个要求或设计；
- `verifies`：验证某个要求或任务；
- `supersedes`：替代旧文档；
- `blocks`：阻止另一个对象继续；
- `artifacts`：流程阶段使用当前 WORK 中的哪些文档作为产物或证据。

`artifacts` 允许零到多份，同一文档也可以支撑多个阶段。它属于 workflow 阶段，而不是文档 front
matter 中普通的全局关系。

## 5.9 工作项目录

开发过程文档统一保存在 `development/`。每个工作项对应一个独立目录，WORK 入口和全部附属文档必须聚合在该目录内，不能再按 FEATURE、DESIGN、TASK 等类型拆到不同全局目录。

```text
development/
├── README.md
├── SPECIFICATION.md
├── index.json
├── schema/
├── templates/
└── works/
    └── WORK-001-example/
        ├── 00-work.md
        ├── 10-feature-FEATURE-001.md
        ├── 20-experience-EXPERIENCE-001.md
        ├── 30-design-DESIGN-001.md
        ├── 40-decision-DECISION-001.md
        ├── 50-plan-PLAN-001.md
        ├── 60-task-TASK-001.md
        ├── 70-verify-VERIFY-001.md
        └── 80-memory-MEMORY-001.md
```

工作项目录名固定为 `WORK-<永久编号>-<语义化短名>`。目录内文件按信息层级使用前缀：

```text
00  WORK 工作入口
10  PRODUCT / FEATURE / CAPABILITY / ISSUE / CHANGE / IMPROVEMENT 定义
20  EXPERIENCE 体验
30  DESIGN 技术方案
40  DECISION 技术决策
50  PLAN 开发计划
60  TASK 开发任务
70  VERIFY 验证证据
80  MEMORY 长期记忆
```

WORK 入口固定为 `00-work.md`。其他文档固定为`<层级>-<小写类型>-<永久 ID>.md`，例如 `30-design-DESIGN-002.md`。同层文件按类型名和永久 ID 保持稳定顺序，不用文件顺序额外表达上下级关系。无文档的开发、复核、上线和观察阶段不会为了填满编号而创建空 Markdown。

归档、废弃或被替代的文档仍保留在原工作项目录中，只改变元数据状态，从而保留完整上下文和历史顺序。项目根目录保留 `AGENTS.md`，用于告诉智能体项目总规则、文档入口、开发规则、禁止事项与脚本命令入口。

## 5.10 文档合并与拆分

小型工作不要求生成全部文档类型，但必须保留能独立表达定义、执行范围和验证证据的最小 artifacts：

```text
WORK
+ 对应类型定义（FEATURE / CAPABILITY / ISSUE / CHANGE / IMPROVEMENT）
+ TASK
+ VERIFY
```

一份文档可以覆盖同一信息层的多个细分步骤。例如 CHANGE 可以同时包含当前问题、目标状态、不变条件、影响检查和回归要求，但章节必须清楚分开。

不能把拥有不同状态机和责任边界的定义、TASK 与 VERIFY 全部塞进 `00-work.md`，否则无法独立追踪定义确认、任务权限和验证证据。内容较长、被多人或多个智能体使用、会被多个工作复用、需要独立版本或审批、属于长期技术决定或需要长期维护时，应在同一个工作项目录内拆成独立文档。拆分不改变归属，也不能重新建立按类型划分的全局目录。

# 6. 状态与关卡：用事实定义“做到哪里”

## 6.1 三类状态机

WORK、TASK 和其他文档有不同责任，因此使用不同状态机。

工作项状态是：

```text
todo → ready → doing → implemented → verified → released → confirmed
```

`cancelled` 表示工作终止。各状态分别代表待开始、可以开发、开发中、代码完成、验证通过、已上线和线上确认。`implemented` 只表示实现已经完成，不代表验证、发布或线上结果。

TASK 状态是：

```text
todo → ready → doing → done → verified
             ↘ blocked
```

`cancelled` 同样表示终止。TASK 只有在依赖、范围与完成标准明确后才能进入 ready；done 表示实现完成，verified 表示已有验证证据覆盖任务。

除 WORK 与 TASK 外，受管理文档使用：

```text
draft → review → approved
                 ├─ deprecated
                 ├─ superseded
                 └─ archived
```

只有 approved 的上游文档可以作为稳定开发依据。低风险快速流程可以省略独立 review 状态，把已
补全定义从 draft 直接确认到 approved，但不能把带占位内容的草稿直接当作 TASK ready 的依据。

## 6.2 状态推导

工作项状态不应完全依赖人工填写。脚本可以根据已经存在的事实推导：

```text
存在 blocking 待确认
→ 首个受影响阶段 blocked，WORK 保持 todo

ready 边界前的 required 阶段完成，TASK 已可执行
→ ready

存在 doing TASK
→ doing

所有 TASK done
→ implemented

所有必要 VERIFY approved 且 result=pass
→ verified

记录上线成功
→ released

线上验证通过
→ confirmed
```

阶段状态与 WORK 状态必须一起刷新。WORK 进入 ready、implemented、verified、released 或 confirmed时，对应边界之前的 required 阶段必须为 done。人工可以在有理由和证据时覆盖状态，但工具不能代替人工完成产品判断、高风险确认或线上责任。

## 6.3 定义关卡

产品功能进入稳定开发依据前，至少应确认为什么做、谁会用、正常流程、边界与失败情况、完成标准、性能和安全等关注项、本次不做什么，以及不存在关键卡点。

基建能力至少应确认使用者、提供的能力、输入输出、失败行为、性能与稳定性、兼容、升级或迁移要求，并且没有关键卡点。

这些要求不是为了让定义文档变长，而是为了防止把重要业务与能力假设推迟到代码阶段才发现。

## 6.4 体验与设计关卡

EXPERIENCE 应按适用情况确认主流程、异常流程、加载、空、错误等状态、移动端、无障碍和关键文案；开发或运维体验则检查接入、错误、调试、部署、监控和恢复。

DESIGN 至少应明确整体方案、模块职责、数据影响、接口、失败处理、安全、监控和迁移，重要方案要有比较，关键风险要有记录，并且不能带着 blocking 未知进入实施。

## 6.5 计划与开发关卡

PLAN 需要让范围可拆、依赖和顺序明确，并记录风险、验证与回退方式。TASK 则把计划落成单个智能体可以独立执行的范围。

开发完成检查至少包括：代码或文档产物完成、必要测试完成、没有超范围修改、没有偷偷改变上游定义，新增未知和风险已经记录。只有满足这些事实，TASK 才能从 doing 进入 done。

## 6.6 验证关卡

验证阶段要求重要要求都有对应证据，必要测试已经通过，没有严重回归，修改范围正确，没有未处理的实现偏差，并且 VERIFY 已记录实际结果。验证不是把测试命令列在 TASK 里，而是实际执行并保存结果。

## 6.7 完成定义

代码完成不能视为整个工作完成。最低闭环是：

```text
定义明确
↓
代码完成
↓
验证通过
```

需要上线的工作还要继续：

```text
定义明确
↓
代码完成
↓
验证通过
↓
已上线
↓
线上确认
```

这一区分保证“已经实现”“已经证明”和“已经在真实环境稳定运行”不会被压成同一个模糊的完成状态。

# 7. 追踪、复核与验证：让每项要求都有证据

## 7.1 端到端追踪链

系统至少要支持两条核心链路。

第一条是从工作到验证的文档链：

```text
WORK
↓
FEATURE / CAPABILITY / ISSUE / CHANGE / IMPROVEMENT
↓
EXPERIENCE
↓
DESIGN
↓
PLAN
↓
TASK
↓
VERIFY
```

第二条是从局部要求到证据的实现链：

```text
功能或能力要求
↓
开发任务
↓
代码与测试
↓
验证结果
```

workflow 还要能够追到实际 artifacts：

```text
WORK
↓
workflow stage
↓ artifacts
当前工作项中的定义 / 体验 / 设计 / 计划 / 任务 / 验证 / 记忆
```

工具需要发现断链，而不是等到上线前由人手工拼接。

## 7.2 局部要求与验收编号

FEATURE、CAPABILITY、CHANGE 等定义文档中的重要要求应使用局部编号，例如 `REQ-001`、`REQ-002`；验收项使用 `AC-001`、`AC-002`。TASK 可以声明：

```yaml
implements:
  - FEATURE-001#REQ-002
```

VERIFY 可以声明：

```yaml
verifies:
  - FEATURE-001#AC-001
  - FEATURE-001#AC-002
```

局部编号使工具能够回答“这个要求由哪个任务实现、是否有测试、是否已经验证”，也使需求文字调整时不必依赖脆弱的段落位置。

## 7.3 待确认项

待确认项至少记录编号、问题、当前假设、影响、状态和负责人。`assumed` 不是“可以忽略”，而是已经明确记录继续工作的假设；如果假设被推翻，系统应能找到受影响的设计和任务。存在 `blocking` 待确认项时，受影响后续阶段不得继续。

## 7.4 风险点

风险记录至少包含编号、风险描述、发生可能性、影响程度、触发条件、发现方式、避免方法、发生后的处理、是否可回退和负责人。风险状态使用：

```text
open
mitigated
accepted
closed
```

`accepted` 表示有责任主体明确接受剩余风险，不等于风险已经消失。

## 7.5 影响面检查

中风险及以上，或者跨模块及以上工作，需要逐项检查：

- 用户行为与界面；
- 接口、数据库和数据；
- 权限与安全；
- 性能与稳定性；
- 日志、监控和测试；
- 部署、迁移与兼容；
- 其他模块。

每项标记为 `affected`、`not-affected` 或 `unknown`。存在重要 unknown 时不能直接继续；它应转成待确认项，必要时阻塞设计或开发阶段。

## 7.6 独立复核

复核和开发应尽量分离。复核重点包括实现错误、遗漏要求、超范围修改、隐性假设、实现偏差、明显安全问题、缺失测试和不必要复杂度。

复核智能体默认只报告问题，不直接修改代码。这样可以保持开发与判断职责分离，也避免评审者在修复一个问题时引入另一组未经复核的变更。若用户明确要求修复，可以在问题确认后进入新的执行阶段。

## 7.7 验证矩阵

验证类型根据 WORK Type、风险、影响面和 concerns 选择，可能包括：

- 功能验证；
- 单元、集成和端到端测试；
- 回归测试；
- 安全和性能检查；
- 兼容性与迁移测试；
- 回退和故障测试；
- 线上验证。

验证强度应与风险匹配，但无论流程长短，都必须覆盖定义中的重要验收项。自动测试不是唯一证据；人工场景、运行环境、迁移演练和线上指标也可以进入 VERIFY，但必须记录实际执行过程和结果。

## 7.8 上线

需要上线的工作应根据风险考虑迁移、兼容、功能开关、灰度、停止条件、回退、上线后检查与监控指标。
高风险工作必须明确怎样上线、观察什么、什么情况停止、什么情况回退以及具体如何回退。

上线是独立阶段，不应因为代码合并或构建产物生成就自动完成。没有独立 artifact 的上线阶段可以由
负责人显式推进，但 required 上线阶段不能跳过。

## 7.9 线上观察

上线后根据工作内容观察错误率、请求量、延迟、资源使用、关键业务指标、日志异常、告警、用户反馈
和成本。只有线上确认完成后，WORK 才能进入 `confirmed`。

不需要业务上线的纯仓库维护可以把可选上线阶段标记为 skipped 并记录原因；若可靠性、性能、成本或
可观测 concern 使观察成为 required，仍需用与该工作相适应的实际证据完成观察。

## 7.10 项目记忆

验证和观察完成后，只有未来仍有价值的内容才进入 MEMORY。好的项目记忆能解释当时为什么这样选、
哪些方案失败、踩过什么坑、留下哪些技术债以及何时应重新考虑。普通执行日志和可以从 Git diff
恢复的事实不需要重复写入。

# 8. 人、智能体与脚本：责任和写权限

## 8.1 三方责任边界

确定性规则、内容理解和价值判断应由不同主体承担。

脚本负责结构、状态、编号、模板、关系、流程、基础校验、查询和上下文组装。凡是可以由明确规则
判断的事情，都应尽量自动化，避免人工重复维护。

智能体负责内容理解与生成、语义检查、风险和影响面建议、文档审查、代码实现与验证分析。智能体
可以提出判断，但不能把建议伪装成已经获得责任主体确认的决定。

人负责最终产品判断、关键取舍、高风险决定和无法自动判断的问题。需要人负责的事项应被集中聚合，
而不是散落在多份文档中。

这套边界可以概括为：

```text
规则能判断 → 脚本
需要理解   → 智能体
需要负责   → 人
```

## 8.2 逻辑角色

系统建议支持以下逻辑角色：

```text
需求智能体
体验智能体
架构智能体
计划智能体
开发智能体
复核智能体
验证智能体
上线智能体
维护智能体
```

角色表示职责，不要求使用不同模型或不同进程。同一个智能体可以在不同时间切换角色，但每次行动都要遵守当前角色的写权限和工作项边界。

## 8.3 默认写权限

默认写权限按信息层分配：

| 角色 | 默认负责的产物 |
|---|---|
| 需求智能体 | PRODUCT、FEATURE、CAPABILITY，以及问题或改动定义 |
| 体验智能体 | EXPERIENCE |
| 架构智能体 | DESIGN、DECISION |
| 计划智能体 | PLAN、TASK |
| 开发智能体 | 代码、测试和任务执行记录 |
| 复核智能体 | 复核结果 |
| 验证智能体 | VERIFY |
| 上线智能体 | 上线记录与阶段证据 |
| 维护智能体 | MEMORY 与维护类工作 |

下游角色不能默认修改上游文档。开发智能体发现 FEATURE 有问题时，应提出产品变更；复核智能体发现缺陷时默认报告；验证智能体不能通过修改验收标准让失败结果变成通过。

## 8.4 智能体任务上下文包

系统需要根据 TASK 自动组装“恰好够用”的上下文，而不是把整个项目全部塞给智能体。上下文包通常
包含：

- 项目规则入口；
- 当前 WORK；
- 相关功能或能力定义；
- 相关 EXPERIENCE；
- 相关 DESIGN 与 DECISION；
- 相关 PLAN；
- 当前 TASK；
- 相关代码路径和测试路径；
- 相关 MEMORY。

上下文包还必须显式包含 TASK 的可读、可写和禁止路径。这样既减少无关信息，也能让智能体在越界前发现需要升级。

## 8.5 人工确认

系统应统一展示“需要你确认”，其中聚合决定、待确认项、高风险、产品行为变化、重大技术变化与不
可逆操作。关键风险、人工产品判断、发布责任和线上确认不能由脚本根据测试全绿自动签署。

# 9. 文档管理工具：生成、校验、查询与状态刷新

## 9.1 工具边界与模块

文档管理工具负责把前八章的确定性规则变成可执行操作。建议模块包括工作项管理、流程选择、模板生成、编号管理、元数据解析、引用管理、文档检查、追踪关系、状态计算、待确认管理、风险管理、任务管理、验证管理、上下文生成、项目查询和项目记忆。

工具不负责替代产品判断，也不负责凭空生成正确内容。它可以发现定义缺少关键章节，但“这个业务规则是否正确”仍需要智能体分析和人的责任判断。

## 9.2 流程选择器

流程选择器至少接受：

```yaml
work_type:
risk:
impact:
concerns:
blocking_items:
```

还可以接受用于自动升级和专项判断的事实：

```yaml
reversible:
data_change:
public_api_change:
security_sensitive:
user_visible:
```

选择器至少输出：

```yaml
workflow:
  - stage: definition
    label: 功能定义
    requirement: required
    status: ready
    status_source: derived
    artifacts: [FEATURE-001]
    checks: [definition, scope]
    source: profile:product
    reason: product 基础流程

required_documents: []
required_checks: []
human_confirmations: []
blocking_items: []
```

初次选择时可以先输出没有永久 ID 的阶段与所需文档类型；创建文档后再把 ID 绑定到 `artifacts`，并根据文档、TASK、VERIFY 和 WORK 事实同步阶段状态。重建流程必须保留文档永久 ID，只重新计算阶段、门禁与 artifact 绑定。

## 9.3 创建与文档生成

创建工作项的典型命令是：

```bash
scripts/work new \
  --title "增加题目搜索" \
  --type product \
  --risk medium \
  --impact multi-module \
  --concern performance \
  --owner team/web
```

创建过程应：

1. 建立独立工作项目录和 `00-work.md`；
2. 分配永久且永不回退的 ID；
3. 识别 WORK Type；
4. 执行风险自动升级；
5. 先应用类型基础模板，再叠加风险、影响面与 concern 规则；
6. 生成所需文档和标准章节，避免生成不适用文档；
7. 自动建立依赖与引用；
8. 自动填写创建时间、更新时间和初始流程状态；
9. 按信息层级生成固定文件名前缀；
10. 为阶段生成 requirement、status、status_source、artifacts、checks、source 与 reason；
11. 允许无文档阶段、多文档阶段和一份文档支撑多个阶段。

向已有工作增加独立文档可使用：

```bash
scripts/work new-doc \
  --work WORK-003 \
  --type task \
  --title "实现搜索接口" \
  --implements FEATURE-002#REQ-001 \
  --depends-on DESIGN-002 \
  --read-path apps/server/problem-service \
  --write-path apps/server/problem-service \
  --forbidden-path contracts
```

## 9.4 结构校验

`scripts/work check` 是文档系统的自动边界，至少检查：

- 元数据格式、必填字段、文档类型与状态是否合法；
- 永久编号是否唯一，文件名中的类型和 ID 是否与元数据一致；
- 工作项目录名是否与 WORK ID 一致；
- 附属文档是否和所属 WORK 位于同一目录；
- 文件层级前缀是否与文档类型一致；
- 引用对象是否存在，依赖是否形成循环；
- workflow 是否匹配 WORK Type 基础模板；
- 风险、影响面和 concern 增量是否进入 workflow；
- 阶段顺序、必需性、检查项、规则来源与 artifacts 是否有效；
- artifacts 是否存在并且属于当前 WORK；
- 必需文档是否至少关联一个阶段；
- 阶段进度是否与文档、TASK、VERIFY 和 WORK 状态一致；
- 卡点是否解决，要求是否有任务，重要验收是否有验证；
- 已验证任务是否有 VERIFY，已上线工作是否已通过验证；
- 文档状态与 WORK 状态是否冲突；
- `development/` 顶层是否重新出现按文档类型划分的目录；
- 工作项目录是否保持扁平并只包含受管理 Markdown。

进行中的工作缺少后续文档可以先提示；一旦 WORK 进入 ready 或更后状态，同样的断链应成为错误。

## 9.5 内容级校验

纯规则无法判断所有语义问题，因此智能体还应检查：

- FEATURE 是否混入大量技术实现；
- DESIGN 是否擅自改变产品行为；
- TASK 是否超出 DESIGN 与 PLAN；
- 代码是否与上游定义冲突；
- VERIFY 是否真正覆盖验收要求；
- 是否存在没有声明的关键假设。

内容级检查通常给出审查结果，不要求全部转成脚本规则。能稳定转化为确定性规则的部分，再逐步下沉到工具。

## 9.6 管理动作

工具需要支持创建、查看、更新、查询、列出、关联、检查、归档、废弃、替代、追踪、生成流程、刷新状态、按当前分类与风险重建流程，以及推进没有独立 artifact 的操作阶段。

常用命令包括：

```bash
scripts/work flow WORK-003
scripts/work list --work WORK-003
scripts/work show FEATURE-002
scripts/work overview
scripts/work list --needs-human
scripts/work trace FEATURE-002
scripts/work context TASK-004
scripts/work rebuild-flow WORK-003
scripts/work refresh WORK-003
```

状态变化必须带理由：

```bash
scripts/work set-status DESIGN-002 approved --reason "架构复核通过"
scripts/work set-status VERIFY-002 approved --result pass --reason "验收场景和回归检查通过"
scripts/work set-stage WORK-003 release skipped --reason "纯仓库维护无需业务上线"
scripts/work refresh WORK-003
```

有 artifacts 的阶段只能由文档、TASK 或 VERIFY 的事实推进；`clarify` 由 `blocking_items` 推进。复核、上线和观察等没有独立 artifact 的阶段可以显式推进，但 required 阶段不能标为 skipped，每次变化都必须记录理由并检查前置 required 阶段。

归档、废弃与替代只改变状态，不把文件移出所属工作项目录：

```bash
scripts/work link TASK-004 --relation implements --to FEATURE-002
scripts/work archive DESIGN-001 --reason "工作已结束，设计仅保留历史参考"
scripts/work deprecate DESIGN-001 --reason "基础假设不再成立"
scripts/work supersede DESIGN-001 --by DESIGN-003 --reason "新方案覆盖旧方案"
```

## 9.7 查询与总览

系统至少应能回答：

- 这个工作是什么，为什么做，现在做到哪里；
- 下一步是什么，为什么还不能开发；
- 有哪些卡点、风险和待确认；
- 一个功能对应哪些任务；
- 一个 TASK 实现了哪个要求；
- 一个要求是否有测试和验证；
- 哪些文档已经过期；
- 哪些技术决定影响某个模块；
- 某个模块正在被哪些工作修改。

项目级总览应展示工作项状态分布、卡住数量、高风险数量和待人工确认数量。例如：

```text
当前工作：12

待开始      2
可以开发    3
开发中      4
代码完成    1
验证通过    1
已上线      1

卡住        2
高风险      1
需要你确认  3
```

单个 WORK 总览需要快速展示工作内容、原因、状态、实际流程、完成阶段、下一步、卡点、风险、文档、任务和验证程度。

## 9.8 创建结果示例

新建工作项后，工具应给出可以直接行动的结果，而不是只返回文件路径：


## 9.9 最终验收问题

任何由本体系管理的工作，都应该能够通过文档、工具和智能体稳定回答：

1. 这是什么工作？
2. 为什么做？
3. 现在处于什么状态？
4. 接下来应该做什么？
5. 哪些步骤必须做？
6. 哪些步骤不需要，哪些可选步骤已经明确跳过？
7. 谁会受到影响？
8. 风险有多大？
9. 会波及哪里？
10. 还有什么没有确认，是否存在 blocking 卡点？
11. 当前智能体可以读什么、改什么？
12. 当前智能体不能动什么？
13. 开发依据哪些定义、体验、方案和决定？
14. 对应哪些任务？
15. 每个要求在哪里实现？
16. 怎样证明它已经完成，验证覆盖了哪些验收项？
17. 上线后怎样确认没有问题？
18. 未来的人或智能体为什么能够理解当初的决定？

如果这些问题可以稳定回答，而且系统没有因为流程本身制造大量无意义文档，这套协作开发文档体系才算真正建立起来。
