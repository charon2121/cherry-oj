# 开发工作记录

只有明确调用 `$dev-work`（或明确要求启用这套流程）时，才启动开发文档系统。普通开发、修复和重构直接遵守项目工程规则，不要求建立工作目录、维护状态或签闸。

启用以后，每个工作只要求一份简短说明。先说明为什么做、准备怎样解决、范围和代价、怎样算完成；实施后在同一份说明补上结果和验证。人默认只读这一份，详细资料需要时再看。

## 使用

例如：`$dev-work 开发题目收藏功能`、`$dev-work 修复登录后立即掉线`。

仓库 skill 在 [dev-work/SKILL.md](../.agents/skills/dev-work/SKILL.md)。它会先准备说明，供你确认目标和重要取舍；获准后实施，再交付实际结果供你接受。确认通过聊天完成，用户明确免除某次确认时按该次授权执行。

五类工作保留不同的思考和验证重点，见[任务流程与材料](./specification/04-workflows.md)。类型影响要回答的问题，不自动生成一整套文件。

## 文件放在哪里

新工作使用 `works/YYYY-MM-DD-简短英文名/00-work.md`。默认没有编号、元数据、阶段表或额外证据文件；少量结果直接写在主文档。复杂方案、独立分工、较长证据才拆附件，见[文档写法](./specification/05-documents.md)。可直接手写，也可用可选工具：

```bash
scripts/work new fix login-timeout --title '修复登录后立即掉线'
scripts/work list
scripts/work show WORK-061
scripts/work check
```

工具只帮助创建、查找和检查记录，不判断授权、签署或工作进度。CI 和 hooks 保留文档链接与历史迁移完整性检查，不要求每次代码修改附带工作文档。

## 已有 WORK 怎么处理

[历史工作目录](./WORKS.md)保留原编号和文件路径。WORK-001 至 WORK-062 的 `00-work.md` 已换成简短入口；原主文档另存为同目录的 `90-history-WORK-xxx.md`，原定义、方案、任务、证据和 `flow.json` 都原样保留。

这些旧状态、签闸、路径列表和命令是当时的记录，不再驱动当前流程。继续旧工作时先看短说明和必要依据，再按当前授权更新主文档；需要启用文档流程时明确调用 skill。原始资料只读，新增结果另写，不能回填历史验收。

[迁移说明](./history/README.md)与[校验清单](./migration.json)记录保留范围。旧工具、测试、规则、模板、Schema 和编号表保存在迁移快照中，已退出日常使用。

长期有效的产品、架构和编码事实仍在 [`docs/`](../docs/README.md)。工作里形成了已确认、能约束后续多项工作的结论，才更新全局文档，并保留来源。
