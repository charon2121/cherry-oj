# 7. 追踪、复核与验证

## 7.1 端到端追踪链

默认链路为 WORK 中的 AC → 实现与测试 → VERIFY。拆出任务时增加 TASK implements 引用。
没有 TASK 时由主工作承接实施，不为满足追踪链创建空任务。

## 7.2 局部要求与验收编号

主文档用 `- AC-001：...` 声明验收项，必要时用 REQ 编号；VERIFY.verifies 引用 `WORK-xxx#AC-001`。
只引用 WORK ID 表示文档级关联，不代表逐条验证。精简验收缺少 AC 锚定证据时拒绝签署。
历史工作缺少锚定仍只提示，不强制补写历史。

## 7.3 待确认项

「未知」直接说明问题、当前假设、影响与继续条件，阻塞项同步到 blocking_items。
普通工作不额外维护完整的问题状态表；重要未知不能隐藏在实现记录中。

## 7.4 风险点

主文档「取舍」写人需要承担的代价、不可逆影响与停止条件，工程分析放到执行方案或附件。
不把所有理论风险展开为清单。接受剩余风险不等于风险消失，交付仍须呈现。

## 7.5 影响面检查

按实际影响检查用户行为、接口与数据、权限、安全、稳定性、部署与其他模块。
结果只记录一次，check-result 引用证据。重大未知返回主文档澄清。

## 7.6 独立复核

复核关注遗漏、越界、错误假设、实现偏差、缺少证据和不必要复杂度。
高风险要求独立审查者；同一个 Agent 切换角色不能当作独立复核。
复核默认只报告问题，修复遵守原授权与范围，不借复核扩大工作。

## 7.7 验证矩阵

验证随实际风险选择：功能、单元、集成、端到端、故障、性能、安全、兼容与回退。
使用者关心的结果在 VERIFY 前四节呈现，详细命令、环境和日志定位放最后一节。
未运行的检查不能计通过，失败不能用重跑成功覆盖原始记录。

## 7.8 项目记忆

未来有用的决定、失败方案与教训才进入 MEMORY。确认后跨工作有效的事实可进入 docs/。
正常状态跳转与 Git diff 已能恢复的变化不必复制到记忆中。
