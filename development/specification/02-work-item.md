# 2. 工作项：统一入口与流程决策

## 2.1 什么是工作项

系统把所有需要跟踪、设计、开发或验证的工程工作统一抽象为工作项（WORK）。新增项目搜索、增加Redis 缓存、修复登录失败、重构订单模块、升级数据库版本、优化接口性能和增加安全审计，都可以作为一个独立工作项。

工作项不是一张只记录标题和负责人的工单。它至少要回答：为什么做、成功标准是什么、属于哪种工作、风险有多大、会波及哪里、有哪些额外关注、当前走什么流程、还有哪些待确认和风险点，以及关联了哪些定义、任务和验证文档。

一个工作项进入系统后，通常经历以下过程：

```text
创建工作项
    ↓
判断工作类型
    ↓
评估风险与影响面
    ↓
识别额外关注与当前卡点
    ↓
生成实际流程和所需文档
    ↓
定义、设计与任务拆分
    ↓
开发、复核与验证
    ↓
上线、观察与项目记忆
```

## 2.2 五种工作类型

工作类型决定主流程。系统支持五种类型，每个 WORK 必须选择其中一种；TASK 只继承所属 WORK 的类型与边界，不能重新决定主流程。

### 2.2.1 产品功能（product）

产品功能是用户能够直接感受到的新能力或行为变化，例如搜索、登录、支付、个人资料、项目管理、页面功能和交互变化。它的主定义文档是 FEATURE，流程通常需要用户体验设计，并且对业务规则、边界情况和失败状态有明确要求。

### 2.2.2 基建（infra）

基建主要服务于系统、开发者、运维人员、智能体或其他模块，例如缓存、消息队列、日志系统、任务调度、权限底座、构建与发布系统、数据库基础设施、内部开发工具和公共服务。它的主定义文档是CAPABILITY，不默认要求用户界面设计，但需要考虑开发体验、运维要求、接入方式和失败恢复。

### 2.2.3 问题修复（fix）

问题修复用于实际行为与预期行为不一致的情况，例如页面报错、接口异常、数据错误、回归问题和边界缺陷。它的主定义文档是 ISSUE。即使使用快速流程，也必须说清楚实际是什么、应该是什么、如何复现，以及如何确认已经修好。

### 2.2.4 重构维护（maintenance）

重构维护原则上保持外部行为不变，主要改善内部工程状态，例如代码重构、模块拆分、依赖升级、技术债处理、删除旧代码和测试整理。它的主定义文档是 CHANGE，最重要的不是新功能，而是明确哪些行为和边界绝对不能改变。

### 2.2.5 工程改进（improvement）

工程改进用于提升系统性指标或控制工程风险，例如性能、稳定性、安全、隐私、成本、质量与合规。它的主定义文档是 IMPROVEMENT，需要同时记录当前数据、目标指标、验证方法和上线后的持续观察项。

## 2.3 额外关注（concerns）

工作类型决定主流程，额外关注决定还要增加哪些专项检查。一个工作项可以同时包含多个 concern：

| 标识 | 含义 | 常见增量 |
|---|---|---|
| `security` | 安全 | 威胁检查、人工确认、上线门禁 |
| `privacy` | 隐私 | 数据范围、授权与保留策略 |
| `data` | 数据 | 数据一致性、迁移与回退检查 |
| `performance` | 性能 | 基线、目标指标、性能验证与观察 |
| `reliability` | 稳定性 | 故障、恢复、回退与持续观察 |
| `observability` | 可观测 | 日志、指标、告警与定位能力 |
| `compatibility` | 兼容性 | 旧接口、旧数据与升级路径 |
| `accessibility` | 无障碍 | 键盘、语义、提示和辅助技术检查 |
| `cost` | 成本 | 资源与费用基线、上线后观察 |
| `release` | 上线风险 | 灰度、停止条件、回退和线上确认 |

例如，一个涉及账户数据的新产品功能可以声明：

```yaml
work_type: product
concerns:
  - security
  - privacy
  - data
```

这不会把它变成另一种工作类型，只会在产品功能基础流程上增加相应门禁。

## 2.4 风险级别

风险分为 `low`、`medium`、`high` 和 `critical` 四级。

低风险工作影响有限，问题容易发现、容易回退且数据风险低。中风险工作可能影响多个模块，需要明确验证并写清回退方式。高风险工作会影响核心业务、重要数据、大量用户或关键基建，必须有正式技术方案和独立复核。

关键风险包括不可逆数据变化、权限模型或登录认证体系变化、严重安全风险、核心数据库变化、生产发布体系变化、可能导致大面积服务不可用以及无法快速回退的操作。关键风险必须留下人工确认，脚本或智能体不能自行代签。

### 2.4.1 风险自动升级

风险不能完全依赖创建者主观填写。满足下列任一情况时，不允许直接标为低风险：

- 修改数据库结构或持久化数据格式；
- 修改公共接口、登录、权限或公共基础模块；
- 引入新的外部依赖；
- 涉及用户隐私、计费或资金；
- 涉及并发、事务或数据一致性；
- 修改发布基础设施；
- 无法快速回退。

以下情况应至少评估为高风险：

- 不可逆或大规模数据迁移；
- 权限模型或登录认证模型整体变化；
- 核心数据库结构、核心业务链路或生产基础设施变化；
- 密钥或凭证机制变化；
- 多个核心服务同时受到影响。

管理工具应根据这些事实提高最低风险，不能因为调用者传入 `low` 就忽略客观风险。

## 2.5 影响面

影响面分为 `local`、`multi-module` 和 `system`。

局部影响通常只修改一个模块，不改变公共接口或共享数据。跨模块影响表示多个模块需要配合，或者公共接口、共享组件、共享数据发生变化。系统级影响通常涉及登录或权限体系、核心数据库模型、全局配置、公共基础库、发布系统、网络层或多个服务间协议。

风险和影响面回答不同问题：风险决定检查需要多严格，影响面决定检查需要覆盖多远。一个修改范围很小但不可逆的数据操作可能风险很高；一个覆盖多个内部模块、可快速回退的整理也可能是系统级影响但不要求业务上线。二者不能互相替代。

## 2.6 当前未知与流程输入

流程是否能够继续，还取决于当前未知。未知统一记录为待确认项，而不是隐藏在聊天记录或智能体
推断中。待确认项可以处于：

- `open`：问题尚未确认；
- `assumed`：已经记录当前假设，可以按该假设继续；
- `resolved`：已经得到确认；
- `blocking`：缺少结论会影响后续工作，受影响阶段必须卡住。

因此，实际流程由以下信息共同决定：

```text
工作类型
+ 风险级别
+ 影响面
+ 额外关注
+ 当前卡点
```

它们分别回答“走哪条主流程”“检查多严格”“覆盖多远”“增加什么专项检查”和“现在能不能继续”。

## 2.7 流程生成顺序

流程必须按稳定顺序生成：

```text
WORK Type 基础流程模板
→ 风险级别增量规则
→ 影响面增量规则
→ concern 专项规则
→ 当前未知与人工确认卡点
→ 当前 WORK 的实际 workflow
```

风险、影响面和 concern 可以把可选阶段升级为必做、插入阶段、要求额外文档、增加阶段检查门禁、增加人工确认，或者要求上线与观察。它们不能抹掉 WORK Type 的基础顺序与语义，更不能把所有工作改造成同一条“完整流程”。
