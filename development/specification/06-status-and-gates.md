# 6. 状态与关卡：用事实定义“做到哪里”

## 6.1 三类状态机

WORK、TASK 和其他文档有不同责任，因此使用不同状态机。

工作项状态是：

```text
todo → ready → doing → implemented → verified → released → confirmed
```

`cancelled` 表示工作终止。各状态分别代表待开始、可以开发、开发中、代码完成、验证通过、已上线和线上确认。`implemented` 只表示实现已经完成，不代表验证、发布或线上结果。

TASK 状态是：

```text
todo → ready → doing → done → verified
             ↘ blocked
```

`cancelled` 同样表示终止。TASK 只有在依赖、范围与完成标准明确后才能进入 ready；done 表示实现完成，verified 表示已有验证证据覆盖任务。

除 WORK 与 TASK 外，受管理文档使用：

```text
draft → review → approved
                 ├─ deprecated
                 ├─ superseded
                 └─ archived
```

只有经人审核后进入 approved 的上游文档可以作为稳定开发依据。`approved` 是人的确认，不是智能体
对自己文档质量的评价。低风险快速流程可以省略独立 review 状态，由人把已补全定义从 draft 直接
确认到 approved，但不能把带占位内容的草稿直接当作 TASK ready 的依据。

## 6.2 状态推导

工作项状态不应完全依赖人工填写。脚本可以根据已经存在的事实推导：

```text
存在 blocking 待确认
→ 首个受影响阶段 blocked，WORK 保持 todo

ready 边界前的 required 阶段已经由人确认完成，TASK 已获得执行授权
→ ready

存在 doing TASK
→ doing

所有 TASK done
→ implemented

所有必要 VERIFY approved 且 result=pass
→ verified

记录上线成功
→ released

线上验证通过
→ confirmed
```

阶段状态与 WORK 状态必须一起刷新。WORK 进入 ready、implemented、verified、released 或 confirmed时，对应边界之前的 required 阶段必须为 done。人工可以在有理由和证据时覆盖状态，但工具不能代替人工完成产品判断、高风险确认或线上责任。

## 6.3 定义关卡

产品功能进入稳定开发依据前，至少应确认为什么做、谁会用、正常流程、边界与失败情况、完成标准、性能和安全等关注项、本次不做什么，以及不存在关键卡点。

基建能力至少应确认使用者、提供的能力、输入输出、失败行为、性能与稳定性、兼容、升级或迁移要求，并且没有关键卡点。

这些要求不是为了让定义文档变长，而是为了防止把重要业务与能力假设推迟到代码阶段才发现。

## 6.4 体验与设计关卡

EXPERIENCE 应按适用情况确认主流程、异常流程、加载、空、错误等状态、移动端、无障碍和关键文案；开发或运维体验则检查接入、错误、调试、部署、监控和恢复。

DESIGN 至少应明确整体方案、模块职责、数据影响、接口、失败处理、安全、监控和迁移，重要方案要有比较，关键风险要有记录，并且不能带着 blocking 未知进入实施。

## 6.5 计划与开发关卡

PLAN 需要让范围可拆、依赖和顺序明确，并记录风险、验证与回退方式。TASK 则把计划落成单个智能体可以独立执行的范围。

智能体写完这些文档后必须先停在文档交付点，向人集中展示主要变化、待确认项、风险和计划修改范围。
人的初始需求不能被解释为提前批准尚未写出的文档。只有人随后明确表示文档通过并允许执行，相关
上游文档才能记录为 approved，TASK 才能进入 ready，开发阶段才可以开始。

开发完成检查至少包括：代码或文档产物完成、必要测试完成、没有超范围修改、没有偷偷改变上游定义，新增未知和风险已经记录。只有满足这些事实，TASK 才能从 doing 进入 done。

## 6.6 验证关卡

验证阶段要求重要要求都有对应证据，必要测试已经通过，没有严重回归，修改范围正确，没有未处理的实现偏差，并且 VERIFY 已记录实际结果。验证不是把测试命令列在 TASK 里，而是实际执行并保存结果。

## 6.7 完成定义

代码完成不能视为整个工作完成。最低闭环是：

```text
定义明确
↓
代码完成
↓
验证通过
```

需要上线的工作还要继续：

```text
定义明确
↓
代码完成
↓
验证通过
↓
已上线
↓
线上确认
```

这一区分保证“已经实现”“已经证明”和“已经在真实环境稳定运行”不会被压成同一个模糊的完成状态。
