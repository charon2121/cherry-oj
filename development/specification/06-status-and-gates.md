# 6. 状态与关卡：用事实定义“做到哪里”

## 6.1 三类状态机

WORK、TASK 和其他文档有不同责任，因此使用不同状态机。

工作项状态是：

```text
todo → ready → doing → implemented → verified
```

`cancelled` 表示工作终止。各状态分别代表待开始、可以开发、开发中、代码完成和验证通过；`verified` 是终态。`implemented` 只表示实现已经完成，不代表验证结果。

项目当前处于 MVP 开发阶段，没有生产环境，因此流程里没有上线与线上观察阶段，也没有 `released` 与 `confirmed` 状态——理由见 [§4.9](./04-workflows.md#49-强制完整流程)。真正具备生产环境后再重新引入。

TASK 状态是：

```text
todo → ready → doing → done → verified
             ↘ blocked
```

`cancelled` 同样表示终止。TASK 只有在依赖、范围与完成标准明确后才能进入 ready；done 表示实现完成，verified 表示已有验证证据覆盖任务。

除 WORK 与 TASK 外，受管理文档使用：

```text
draft → review → checked   ┐
              ↘  approved  ├─ deprecated / superseded / archived
```

**定稿有两种方式，因为文档有两类内容。**

| 类别 | 文档 | 终态 | 谁给出 | 判据 |
|---|---|---|---|---|
| 决定类 | PRODUCT、FEATURE、CAPABILITY、ISSUE、CHANGE、IMPROVEMENT、EXPERIENCE、DECISION | `approved` | 人，在意图闸上一次签署 | 没有客观标准，只能由人拍板 |
| 验收类 | VERIFY | `approved` | 人，在验收闸上一次签署 | 结论是否被接受由人决定 |
| 记录类 | DESIGN、PLAN、MEMORY | `checked` | 工具 | 结构与内容校验通过；陈述只有真假，没有“批准”可言 |

给记录类文档盖章是橡皮图章：它训练人快速通过，而这个习惯会原样带到真正需要判断的文档上。
**过多的闸门不是更安全，是把所有闸门一起废掉。** 因此记录类文档由工具在 `refresh` 时从 `review`
推进到 `checked`，不消耗人的判断力。

`approved` 与 `checked` 都表示“已定稿、可以作为开发依据”，区别只在于由谁确认。二者都不允许由
智能体自行声明代表人的判断：`approved` 只能来自闸，`checked` 只能来自校验通过。带占位内容的草稿
在任何情况下都不能作为 TASK ready 的依据。

## 6.1.1 两道闸

人工确认收拢到每个工作**仅有的两次**签署，记录在 WORK 的 `gates` 字段：

```text
意图闸 intent      开工前   覆盖全部决定类文档   回答“这是不是我要的”
验收闸 acceptance  收束时   覆盖 VERIFY 与完成声明  回答“这是不是做完了”
```

- 一道闸一次签署，**同时**把它覆盖的全部文档推进到 `approved`；不再逐份审批。
- 闸有前置条件：意图闸要求没有未澄清的 `blocking_items`、覆盖文档都已脱离 `draft`；验收闸要求
  意图闸已过、全部 TASK 已完成、VERIFY 已记录结论。前置条件不满足时工具拒绝签署并列出原因。
- 闸可以撤回，撤回会把它覆盖的 `approved` 文档退回 `review`。若工作状态正建立在该闸之上
  （例如已经 verified），必须先退工作状态再撤闸。
- 智能体不能代签任何一道闸，也不能从格式校验通过、测试全绿或最初的完成请求中推断授权。

## 6.1.2 结论是否仍然成立

工作状态回答「进展到哪」，`outcome` 回答「结论还算不算数」。这两件事必须分开：

```yaml
outcome: {"state": "superseded", "by": "WORK-012", "reason": "运行时实现已整体撤回"}
```

| state | 含义 | `by` |
|---|---|---|
| 缺省 | 结论仍然成立 | — |
| `superseded` | 被后续工作取代或撤回 | 必填 |
| `invalidated` | 前提或结论被证伪，没有接替者 | 可空，但必须有 MEMORY |

**不能用 status 表达这件事。** 一个被撤回的工作确实走完过流程、确实通过过验证；把它改成
`cancelled` 是篡改历史。还没有产出的工作（未到 `implemented`）不能标记 outcome——没有结论就谈不上
结论被推翻，那种情况用 `cancelled`。

标记必须出现在总览、单项视图和追踪关系里。不进视图的字段等于不存在：此前 WORK-010 被 WORK-012
整体撤回，只能靠正文一句引言表达，在任何视图里都和一个有效的已验证工作长得一模一样。

## 6.2 状态推导

工作项状态不应完全依赖人工填写。脚本可以根据已经存在的事实推导：

```text
存在 blocking 待确认
→ 首个受影响阶段 blocked，WORK 保持 todo

ready 边界前的 required 阶段已经由人确认完成，TASK 已获得执行授权
→ ready

存在 doing TASK
→ doing

所有 TASK done
→ implemented

所有必要 VERIFY approved 且 result=pass
→ verified

```

阶段状态与 WORK 状态必须一起刷新。WORK 进入 ready、implemented 或 verified 时，对应边界之前的 required 阶段必须为 done。人工可以在有理由和证据时覆盖状态，但工具不能代替人工完成产品判断或高风险确认。

## 6.3 定义关卡

产品功能进入稳定开发依据前，至少应确认为什么做、谁会用、正常流程、边界与失败情况、完成标准、性能和安全等关注项、本次不做什么，以及不存在关键卡点。

基建能力至少应确认使用者、提供的能力、输入输出、失败行为、性能与稳定性、兼容、升级或迁移要求，并且没有关键卡点。

这些要求不是为了让定义文档变长，而是为了防止把重要业务与能力假设推迟到代码阶段才发现。

## 6.4 体验与设计关卡

EXPERIENCE 应按适用情况确认主流程、异常流程、加载、空、错误等状态、移动端、无障碍和关键文案；开发或运维体验则检查接入、错误、调试、部署、监控和恢复。

DESIGN 至少应明确整体方案、模块职责、数据影响、接口、失败处理、安全、监控和迁移，重要方案要有比较，关键风险要有记录，并且不能带着 blocking 未知进入实施。

## 6.5 计划与开发关卡

PLAN 需要让范围可拆、依赖和顺序明确，并记录风险、验证与回退方式。TASK 则把计划落成单个智能体可以独立执行的范围。

智能体写完这些文档后必须先停在文档交付点，向人集中展示主要变化、待确认项、风险和计划修改范围。
人的初始需求不能被解释为提前批准尚未写出的文档。只有人随后明确表示文档通过并允许执行，相关
上游文档才能记录为 approved，TASK 才能进入 ready，开发阶段才可以开始。

开发完成检查至少包括：代码或文档产物完成、必要测试完成、没有超范围修改、没有偷偷改变上游定义，新增未知和风险已经记录。只有满足这些事实，TASK 才能从 doing 进入 done。

## 6.6 验证关卡

验证阶段要求重要要求都有对应证据，必要测试已经通过，没有严重回归，修改范围正确，没有未处理的实现偏差，并且 VERIFY 已记录实际结果。验证不是把测试命令列在 TASK 里，而是实际执行并保存结果。

## 6.7 完成定义

代码完成不能视为整个工作完成。最低闭环是：

```text
定义明确
↓
代码完成
↓
验证通过
```

这一区分保证“已经实现”和“已经证明”不会被压成同一个模糊的完成状态：代码写完只是 `implemented`，必须有 approved 且 `result=pass` 的 VERIFY 才是 `verified`。

MVP 阶段没有生产环境，`verified` 就是完成。等到真正有生产环境时，再在这条闭环之后接上线与线上确认——但不能反过来，为了流程看起来完整而保留两个永远走不完的阶段。
