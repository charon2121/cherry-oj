# 4. 五类任务的流程与材料

所有类型共用：准备短说明 → 用户确认目标与取舍 → 实施与必要复核 → 验证并交付结果 → 用户接受。确认通过聊天完成；用户对某次工作给出的明确豁免优先。只要求改文档时，写完即交付文档，不延伸到业务实施。

## 必需材料

每项工作必需 `00-work.md`。下表的定义和技术要点写在这份说明中；细节太长才作为附件，验证结果在实施后补齐，不提前造空证据。

| 类型 | 动手前要弄清楚 | 实施顺序 | 交付时的证据 |
|---|---|---|---|
| 功能 product / feature | 谁在什么场景使用；前后变化；正常、失败与权限行为 | 定义场景 → 有界面时确认体验方向 → 契约和方案 → 实施 → 跑完整场景 | 实际场景、必要测试、权限/失败路径；界面变化有可查看的效果 |
| 修复 fix / bug | 实际与预期；复现条件；已知原因和未确认的推断 | 复现或取得证据 → 定位 → 做针对性修复 → 验证原问题及邻近行为 | 原失败与修复后的对照；难以复现时写清证据局限，根因不明不冒称已解决 |
| 基建 infra | 谁使用；怎么接入；输入输出；限制、失败和恢复 | 确认使用合同 → 接入/迁移与恢复方案 → 建基础能力 → 集成验证 | 使用方真实接入；配置、失败与恢复；涉及迁移时记录迁移结果 |
| 维护 maintenance | 当前结构问题；目标；不能变化的对外行为和边界 | 固定不变量与回归依据 → 有依赖时安排步骤 → 重构/清理 → 前后对照 | 行为或构建对照；跨模块回归；相关旧入口已同步 |
| 改进 improvement | 当前基线；可观察目标；比较方式和容许代价 | 取得基线 → 比较方案 → 改动 → 按相同条件比较 | 性能改进有测量条件和前后数值；体验改进有场景与人工反馈 |

任务可以混合：修 bug 涉及界面时加体验检查，功能涉及数据迁移时加迁移与恢复；仍用一份主说明，不为分类复制工作。

## 哪些情况才加附件

| 实际需要 | 可增加的材料 |
|---|---|
| 接口、数据或方案复杂，短说明放不下可执行细节 | `design.md`；比较与重要决定可在其中写清，长期需要独立引用才用 `decision.md` |
| 用户流程多，需要单独看界面或交互 | `experience.md` 或明确的效果材料；简单页面在主文档链接效果即可 |
| 工作有依赖、独立委派或分批交付 | `plan.md` 和确有独立边界的 `task-短名.md`，单人连续工作不拆 TASK |
| 验证结果较多，需要保留逐项证据 | `verify.md`，主说明只给结果、差异和链接 |
| 新结论以后会复用 | 优先更新已有全局文档并链接来源；暂时只适合本工作才保留独立经验记录 |

附件由需要决定，不随类型生成 FEATURE、ISSUE、CAPABILITY 等第二份定义。没有内容的章节删除，不用“无”“不适用”的列表撑满模板。

## 验证怎么加深

权限和安全相关要检查拒绝路径；涉及数据要说明备份、迁移或无法回退的代价；公共契约和跨模块改动要跑消费者回归。高风险方案需要适当的复核和恢复验证，复核方式依已有授权与可用条件决定，不自动委派其他 Agent。未执行的检查如实记录，测试成功不代替产品判断。
