# 8. 人、智能体与脚本：责任和写权限

## 8.1 三方责任边界

确定性规则、内容理解和价值判断应由不同主体承担。

脚本负责结构、状态、编号、模板、关系、流程、基础校验、查询和上下文组装。凡是可以由明确规则
判断的事情，都应尽量自动化，避免人工重复维护。

智能体负责内容理解与生成、语义检查、风险和影响面建议、文档审查、代码实现与验证分析。智能体
可以提出判断，但不能把建议伪装成已经获得责任主体确认的决定，也不能审批自己刚生成的开发依据。

人负责最终产品判断、关键取舍、高风险决定和无法自动判断的问题。需要人负责的事项应被集中聚合，
而不是散落在多份文档中。

这套边界可以概括为：

```text
规则能判断 → 脚本
需要理解   → 智能体
需要负责   → 人
```

## 8.2 逻辑角色

系统建议支持以下逻辑角色：

```text
需求智能体
体验智能体
架构智能体
计划智能体
开发智能体
复核智能体
验证智能体
上线智能体
维护智能体
```

角色表示职责，不要求使用不同模型或不同进程。同一个智能体可以在不同时间切换角色，但每次行动都要遵守当前角色的写权限和工作项边界。

## 8.3 默认写权限

默认写权限按信息层分配：

| 角色 | 默认负责的产物 |
|---|---|
| 需求智能体 | PRODUCT、FEATURE、CAPABILITY，以及问题或改动定义 |
| 体验智能体 | EXPERIENCE |
| 架构智能体 | DESIGN、DECISION |
| 计划智能体 | PLAN、TASK |
| 开发智能体 | 代码、测试和任务执行记录 |
| 复核智能体 | 复核结果 |
| 验证智能体 | VERIFY |
| 上线智能体 | 上线记录与阶段证据 |
| 维护智能体 | MEMORY 与维护类工作 |

下游角色不能默认修改上游文档。开发智能体发现 FEATURE 有问题时，应提出产品变更；复核智能体发现缺陷时默认报告；验证智能体不能通过修改验收标准让失败结果变成通过。

在人的初始意图到达后，需求、体验、架构和计划角色可以写对应文档；开发、上线等实施角色默认没有
写权限。人完成文档审核并明确授权后，实施角色才获得当前 TASK 边界内的写权限。只读检查、文档
校验和维护文档结构的管理命令不属于产品实施，可以在文档回合完成。

## 8.4 智能体任务上下文包

系统需要根据 TASK 自动组装“恰好够用”的上下文，而不是把整个项目全部塞给智能体。上下文包通常
包含：

- 项目规则入口；
- 当前 WORK；
- 相关功能或能力定义；
- 相关 EXPERIENCE；
- 相关 DESIGN 与 DECISION；
- 相关 PLAN；
- 当前 TASK；
- 相关代码路径和测试路径；
- 相关 MEMORY。

上下文包还必须显式包含 TASK 的可读、可写和禁止路径。这样既减少无关信息，也能让智能体在越界前发现需要升级。

## 8.5 人工确认

系统应统一展示“需要你确认”，其中聚合决定、待确认项、高风险、产品行为变化、重大技术变化与不
可逆操作。关键风险、人工产品判断、发布责任和线上确认不能由脚本根据测试全绿自动签署。

### 8.5.1 人工确认只有两个点

**每个工作只保留两次人工签署**，其余文档由工具定稿（判据与状态见
[第 6 章](./06-status-and-gates.md)）：

| 闸 | 时机 | 你在判断什么 | 覆盖 |
|---|---|---|---|
| 意图闸 | 开工前 | 要达成什么、成功标准、不能破坏什么、边界在哪 | 全部决定类文档 |
| 验收闸 | 收束时 | 实际发生了什么、和当初承诺差在哪、遗留什么 | VERIFY 与完成声明 |

人工注意力是这个系统里最稀缺的资源，必须按稀缺资源分配。审批点数量应当与**工作数**成正比，
而不是与**文档数**成正比——否则文档体系每增长一层，人的负担就跟着增长一层，最终结果不是更
严格的把关，而是所有把关一起退化成走过场。

闸的前置条件由工具检查并在不满足时拒绝签署，但**前置条件全部满足不等于闸自动通过**：工具只能
证明材料齐备，不能代替人回答“这是不是我要的”。

### 8.5.2 两轮协议

每项工作的首次协作使用以下两轮协议：

```text
人说明意图
→ 智能体编写或修改文档
→ 智能体交付文档并停止实施
→ 人审核，提出修改或明确通过
→ 人明确允许执行
→ 智能体开始 TASK、编码或其他实施动作
```

审核未通过时继续修改文档，仍不能实施。只有后续的人类消息可以同时表达“文档通过”和“允许执行”；
智能体不能从沉默、格式校验通过、测试通过、工作项状态或最初的完成请求中推断授权。若人明确说明
本次只修改文档，流程结束于文档交付。

“人明确通过”在系统里的落点就是意图闸：`scripts/work gate <WORK> intent`。智能体可以准备材料、
可以说明前置条件已满足，但不能执行这条命令，也不能把任何一份决定类文档直接置为 `approved`。
