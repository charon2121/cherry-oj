# 8. 人、Agent 与脚本

## 8.1 三方责任边界

人决定目标、边界、重要取舍与是否接受结果。Agent 理解需求、设计实现、复核证据和维护上下文。
脚本检查结构、引用、边界、状态和检查结论，生成视图。三者不能相互冒充。

## 8.2 逻辑角色

需求、体验、架构、计划、开发、复核、验证、维护是职责，不是必须分别输出文档的岗位。
同一 Agent 可承担多种职责，但不因此获得人工签署权，也不能把自身复查称为独立复核。

## 8.3 默认写权限

先形成主文档及必要附件；实施授权后，在 WORK/TASK 范围内改动。
发现上游问题先提出升级，不通过修改定义掩盖实现偏差。
记录技术进度是 Agent 的职责；验收结果的人工批准仍由人负责。

## 8.4 智能体任务上下文包

没有独立任务时使用 context WORK-xxx：包含主工作、附件、证据和读写边界。
独立 TASK 使用 context TASK-xxx：主工作、任务、直接依据与相关决定/记忆。
既有 AGENTS.md 与语言、框架规范仍需按需读取，不把整个仓库无差别加入上下文。

## 8.5 人工确认

每个工作只保留意图与验收两道闸。默认不增设常设实施授权，也不增加逐文档审批。
已由人明确授权的工作按会话范围继续；不得把格式检查、沉默或测试通过当作新的授权。

### 8.5.1 人工确认只有两个点

意图：变化、边界、取舍、未知、验收。验收：实际结果、承诺差异、验证情况、遗留问题。
前者来自主文档原文，后者来自 VERIFY 原文，不另维护摘要文件。
批准这些内容不表示审查了全部技术细节；重要代价不能只写在附件中。

### 8.5.2 两轮协议

人说明意图 → Agent 整理并展示审核内容 → 人在后续消息确认并允许执行、签署意图闸 → Agent 实施。
交付后由人签署验收闸。Agent 可以说明材料齐备和给出命令，但不能执行签署或伪造已批准状态。
用户只要求改文档时，文档交付后停止。
