# 3. 信息职责与边界

## 3.1 六个问题必须分开

为什么做、做什么、怎样使用、怎样实现、怎样执行、怎样证明，是不同问题。
精简主文档用章节区分它们，内容复杂或需要独立协作时才拆文件。

## 3.2 信息优先级

人工明确确认的决定 → WORK 的目标/边界/验收 → 执行方案与附件 → 独立 TASK → 代码和测试
→ 注释 → Agent 推断。历史 layered 工作仍以独立定义文档为产品依据。

主文档是人工判断的唯一主文，不能另写一份措辞不同的摘要。
附件解释方案，重要取舍必须在主文档明确呈现；人签署主文档不代表逐份批准附件。

## 3.3 任务读写边界

compact WORK 必须声明 read_paths、write_paths、forbidden_paths；无额外禁区时显式空列表。
路径使用仓库相对路径，不接受绝对路径或父目录跳转。TASK 保留独立范围，不能扩大主工作范围，
并继承主工作禁区。执行者也必须遵守全局授权，不把路径声明解释成提交、部署或发送消息的许可。

## 3.4 三种改动升级

普通实现调整在已确认边界和方案内自主处理。重要技术路线改变时先更新执行方案，必要时更新 DESIGN。
产品行为、范围或实质代价变化时，暂停相关工作，更新主文档并重新获得确认。
不能通过先扩大路径清单、事后补文档来改变范围。

## 3.5 实现偏差

偏差说明应该怎样、实际怎样、影响与处理建议；不能直接改验收标准使失败结果变成通过。
交付在 VERIFY 的「承诺差异」呈现。详细日志只留一处，其他位置引用。

## 3.6 人工注意力的聚合

board 从主文档前五节读取变化、边界、取舍、未知、验收；交付读取 VERIFY 前四节。
状态和详细流程按需展开。Agent 对摘要完整性负责，不能隐藏重要风险以换取签署。
