# 3. 信息分层：内容边界、决策权与改动升级

## 3.1 六个问题必须分开

同一个工作项会产生多种信息，但这些信息不能混在同一层里。系统要求分别回答六个问题：

| 信息层 | 回答的问题 | 典型产物 |
|---|---|---|
| 背景与目标 | 为什么做 | PRODUCT、WORK 背景 |
| 定义 | 做什么 | FEATURE、CAPABILITY、ISSUE、CHANGE、IMPROVEMENT |
| 体验 | 怎么使用、接入和运维 | EXPERIENCE |
| 设计 | 怎么实现、为什么这样选 | DESIGN、DECISION |
| 执行 | 怎么开发、范围和依赖是什么 | PLAN、TASK |
| 证据 | 怎么验证、怎样证明完成 | VERIFY、MEMORY |

产品定义不能直接夹杂具体数据库字段、框架、代码文件或函数实现；技术方案不能借实现便利重新定义产品行为；开发任务也不能重新决定产品需求或整体架构。章节可以放在同一个工作项目录中，但信息责任必须保持清楚。

## 3.2 信息优先级

发生冲突时，项目按以下优先级处理信息：

```text
人工确认的决定
↓
功能定义 / 能力定义 / 问题说明 / 改动说明 / 改进说明
↓
体验设计 / 技术方案 / 技术决策
↓
开发计划
↓
开发任务
↓
代码与测试
↓
代码注释
↓
智能体自己的推断
```

上层与下层冲突时默认以上层为准。代码不能反向覆盖已经确认的需求，智能体也不能因为现有实现比较方便，就把实现现状解释成新的产品规则。若上游确实有问题，应使用改动升级流程修正，而不是悄悄改变权威顺序。

## 3.3 任务读写边界

每个 TASK 都必须明确三类范围：

```text
可以看什么
可以改什么
不要动什么
```

它们在元数据中对应 `read_paths`、`write_paths` 和 `forbidden_paths`。任务进入 `ready` 之前，
这些范围必须具体到足以约束单个智能体独立执行。发现需要修改禁区或超出允许范围时，不能只扩大路径列表；应先判断它是普通实现调整、技术方案变化还是产品行为变化。

## 3.4 三种改动升级

### 3.4.1 普通实现调整

如果调整不改变功能或能力定义、不改变技术方案的重要决定，也不改变外部行为，可以在现有 TASK
范围内处理。实现细节仍要符合任务的读写边界。

### 3.4.2 技术方案变化

技术实现路线发生明显变化时，必须暂停相关任务、更新 DESIGN，重新检查影响面，并在需要时更新
DECISION 与 PLAN。TASK 不能通过“实现记录”取代方案层的正式变化。

### 3.4.3 产品行为变化

用户可观察行为或业务规则发生变化时，必须暂停实现、更新 FEATURE 或 PRODUCT、获得人工确认，并根据新定义重新生成后续流程。产品变化不能隐藏在代码评审或任务备注里。

## 3.5 实现偏差

如果代码行为与上游定义不一致，应建立实现偏差记录，至少写清：

- 应该是什么；
- 现在是什么；
- 影响哪里；
- 可能原因；
- 建议怎样处理。

不得通过直接修改需求来“消除”偏差。偏差可能最终促成产品变更，也可能要求代码回到原定义，但这
必须经过对应层级的判断。

## 3.6 人工注意力的聚合

系统应把所有需要人负责的内容集中显示，包括关键决定、待确认项、高风险、产品行为变化、重大技术变化和不可逆操作。人工不应为了寻找三处关键问题而逐篇阅读所有文档；普通实现细节、格式和引用关系应由智能体与工具处理。
