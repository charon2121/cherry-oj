# DECISION-019：确定下载版设计系统的权威性、双主题与生产适配边界

## 要决定什么

下载目录中的 Claude Design 产物应以什么身份进入仓库，哪些内容必须精确复现，哪些原型实现必须转换为
生产实现，以及如何在来源仅提供暗色的情况下保留产品现有浅色主题。

## 背景

用户明确表示下载版页面符合其审美，并要求用它重建仓库现有设计系统，同时明确浅色主题必须保留。下载版与当前系统都源自
Linear-inspired OpenDesign 材料，但下载版更严格地保持暗色、半透明层级、精确尺寸和克制交互。它同时
包含示例代码中的原型性缺陷：远程 CDN、inline style、鼠标状态、随机 id、可点击非语义节点和内联 SVG
路径。若把代码逐字复制，会获得接近的截图，却破坏现有生产质量；若只借鉴颜色，又会重演 WORK-034 原先
发现的“token 合规但风格不一致”。

## 候选方案

1. **逐字复制下载包到 Web。** 视觉最直接，但无法满足 React 19/TypeScript/Base UI、SSR、键盘、可访问性、
   本地依赖和项目 API，且会把 demo 功能误带入产品。
2. **只拷贝 token，保留现有组件和页面。** 迁移最小，但只能改变颜色/尺寸，无法达到用户认可的 Shell、
   密集列表、toolbar、Card、状态点和排版组合，正是此前失败原因。
3. **冻结完整来源，只重建暗色并删除浅色。** 暗色忠实度最高、状态矩阵较小，但会删除用户明确要求保留的
   产品能力。
4. **冻结完整来源，按同一语义生产化重建双主题。** 下载版精确约束暗色和跨主题的组件/构图；浅色保留
   现有主题 ID 与交互，用相同语义重做主题相关颜色和 elevation。两主题共用组件结构和非颜色 token。

## 决定

待人工确认以下整体决定：

- 选择方案 4。`~/Downloads/Cherry OJ Design System` 的 99 文件完整快照是 WORK-034 的视觉来源证据；
  `readme.md`、tokens、组件 prompt 和 UI kit 是语义/构图权威，生成 HTML/bundle/manifest/lint 是辅助证据。
- 下载版值与视觉配方必须精确迁移；生产实现不复制其原型代码结构，继续使用 TypeScript、React 19、
  Base UI、TanStack、Tailwind adapter、lucide-react 和现有业务状态。
- 保留 `cherry-black`、`pure-white`、ThemeSwitcher、用户主题偏好和无闪烁首屏主题脚本。暗色颜色精确
  对齐下载版；浅色保留现有产品行为，但按新 surface/text/border/elevation 语义重新校准。
- 双主题不是两套设计系统：组件 DOM、variant、spacing、typography、radius、layout、motion 和状态规则
  必须共用；主题文件只提供确实随明暗变化的 token，禁止复制组件或在页面写主题分支。
- 生产 token 保留 `--ds-*` 命名空间作为仓库边界，通过映射实现下载版 `--accent`、`--surface-*` 等语义；
  保留命名空间不是保留旧设计值。
- 全站功能、API、权限、数据和路由语义不变。下载版 marketing/app kit 只提供视觉构图，不授权新增注册、
  竞赛、站点营销、命令面板等产品功能。
- 安全和可访问性是显式生产适配：inline prose link 保留下划线；可点击行使用真实 link/button；disabled
  不让必要文字跌破对比度；id 使用 `useId`；字体本地提供；图标使用 lucide-react；长文本继续 CodeMirror。
- 旧设计系统通过 Git 历史回退，不在运行时保留旧/新系统切换。主题切换只在新系统的暗色和浅色之间发生。
  所有适配偏差与浅色推导依据写入文档和 VERIFY，不能静默偏离。

## 理由

用户认可的是整套视觉语言，不只是几个色值；因此必须把来源快照、tokens、组件与 UI kit 一起作为目标。
同时 Cherry OJ 已有认证、编辑器、危险操作和可访问性边界，下载包没有覆盖这些生产问题。视觉权威与代码
实现权威分开，既能做截图级对照，也避免把原型缺陷固化进产品。用户明确要求保留浅色，因此来源的 dark-only
属性只是输入限制，不是产品功能决定；通过同构 token 而不是两套组件实现双主题，能保留能力并控制维护成本。

## 影响与风险

所有页面和组件状态必须在两个主题下重新验收，截图/对比度/首屏测试量相应增加。浅色没有下载版直接视觉
真源，其依据是共同的构图与 token 语义、现有 `pure-white` 产品能力以及 WCAG/层级验证；不得声称浅色是
下载版的精确复制。组件 API 可为目标配方调整，但业务调用必须由迁移任务同步修改。来源包自身未附完整
许可证文件，实施必须保留当前 Apache-2.0/Lucide 许可和 NOTICE，并记录新来源 hash。下载版已知的远程字体、
无下划线、opacity disabled 等做法不会逐字进入生产，可能产生极小视觉差异，需由用户最终验收。

## 重新考虑条件

若用户要求增加更多主题、浅色必须逐值匹配另一份视觉来源、提供新的官方字体/Logo、下载包内容变更、许可链
无法确认，或生产适配导致用户认为观感不再等同于目标，必须撤回/修订本决定后再继续。多个产品未来需要共享
独立 npm 设计系统时，再评估从仓库内代码包拆成版本化 package；本次不提前发布包。
