# DECISION-022：采用判题节点自注册与节点侧数据安装

## 要决定什么

判题环境、节点在线状态和测试数据可用性由静态配置/共享目录继续维持，还是改为真实节点注册与逐节点
安装回执。

## 背景

当前部署先要求数据库存在 ACTIVE 环境，再由 judging-service 把文件写到本地目录。这既不能证明 Go
Judge 在线，也不能证明它看得到该目录。default profile 修补只能创建数据库行，强制共享 volume 也只
适用于单机，二者都不能成为新增节点时仍成立的系统事实。

## 候选方案

1. 无 profile 时自动加载 dev fixture：改动最小，但继续制造虚拟环境，且不解决目录错位。
2. 统一 Java 与 Go 的共享 volume：可完成单机联调，但跨主机、扩容、节点离线仍需人工配置。
3. judging-service 轮询固定节点列表：能探活，但节点列表和能力仍来自静态配置，扩缩容需要重启控制面。
4. Judge 节点自注册/心跳，节点自己安装数据并返回逐节点回执：控制面由真实运行事实驱动，支持本地与
   生产统一、节点扩缩容和未来对象存储。

## 决定

采用方案 4。`judge_environment` 表示不可变的环境兼容分组，`judge_node` 表示有租约的运行实例，
`test_data_node_deployment` 表示某节点真实安装某摘要的回执。首次真实环境自动 ACTIVE；不同指纹环境
只 REGISTERED，不自动切换。测试数据由 judging-service 流式推送到 Judge 节点安装 API。

## 理由

这个方案删除了两个错误前提：数据库 seed 不再代表机器存在，Java 本地文件不再代表 Judge 已获得数据。
扩容只需启动新节点；离线由租约判断；部署是否可用由节点回执判断。它保留现有环境切换与 calibration
模型，并允许以后把“推送 ZIP”替换成“节点按内容 hash 从对象存储拉取”，无需再次推翻控制面。

## 影响与风险

需要新增跨语言内部协议、两张表/迁移、Go 安装端点与心跳客户端、Java 注册和远程部署逻辑、Compose
配置及 ADMIN 错误映射。风险集中在租约竞态、回执校验、重复安装和迁移切换；以 feature flag 保留
legacy-local 回退，禁止在一次提交中直接删除旧链路。

节点控制只使用私网加一个共享 control token，不引入 PKI、证书轮换或新的账号系统。token 仅来自环境
变量，不进入数据库、响应或日志。

## 重新考虑条件

当节点数量或 ZIP 广播成本显著增长、出现跨机房部署，改为内容寻址对象存储与节点主动拉取；环境、租约
和逐节点回执仍保留。当已有 Kubernetes/Consul 成为统一服务发现来源时，可替换注册入口，但不能退回
“静态行等于在线节点”的模型。
