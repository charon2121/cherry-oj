# CHANGE-001：重建统一开发文档系统

## 为什么做

项目的开发记录原来分成两套：一套写产品要什么，一套写工程师做什么，各有各的状态和维护方式。
这种分法只装得下「需求」和「任务」两种东西，遇到打地基、修问题、做重构，以及记录风险、体验、
验证结果和经验教训时就没有位置可放；同一件事的来龙去脉还被拆到两个地方，想了解一件事做得怎么样，
得分别翻找再自己拼起来。本次重建统一的开发文档系统，让一件工作从提出到验证的全部记录集中在一处。

## 当前状态

`product/` 负责 REQ、产品决定和版本验收，`tasks/` 负责任务认领和技术状态；二者拥有不同命令、
Schema 和状态机，并通过双向 ID 维持一致性。全局 `docs/` 又被 Git 忽略，导致新克隆无法取得架构
和数据模型等被规则称为依据的文档。

## 当前问题

旧模型把同一次工程工作的原因、用户定义、设计、执行和验证拆散，基建、修复、维护与工程改进又被
迫使套用产品/任务二分。智能体无法从一个入口得知风险、影响面、必需流程、允许修改范围和验证断链；
人工还需要维护 REQ/TASK 的反向引用。

## 目标状态

- REQ-001：所有开发工作从稳定的 WORK ID 进入，并按工作类型、风险、影响面、关注项和未知生成流程。
- REQ-002：功能定义、技术方案、计划、任务、验证与记忆共享统一元数据和引用模型。
- REQ-003：`docs/` 与 `development/` 形成明确、可进入 Git 的两层文档边界。
- REQ-004：结构、编号、引用、依赖、状态与基础完成证据由脚本和 CI 检查。
- REQ-005：工具能为 TASK 组装受代码读写范围约束的智能体上下文。

## 不变条件

- REQ-006：运行时代码、接口契约、数据库和部署行为不变。
- REQ-007：仍有效的 C++ ACM 产品能力定义和旧流程的长期经验不能丢失。
- REQ-008：人工继续负责关键风险、产品行为和不可逆决定；工具不能根据测试自动代签这些判断。

## 影响范围

涉及根目录协作说明、`CLAUDE.md`、CI、Git 忽略规则、旧产品/任务目录与脚本；新增
`development/` 以及统一 `scripts/work`。全局设计文档本身不在本任务内重新定义。

## 风险

旧命令被删除是有意的不兼容变更。主要风险是迁移遗漏、状态规则过严导致无法渐进工作、或规则过松让
断链进入稳定状态；分别通过内容迁移、草稿阶段提示/稳定阶段报错和端到端用例控制。

## 回归检查

- AC-001：现有语言工程的构建与测试结果不因文档系统重构发生变化。
- AC-002：仓库不再引用旧产品/任务命令或把两个目录声明为真源。
- AC-003：C++ ACM 闭环的用户流程、业务规则、验收场景和未决问题可在新 FEATURE 中找到。
- AC-004：`scripts/work check` 能在正常仓库通过，并拒绝不存在引用、依赖环和无证据的 verified 状态。
