# DESIGN-001：重建统一开发文档系统

## 背景

旧双中心的结构问题与不变条件见 CHANGE-001。本方案实现 `development/SPECIFICATION.md` 中可先由
确定规则落地的部分：统一
元数据、流程选择、风险升级、编号、引用、状态、验证约束、查询和智能体上下文；语义审查仍由智能体
或人工完成。

## 目标与限制

目标是让一次工作从提出到验证只有一个入口，并能渐进地产生恰好需要的文档。工具必须使用 Python
标准库、可以在 GitHub Actions 直接运行；不得把内容价值判断伪装成结构规则，也不得修改运行时系统。

## 整体方案

仓库使用两层文档：`docs/` 保存经确认的全局事实，`development/` 保存具体工作过程。每个 WORK 记录
分类输入、流程输出和总状态；所有下游文档通过 `work` 归属，通过 `depends_on / related / implements /
verifies / supersedes` 建立图。

`scripts/work new` 执行风险升级、流程选择、单调编号和文档生成。`check` 做结构校验，`refresh` 只按
事实推导状态，`context` 从 TASK 选择上游定义、决定、记忆和代码范围。

## 模块与数据

- `development/index.json`：各类型下一个编号，删除文档也不回退；
- `development/schema/`：统一元数据的机器可读说明；
- `development/templates/`：各层正文的最小问题集；
- 类型目录：受管理文档与归档；
- `scripts/work`：无第三方依赖的解析、生成、校验与查询工具；
- `scripts/work_test.py`：在临时仓库验证行为，不污染真实工作项。

front matter 限制为每行一个 JSON 兼容值，复杂列表/对象仍能表示，但解析不依赖 PyYAML。

## 接口与状态

WORK、TASK 和普通文档分别使用三套状态集合。草稿阶段允许后续文档尚未完成；WORK 一旦进入 ready
或更后状态，缺少流程文档、卡点、未确认人工决定、未完成任务或缺少通过验证都会按阶段成为错误。

引用可以指向文档 ID 或局部要求（如 `FEATURE-001#REQ-002`）；局部编号必须真实出现在目标正文中。

## 安全与失败

TASK 必须在 ready 前声明可读、可写和禁止路径；上下文包明确展示这些边界。原子替换写入元数据，
生成前先对内存中的整体文档图校验，避免半成品。工具不执行 Git 提交、发布、外部写入或人工确认。

失败时返回非零并列出具体文档与字段。进行中工作缺少尚未到达的文档只提示，防止流程阻止自身建立。

## 监控与部署

CI 运行工具端到端测试和 `scripts/work check`。这是仓库结构边界，不需要独立部署；观察信号是 CI
失败类型、人工绕过频率和上下文包是否仍包含不足或无关信息。

## 迁移与兼容

旧 `product/`、`tasks/` 及专用脚本直接删除，不提供兼容命令。仍有效的 REQ-0001 完整迁入
FEATURE-001，旧任务的长期价值汇总进 MEMORY-001，细节继续由 Git 历史保留。旧 ID 不映射成新 ID，
避免让两个语义模型看似等价。

## 备选方案

1. 在旧 `product/` 和 `tasks/` 上继续扩展：迁移量小，但会永久保留双状态和双向同步问题。
2. 根目录下按文档类型分目录：按类型浏览直接，但会拆散单项上下文并增加人工定位成本。
3. 采用数据库或第三方 YAML/图工具：查询能力更强，但引入安装、迁移和本地/CI 一致性成本。

目录布局已由 DESIGN-003 与 DECISION-003 修订为“一个 WORK 一个独立目录”，附属文档在目录内按信息
层级排序；Markdown + JSON 子集 front matter、永久 ID 和标准库 CLI 等其余设计继续有效。跨工作查询
由 CLI 扫描元数据完成，不要求用物理类型目录换取可发现性。

## 风险与重审条件

代价是 CLI 需要显式维护状态语义，内容级正确性仍不能由 Schema 保证。若工作项达到数百个、查询性能
明显下降，或需要多人实时写入与细粒度审批，再评估 SQLite/服务化索引；若一种文档经常无法独立复用，
再考虑按 WORK 聚合存储。
