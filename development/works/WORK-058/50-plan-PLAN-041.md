# PLAN-041：判题引擎结构重切的分阶段实施计划

## 目标

按 [DESIGN-051](30-design-DESIGN-051.md) 把 `apps/judge-engine` 重切为三棵服务子树，使信任边界与部署
边界由编译器强制，并在同一轮内收敛配置耦合、执行接口时序协议、结论散布、节点职责混合与文档失真。

覆盖 [CHANGE-014](10-change-CHANGE-014.md) 的 REQ-001 至 REQ-012。

## 改动区域

- `apps/judge-engine/`：全模块目录结构、包划分、配置类型、执行后端接口、结论推导、节点能力与错误消息。
- `docs/engine.md`：按新结构重写。
- `docs/coding-standards/languages/go.md`：其中引用旧包路径的条目同步更新（不改变规则本身）。

不改动：`apps/server`、`apps/web`、`contracts/`、`deploy/`、`scripts/`、数据库、依赖版本。

## 阶段与顺序

顺序原则：**先纯移动与去重，再结构重排，再行为变更，最后接口重写与逻辑重组**。每个阶段一个提交、
独立可编译，且 WORK-050 固化的 CI 回归保持通过。

| 阶段 | 内容 | 任务 | 性质 |
|---|---|---|---|
| S1 | 抽出 `internal/hostexec`：本机执行协议、`Request`/`Result`/`Reason`、帧编解码；`Call` 移入 `hostexec/client`；删除 `container.Reason` 重复定义与字符串转换；`launcher` 的协议部分并入 `hostexec`，角色实现留在原处待 S2 搬运 | TASK-125 | 纯移动 + 去重，行为不变 |
| S2 | 目录重切为 `judge/`、`sandbox/`、`helperd/` 三棵子树，实现包下沉到各自 `internal/`；`cmd/*` 退化为参数解析；各服务新增 `Run` 入口与 `doc.go` | TASK-126 | 机械重排，行为不变 |
| S3 | 配置拆为三份服务配置 + `platform/config` 泛型 `Load`；配置、环境、身份三值分离；环境指纹改为显式输入结构并加基准测试；语言清单由注册表生成 | TASK-127 | **行为变更：指纹轮换** |
| S4 | `container.Container` 四阶段协议改为 `backend.Backend` 一次性 `Execute`；`workspace` 与 `backend` 分包；`pool` 回归纯容量管理；`trusted-host` 改名 `devhost` 并默认拒绝启动 | TASK-128 | 接口重写 |
| S5 | 执行结论提取为 `Conclude(Facts)` 纯函数；执行状态机改为显式转移表；补齐 `Facts → Reason` 表驱动测试 | TASK-129 | 逻辑重组 |
| S6 | `node` 拆为 registry / install / identity / probe；`probe` 复用既有 sandbox 客户端；部署清单校验改为覆盖性断言并移除硬编码；跨层预算启动断言 | TASK-130 | 职责拆分 + 校验增强 |
| S7 | 全模块错误消息统一英文；补齐各服务 `doc.go`；重写 `docs/engine.md`；同步 go 编码规范中的包路径引用 | TASK-131 | 收尾 |

S1–S2 完成后，CHANGE-014 的根因（信任边界不可见）即已消除；S3–S6 处理阅读成本与职责混合；S7 使
文档与实现重新一致。

## 并行与依赖

```text
S1 → S2 → S3 → S4 → S5 → S6 → S7
              ↘ S6 ↗
```

- S1 是全部后续阶段的前置：`hostexec` 不先归位，S2 的子树划分无法成立（`container` 仍需引用 helper 包）。
- S2 是 S3–S6 的前置：不先重排目录，后续新增的类型会落在最终会被移走的位置，产生二次搬运。
- S3 与 S6 之间存在弱依赖：S6 的 `probe` 返回值改为 `node.Environment` 依赖 S3 完成的三值分离。若
  S3 因指纹轮换需要等待部署窗口，S6 中不依赖 `probe` 的部分（部署清单校验、预算断言）可先行。
- S4 与 S5 不可互换：`Conclude` 的输入 `Facts` 中包含由 `Execute` 确认的回收事实。
- S7 必须最后做：错误消息与文档要描述最终结构。

单人顺序执行，无并行需求。

## 迁移与交付

- **交付方式**：分阶段合入 `main`，一个阶段一个提交，标题使用 Conventional Commits，正文用中文写
  为什么这么切、当时在哪两个方案间权衡。每个提交独立编译，不存在中间态不可构建的提交。
- **helper 配套**：S1 与 S2 涉及本机执行协议两端，客户端与服务端的改动必须在同一提交内完成，
  不得分提交合入，避免出现跨版本混用（CHANGE-014 REQ-015）。
- **指纹切换**：S3 合入后，节点以新指纹向控制面注册，按 `docs/architecture.md` §3.5 只会出现为
  `REGISTERED`。切换 `ACTIVE` 是人工动作，不由本工作的任何任务执行；切换前旧环境继续服务，切换后
  需要按既有节点协议重新安装测试数据并取得回执。
- **日志检索**：S7 改英文消息后，既有面向中文消息的检索表达式与告警规则需同批更新。该动作在本
  工作范围之外，S7 的产出中需列出受影响的表达式清单供运维更新。

## 风险

| 风险 | 阶段 | 缓解 |
|---|---|---|
| 大范围移动误改 FD 顺序、协议映射或释放时机；macOS 不可见 | S1、S2 | 逐包搬运，每包搬完即跑完整 CI；S1/S2 不允许同时修改逻辑 |
| 目录重排产生巨大 diff，复核无法逐行确认 | S2 | 只做移动与 import 路径修改，用 `git log --follow` 与重命名检测保证可追溯；任何逻辑修改拆到后续阶段 |
| 指纹轮换后遗漏 `ACTIVE` 切换 | S3 | 表现为无可用节点；VERIFY-059 AC-012 覆盖，且切换动作在 PLAN 中显式标为人工 |
| 一次性调用接口重写取消与产物交付时序 | S4 | 保留现有取消路径测试；AC-005 的四条路径 Linux 回归 |
| 提取 `Conclude` 丢失未被测试覆盖的分支 | S5 | 先以重构前行为为基准补齐表驱动测试，再搬运逻辑；测试先于重构合入 |
| 部署校验改造放宽了原有约束 | S6 | 覆盖性断言必须同时检查「声明未被校验」与「校验无声明」两个方向 |
| 错误消息改写时误改错误语义或包装链 | S7 | 只改字面量，不改 `%w` 包装结构与判定条件 |

## 回退

- **基线**：`a611be3`（WORK-049 的最终候选），加上本工作开始前的工作区快照。
- **粒度**：每阶段一个提交，按阶段逆序 `git revert`。只撤销本工作产生的 diff，不触碰 WORK-049、
  WORK-050 及 `apps/server` 的既有增量，不清理其他工作的工作区改动。
- **S3 的特殊性**：撤销 S3 会使环境指纹回到旧值。若届时已人工切换过 `ACTIVE`，需要按节点协议把
  `ACTIVE` 切回旧环境，并确认旧回执仍然可用。该动作是人工的，不能由撤销提交自动完成。
- **部署**：本工作不执行远端部署，无部署回退动作。
- **文档**：`docs/engine.md` 的旧版本随提交保留在 git 历史中，撤销 S7 即恢复。
