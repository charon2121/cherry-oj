# DECISION-035：判题引擎结构重切的边界机制与四项取舍

## 要决定什么

五件在实施前必须定下、且定错代价不对称的事：

1. 本次结构调整会轮换全部节点的环境指纹，是否接受。
2. 零隔离的 `trusted-host` 后端是保留、改造还是删除。
3. 全模块错误消息统一为中文还是英文。
4. 用什么机制守住信任边界：单 module 加 `internal/`，还是拆成多个 Go module。
5. `docs/engine.md` 是重写、降级为教学文档，还是废弃。

## 背景

见 [CHANGE-014](10-change-CHANGE-014.md) 与 [DESIGN-051](30-design-DESIGN-051.md)。

前四项中的第一、二、三、五项由用户在 2026-09-14 的评审对话中直接给出结论；第四项由本设计提出并
需要一并记录，因为它决定了整个目录方案是否成立。

## 候选方案

### 一、环境指纹轮换

| 候选 | 说明 | 代价 |
|---|---|---|
| A. 全部轮换 | 接受配置结构与二进制摘要变化带来的新指纹 | 需要一次显式的环境切换动作 |
| B. 保持兼容 | 让指纹输入保持与旧结构逐字节等价 | 必须冻结配置字段顺序，等于把本次要拆掉的耦合永久固化 |

### 二、零隔离后端

| 候选 | 说明 | 代价 |
|---|---|---|
| A. 保留并改名 `devhost`，默认拒绝启动 | 保留 macOS 上开发整条链路的能力 | 仍需维护一个 `Limits` 语义为假的实现 |
| B. 直接删除 | 结构最干净 | 非 Linux 平台无法端到端开发与调试 |
| C. 维持现状 | 无改动 | `trusted-host` 的命名与 `Spec.Limits` 的存在持续误导 |

### 三、错误消息语言

| 候选 | 说明 | 代价 |
|---|---|---|
| A. 统一中文 | 贴近现有运维语境 | judge 侧、`client`、`node` 全量改写 |
| B. 统一英文 | 与 Go 生态、依赖库错误链一致，检索无编码问题 | sandbox 侧、`pool`、`store` 全量改写；既有中文检索表达式失效 |
| C. 维持现状 | 无改动 | 同一条调用链的日志需要两套检索表达式 |

### 四、边界机制

| 候选 | 说明 | 代价 |
|---|---|---|
| A. 单 module + 服务子树 `internal/` | 编译期拒绝跨信任边界引用 | 同一 module 内仍可通过顶层 `internal/` 共享，需要设计上克制 |
| B. 多 Go module | 隔离更强，跨 module 需显式 require | helper 客户端与服务端可能出现版本偏斜；需要 go.work 与联动发版 |
| C. 架构 lint / 测试 | 改动最小 | 仍是「靠额外机制记住规则」，且不解决配置耦合与接口时序问题 |

### 五、`docs/engine.md`

| 候选 | 说明 | 代价 |
|---|---|---|
| A. 按新结构重写 | 文档重新成为可用的真源 | 739 行的重写工作量 |
| B. 降级为教学文档并标注 | 工作量小 | 一份不准确的长文继续以设计文档的形式存在 |
| C. 废弃 | 最省事 | 失去唯一一份讲清楚 judge / sandbox 分层理由的材料 |

## 决定

> 以下结论由用户于 2026-09-14 给出。决定类文档的终态 `approved` 由人在意图闸上一次覆盖，
> 智能体不代签；此处只记录结论内容与理由。

- **决定一：采用 1-A，接受全量轮换。** 按 `docs/architecture.md` §3.5 的节点协议，新指纹以
  `REGISTERED` 出现，由人显式切换 `ACTIVE`，旧回执保留。

  > 2026-09-15 更正：原文写「轮换集中在配置拆分那一个阶段发生」，不成立。判题可执行文件的摘要
  > 本来就参与环境身份，任何改动判题二进制的提交都会轮换指纹，本工作七个阶段都会。决定本身
  > 不受影响——接受轮换即可；实际做法是全部阶段合入后做一次环境切换。
- **决定二：采用 2-A，改名 `devhost` 并默认拒绝启动。** 需配置显式声明允许不安全后端才可启用。
- **决定三：采用 3-B，统一英文。** 切换时同步更新既有面向中文消息的日志检索表达式。
- **决定四：采用 4-A，单 module + 服务子树 `internal/`。**
- **决定五：采用 5-A，按新结构重写 `docs/engine.md`。**

## 理由

**决定一**：候选 B 要求指纹输入与旧结构逐字节等价，而旧结构的输入正是「对整个 `JudgeConfig` 做 JSON
序列化」——选 B 等于承诺永远不改配置结构的字段顺序，把 CHANGE-014 认定为问题的那条隐式耦合升格为
正式约束。既然指纹本就该在判题策略变化时轮换，一次性轮换并把输入改成显式字段集合，是把这件事
从「意外副作用」变成「可控动作」。

**决定二**：删除（B）会让非 Linux 平台失去端到端开发能力，而该能力在 WORK-049 的重构过程中被实际
使用过；维持现状（C）保留的是一个命名与语义不符的实现——`trusted-host` 听起来像一种可选的信任模式，
实际是「零隔离」，且它接受 `Limits` 却不强制执行。改名加默认拒绝启动，在保留能力的同时让误用需要
一次显式配置。

**决定三**：两种统一都优于分裂，选英文的额外理由是错误链——Go 标准库与 `golang.org/x/sys` 返回的
错误本身是英文，用 `%w` 包装后中英混排；统一英文后整条错误链语言一致。代价（sandbox 侧改写、旧
检索表达式失效）是一次性的。

**决定四**：多 module（B）提供的额外隔离，在本项目的交付方式下换不来收益——README 已明确 helper
客户端与服务端不得混用新旧版本、必须同批次交付，而多 module 正好制造版本偏斜的可能。`internal/`
规则由编译器强制，与多 module 在「能否引用」这个问题上给出同样的答案，却不引入发版耦合。架构 lint
（C）被排除的原因更根本：它把「规则」放在构建产物之外，新加入的人不跑 lint 就发现不了，而编译失败
是跑不掉的。

**决定五**：`engine.md` 是唯一一份解释「为什么 sandbox 不能懂判题」「为什么隔离与限量是两条正交的
轴」的材料，这些判断至今有效，废弃（C）会丢掉它们。降级（B）留下的是一份自称设计文档却描述着
`Container.Reset()`、容器复用这些已不存在结构的长文——这正是 CHANGE-014 列为问题的一条。重写的
工作量真实存在，但它是本次结构调整的产物之一，而不是额外负担。

## 影响与风险

- 决定一使部署侧需要一次人工环境切换；若遗漏，新节点停留在 `REGISTERED` 而不参与路由，表现为
  判题任务无可用节点。VERIFY-059 的 AC-012 覆盖该点。
- 决定三使既有日志检索表达式失效，需与切换同批更新，否则告警规则会静默失配。
- 决定四保留了「同一 module 内仍可通过顶层 `internal/` 共享」的口子。顶层 `internal/` 只允许放
  `contract`、`hostexec`、`platform` 三者，新增共享包需要在本决定上追加记录，否则它会重新成为
  绕过信任边界的通道。
- 决定五的重写若滞后于代码，会短暂出现文档与实现不一致；PLAN-041 将其安排在结构调整完成之后、
  验证之前。

## 重新考虑条件

- helper 与 sandbox 需要分别发版、不再同批次交付时，重新评估决定四。
- 非 Linux 平台不再用于开发整条链路时，重新评估决定二（可直接删除 `devhost`）。
- 出现第二种隔离后端（非 helper 链路）时，重新评估 DESIGN-051 的 `backend.Backend` 形态。
