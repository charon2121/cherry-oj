# MEMORY-044：判题引擎按边界重切的判断与教训

> 本文档在实施前先记录已经成立的判断；实施过程中的教训在各阶段完成后追加。

## 背景

WORK-049 已按命令执行顺序整理过 `apps/judge-engine` 的阅读主线与命名，但读者仍然反映"边界没做好、
读起来困难"。复查后确认：那一轮解决的是**沿着执行顺序读得下去**，没有解决**模块结构没有表达系统
真正的边界**。两者是不同的问题，后者不会因为前者做得更彻底而消失。

## 决定与原因

**根因判断：包树切错了维度。** 现有包树按"这段代码是什么类型"切（api / pool / runner / container /
helper / launcher / store）。这在 MVP 时期是对的——那时只有"在宿主里起一个子进程"，不存在别的维度。
随后模块长出三进程特权分离、节点控制面与部署清单校验，**包树没有跟着重切**，于是两条硬边界在包树
里不可见：root 的 helper 服务端 vs 非 root 的 sandbox（信任边界），以及三个独立部署的二进制（部署
边界）。所有具体症状——一个包装下协议两端、一份配置服务三个二进制、一个枚举定义两遍——都是这一条
的表现，不是各自独立的疏忽。

这条判断的可复用部分：**当一个模块的边界从"一条"变成"多条"时，包树必须重切一次。** 继续按原有
维度细分只会让每个包更小、更难找，而新出现的那条边界仍然没有任何东西守着。

**选 `internal/` 而不是多 module。** Go 的 `internal/` 规则由编译器强制，在"能不能引用"这个问题上
与多 module 给出同样的答案，但不引入版本偏斜。本项目的 helper 客户端与服务端必须同批次交付（不得
混用新旧版本），多 module 恰好制造出违反这一点的可能。详见 DECISION-035 决定四。

**边界要靠构建工具守，不靠文档和 lint。** 现有的"sandbox 不得链接特权 helper"写在 README 里，
"judge 不得进程内调用 sandbox"写在 `engine.md` 里，两条都没有任何机制执行，实际上第一条已经被违反
（`container` → `helper` → 整个特权服务端）。lint 也不够：它在构建产物之外，不跑就发现不了。编译
失败是跑不掉的。

## 尝试与教训

**已经踩到的坑：把配置结构当成指纹输入。** 环境指纹的输入是"对整个 `JudgeConfig` 做 JSON 序列化"，
而该结构没有 JSON 字段名标注，摘要实际依赖 Go 的字段名与声明顺序。后果是**给配置加任何一个字段都
会静默轮换全部节点的环境指纹**，而这条耦合没有写在任何文档或测试里。

可复用的教训：**凡是进入摘要、签名或对外身份的输入，必须是显式列举的字段集合，不能是"某个结构体
整体序列化"。** 结构体会因为无关原因增删字段，而摘要的语义是"这些事实变了"。两者的变化节奏不同，
绑在一起就会出现"改了个无关配置，全网节点身份变了"。加基准测试锚定摘要值，使这类变化必须显式
承认。

**S1 踩到的坑：批量正则改写误伤了字符串字面量，而本地测试看不见。** 把 `Version` 从包内
常量改成 `hostexec.Version` 时，正则同时命中了控制消息测试里的 JSON 线格式字面量，
`{"Version":1}` 变成 `{"hostexec.Version":1}`。本地 `gofmt`、`go vet`、`go test -race ./...`
三项全绿——因为那是 `_linux_test.go`，macOS 压根不编译它。CI 一跑就红。

两条可复用的教训：

1. **跨包改名不能只按标识符匹配，必须把字符串字面量单独核对一遍。** 线格式、日志检索表达式、
   SQL、路径模板里都可能出现和标识符同名的文本，而它们的含义完全不同。有效的做法是提取改动
   前后每个文件的字符串字面量集合做差集：本次这么做之后，剩下的唯一差异正好是预期要删的那五个
   终止原因取值，其余全部一致。
2. **有平台限定后缀的文件是本地验证的盲区。** `_linux.go` / `_linux_amd64.go` 在 macOS 上不参与
   编译，本地三件套全绿不代表它们被检查过。改动涉及这些文件时，本地就要用
   `golang:<version>-bookworm` 容器跑一遍 Linux 测试，不要把它留给 CI。amd64 可以用
   `--platform linux/amd64` 模拟，但 QEMU 不支持部分系统调用（`files_linux_test.go` 的
   `mknod` 用例会报 `function not implemented`）——判断某个失败是不是自己引入的，
   用同样的模拟环境跑一遍基线做对照，这一步很便宜。

**S2 踩到的坑：新建目录撞上了为文件写的忽略规则。** `.dockerignore` 里的 `judge` 与 `sandbox`
原本用于排除同名的构建产物二进制。重切目录后这两个名字成了服务源码目录，忽略规则照样命中，
整棵源码树被挡在 Docker 构建上下文外——而本地的 `go build`、`go vet`、`go test` 全都不经过
构建上下文，三件套全绿也发现不了，只有 CI 的镜像构建会炸。

可复用的教训：**新建目录时，先检查它的名字是否命中既有的忽略规则**（`.gitignore`、
`.dockerignore`、打包与部署的排除列表）。这类规则多半是为文件写的，对目录同样生效，而且
失败点往往落在本地默认不跑的那条链路上。相应地，改动涉及容器镜像时，本地就要跑一遍
`docker compose build` 与冒烟，不要留给 CI——这次本地复现只花了两分钟。

**S3 踩到的坑：把一个刻意的约束误读成了不一致。** 审查时发现「节点只向控制面声明 cpp，而语言
注册表有 cpp/python/java」，判定为两处事实不同步并动手「修复」。实际上整条业务链路端到端只支持
cpp——judging-service 三处把 languageId 限死为 cpp，控制面每次只 provision 一种语言，而节点注册
的兼容性检查要求语言集合逐条精确匹配。多声明两种语言的直接后果是新环境永远无法建立。

可复用的教训：**看到「两处对不上」时，先确认哪一处是约束、哪一处是余量，不要默认「更全的那个
才对」。** 判断依据不在本模块内部——它在消费方。跨服务的声明类字段（能力、版本、支持列表）
改动前必须去读消费方怎么校验它；本模块的测试全绿并不能说明什么，因为约束根本不在这一侧。
相应地，这类字段上值得留一句「这不是遗漏，理由是……」，否则下一个审查的人会做出和我一样的判断。

**S4 的一次偶发，以及怎么对待它。** CI 的业务闭环在 `business.calibrate` 后失败，
但判题相关步骤全部通过、沙箱侧资源清理确认干净，失败的是一次不经过判题引擎的业务请求
（设置题目可见性）返回 500，耗时远高于同批其他请求。同一 commit 整条重跑后全绿。

判别方法值得记住：**先看失败点在不在自己改动的因果链上**。这次的判据是三条并行证据——
判题步骤全过、失败请求不经过本模块、资源清理确认无残留；三条都指向改动之外，重跑才是合理的
判别手段，而不是遇红就重跑。反过来，**重跑转绿不等于问题消失**：偶发不记录就会被一次次
「再跑一遍」养成常态，最后没人知道它从什么时候开始存在。证据已留在对应 run 的产物里。

**S5 踩到的坑：把判断提成纯函数之后，误以为整段都不再依赖顺序。** 重排 `finish` 时把
「解除输入阻塞」挪到了「读取请求是否已取消」之前。而解除输入阻塞的回调在启动冒烟里恰好会
取消这次执行自己的上下文，于是每次正常执行都被判成已取消。

可复用的教训：**从事实推结论可以不依赖顺序，但采集事实本身有顺序要求。** 一个字段是不是
「事实」，要看它会不会被后续动作改写——`ctx.Err()` 就是典型：它在收尾过程中会变，必须在
动手收尾之前读下来。做这类提取时，先把「哪些读取必须发生在哪些动作之前」列出来，
再动手重排。

**这次还暴露了一个诊断缺陷。** 失败在 CI 上稳定复现，但消息只有「socket 没就绪」——真正的
原因留在服务自己的输出里，外部拿不到；本地又因为需要 systemd 无法复现真实链路。于是花了
三轮 CI 在猜。**当一个失败模式藏起自己的原因时，先修这个失败模式，再去修缺陷**：补上诊断后
第一轮就拿到了「冒烟失败: reason=cancelled」，直接定位。

**S6 的一条判断：校验目标不能交给被校验的一方来配置。** 原完成标准写的是「宿主安装路径不再以
字面量出现在代码里」，按字面做就是把它变成配置项。但这一项是**校验目标**而不是部署参数——
交给配置，等于让被校验的那一侧决定校验指向哪里，和「让清单自己声明有哪些项要核对」是同一类错误。
最后收进 `deployment_spec.go` 的具名常量，与必需文件集、必需 cgroup 节点放在一起，
整个文件只回答「一个合格的原生部署长什么样」。**标准本身被改写并写明了理由**，而不是绕过去。

同一阶段的另一条：**「数量对得上」不是覆盖。** 部署校验原先用 `len(manifest.Limits) != 24` 代替逐项核对，
于是「少一条要求」和「多一条从不核对的声明」会互相抵消。改成双向覆盖——要求的每一项必须在清单里，
清单里的每一项也必须是要求的——并要求报错点出**是哪一项**：只说「部署不合格」等于没说。

**S7 的一条方法：批量改写要让误伤在原理上不可能，而不是靠事后检查。** S1 那次正则改坏 backtick 里
JSON 字面量的教训，在这次 238 处错误消息改写上换了做法：用 `go/ast` 只替换
`fmt.Errorf` / `errors.New` **第一个实参**的字面量（含 `"..." + "..."` 跨行拼接），
替换前比对该字节区间与解析出的字面量是否一致，替换后拒绝仍含汉字的结果。
字符串比较、JSON 夹具、结构体标签**在语法层面就够不到**，不需要再去「核对一遍应该没事」。

配套的一条：**`go vet` 的盲区要用独立不变量补。** 它能查出格式动词与实参类型不匹配，
查不出 `%q` 被写成 `%s` 这类同类型替换。改写前后逐条比对动词序列是独立于 `vet` 的检查，
238 处全等——这种「免费且更强」的不变量值得主动找。

**实施前列出的两条待验证判断，结论如下**：

- 「一次性调用能否真的消掉守护顺序的状态字段」——**成立**。四阶段接口的时序原先只写在运行时错误里
  （「只能执行一次」「工作区不再接受输入」），两个实现各维护一组状态字段。改成
  `Execute(ctx, Job, sink)` 之后，「只能执行一次」由「不存在可复用对象」保证，那些字段随之消失；
  复杂度没有搬进 `Job`——它只是把原本分散在四次调用里的参数一次性声明出来。
- 「纯函数结论与重构前是否逐条一致」——**成立**，但保证它的是先补的表驱动测试，不是重构本身。
  过程中还额外暴露出转移表缺了 `starting → cleanup-failed` 一条，是显式表把它逼出来的；
  写成 if-else 分支的话，这条缺失会表现成「走到某个没人想过的分支」。

## 已知问题

- `docs/engine.md` 长期描述着已不存在的结构（容器复用、`Container.Reset()`、cgroup 与 container 互不
  依赖），并且仍以设计真源的形式存在。**文档失真本身就是可读性问题的一部分**：照着它读会走错路，
  而读者要到读完代码才会发现文档不对。本工作已重写它，但这类失真会再次发生，需要在流程上让结构变更
  与文档更新落在同一轮。
  S7 补了一条可操作的做法：**重写完之后照着新文档实走一遍源码**。这一遍当场抓出两处文档与实现
  不符（`/run` 的内部顺序写反、`SO_PEERCRED` 写成了「不靠文件权限」而实际是双重约束），
  而这两处都是「写的时候自以为记得」的地方——不实走就发现不了。
  同一遍还发现 `apps/judge-engine/README.md` 与 `helperd/internal/helper/README.md`
  的链接与类型名全部指向旧结构：**结构变更要把「阅读入口」类文档一起算进影响面**，
  它们比设计文档更容易被漏掉，因为没人会在改代码时想起它们。
- 顶层 `internal/` 保留了"三个服务都能引用"的口子（`contract`、`hostexec`、`platform`）。它是必要的，
  但也是绕过信任边界的潜在通道。新增顶层共享包必须在 DECISION-035 上追加记录。
- ~~节点向控制面声明的语言集合与本地 `language` 注册表长期不一致，本工作顺带修正。~~
  **这条记错了，S3 已推翻。** 节点只声明 cpp 不是不一致，而是被消费方约束死的：
  judging-service 三处把 languageId 限死为 cpp，控制面每次只 provision 一种语言，
  节点兼容性检查要求语言集合逐条精确匹配——多声明一种语言的后果是**没有任何环境能匹配上这个节点**。
  当时按「更全的那个才对」动手改，直接把 `business.new-environment` 打红。
  代码里已留下「这不是遗漏，理由是……」的注释。保留这条划掉的原文，是因为**判断错误的过程本身
  比结论更值得记住**：它正是上面那条「先确认哪一处是约束、哪一处是余量」的反例来源。

## 重新考虑条件

- helper 与 sandbox 需要分别发版、不再同批次交付时，重新评估"单 module + `internal/`"。
- 出现第二种隔离后端（非 helper 链路）时，重新评估 `backend.Backend` 的一次性调用形态。
- 非 Linux 平台不再用于开发整条链路时，`devhost` 可以直接删除。
- 若本次重切之后仍然出现"边界靠人记"的新症状，说明"按边界切"这条判断本身不完整，需要重新找根因，
  而不是继续细分包。
