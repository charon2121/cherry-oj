# CHANGE-014：按信任与部署边界重切判题引擎模块结构

## 为什么做

学生交上代码之后，真正把代码跑起来、给出「对还是错」的那部分叫判题引擎。它其实是三个各自独立
运行的程序：一个负责安排判题、一个负责接收执行请求、还有一个负责搭建隔离环境。第三个需要很高的
系统权限，因为只有它能在操作系统层面把用户代码关进笼子；另外两个刻意不给权限，万一被攻破，损失
也有限。

问题是：这三个程序的代码现在混在同一批文件夹里，谁可以用谁的东西，没有任何机制拦着，全靠写代码
的人自己记住。不需要权限的那个程序，实际上已经把需要权限的那部分代码整个装进了自己的安装包里。
这不等于现在就有漏洞，但它意味着「权限最小化」这件事没有任何保障，只是碰巧还没出事。

同一批文件夹还带来第二个麻烦：三个程序共用一份配置说明。其中一个程序的配置写错，另外两个也会
拒绝启动——哪怕那一项和它们毫无关系。

第三个麻烦是给人看的。想读懂这部分代码的人，现在必须先读一份单独的说明文档才能知道谁负责什么，
而那份文档描述的结构已经和实际代码对不上了。照着它读会走错路。

本次整理要让「谁能碰什么」由构建工具自动拦截，而不是靠人记；让三个程序各管各的配置；并让说明
文档重新和代码一致。

## 当前状态

`apps/judge-engine` 已经过 [CHANGE-013](../WORK-049/10-change-CHANGE-013.md) 的阅读性重构，
执行主线、命名与字面量语义已经整理过，CI 回归已由 WORK-050 固化。本次工作建立在该基线之上。

CHANGE-013 的 REQ-007 明确把「移除特权 helper、合并进程、改变权限模型」这类结构性变化排除在外，
要求另行提出架构决策。本工作就是那个后续架构决策：不改变权限模型本身，而是让模块结构如实表达
它，并把同一批问题里属于结构的部分一次处理完。

本轮只编写文档，尚未实施。文档通过不由智能体代签；创建本文档不构成实施授权。

## 当前问题

已定位的结构性断点（符号与位置见 [DESIGN-051](30-design-DESIGN-051.md)）：

- `internal/sandbox/helper` 单包同时实现本机执行协议的客户端与特权服务端，并混入配置加载、rootfs
  信任校验、启动恢复与安装探测。非特权的 `cmd/sandbox` 经 `container` 传递依赖该包，在源码层面
  可直接调用特权入口，构建工具不拦截。
- `internal/config` 用一个 `Config` 承载三个二进制的配置，`Validate` 一次校验全部：judge 会因
  sandbox 段配错而拒绝启动，sandbox 会因 judge 段配错而拒绝启动。
- `config.JudgeConfig` 同时承担「加载到的配置」「探测到的环境」「注册得到的身份」三种角色，由
  `cmd/judge` 在启动过程中回填。读代码时无法判断某字段当下来自哪一种来源。
- 环境指纹的输入是对 `JudgeConfig` 整体做 JSON 序列化的结果，而该结构没有 JSON 字段名标注，摘要
  实际依赖 Go 字段名与声明顺序。新增任何配置字段都会静默轮换全部节点指纹，该耦合未记录在任何
  文档或测试中。
- 终止原因枚举在 `helper` 与 `container` 两处逐字重复定义，跨包以字符串转换桥接，新增取值不会
  产生编译期错误。
- `container.Container` 用运行时错误表达四阶段时序协议（放输入 → 启动一次 → 等待 → 取产物 → 关闭），
  两个实现各自维护一组状态字段来守护该协议。
- 单次执行的结论散布在 `supervise` 与 `finish` 两处对同一批字段的顺序敏感读写，其中包含撤销先前
  结论的分支，缺少可单独测试的「事实 → 结论」表达。
- `internal/judge/node` 合并了控制面注册、安装端点、安装事务、环境探测与部署清单校验五件事，并
  自建了模块内第三个 HTTP 客户端；部署清单校验把宿主路径、端点地址、限额条目数量硬编码进 Go。
- 错误消息语言在包之间不一致：sandbox 侧为中文，judge 侧为英文，`internal/config` 包内部即分裂。
- `docs/engine.md` 描述的结构（容器复用、`Container.Reset()`、cgroup 与 container 互不依赖）与当前
  实现不符，仍以设计真源的形式存在。

以上是结构审查事实，不能据此推导现有运行行为不正确；WORK-049 与 WORK-050 已确认当前行为通过回归。

## 目标状态

- REQ-001：三个二进制的代码分别位于各自的目录子树，跨越信任边界的引用由 Go 的 `internal` 可见性
  规则在编译期拒绝；非特权服务无法引用特权服务的实现包。
- REQ-002：每个服务拥有自己的配置类型、默认值与校验；任一服务不因其他服务的配置项取值而拒绝启动。
  配置加载的通用机制与具体配置字段分离。
- REQ-003：环境指纹的输入是显式列举的字段集合，新增服务配置项不再改变指纹；指纹计算有固定输入的
  基准测试锚定。
- REQ-004：终止原因只有一处定义，跨包直接复用而非字符串转换；每个取值在结论映射处都有对应分支，
  由测试保证覆盖完整。
- REQ-005：单次执行的对外接口表达为一次性调用，调用方无法构造「执行第二次」的状态；产物在调用
  返回时即可安全发布，容量管理不再承担产物回滚。
- REQ-006：单次执行的结论由一个不做输入输出、不改写状态的函数从已收集的事实推导得出，可在非 Linux
  平台以表驱动方式测试；资源回收的顺序仍保持命令式表达。
- REQ-007：节点相关能力按注册、安装、身份、探测拆分；环境探测复用既有 sandbox 客户端；部署清单
  校验只比对「清单声明与实际是否一致」，不在代码中硬编码清单应有的内容与条目数量。
- REQ-008：跨层预算的依赖关系（HTTP 写期限、会话期限、墙钟与收尾期限、judge 侧调用期限）在启动
  校验中断言，不满足时拒绝启动。
- REQ-009：全模块错误消息统一为英文。
- REQ-010：每个服务目录有说明其职责与引用边界的包文档；`docs/engine.md` 按新结构重写，不再描述
  已不存在的结构。
- REQ-011：`trusted-host` 后端更名为 `devhost`，并在未显式开启不安全后端时拒绝启动。
- REQ-012：本次结构调整导致的环境指纹轮换按既有节点协议处理：新指纹以 `REGISTERED` 出现，由人
  显式切换 `ACTIVE`，不静默替换。

## 不变条件

- REQ-013：保持对外 HTTP 契约、判题结论、状态与判定映射、零值与缺省语义、协议字节、资源预算、
  隔离与回收保证不变。结构调整不夹带已知缺陷修复。
- REQ-014：保持 judge 与 sandbox 的职责划分与权限模型：sandbox 不理解判题，特权仅由 helper 持有，
  不合并进程、不改用其他执行器、不降低隔离强度。
- REQ-015：保持单 Go module 与配套交付：helper 客户端与服务端仍按同一构建批次交付，不引入跨 module
  版本偏斜。
- REQ-016：不改动 Java 服务、Web 前端、`contracts/` 下的跨语言 JSON Schema、数据库结构与依赖版本。

## 影响范围

涉及 `apps/judge-engine` 全模块的目录结构、包划分、配置类型、执行后端接口、结论推导、节点能力拆分
与错误消息，及其对应测试；涉及 `docs/engine.md` 重写。

不涉及 Java 服务、Web 前端、`contracts/`、数据库与部署脚本的逻辑变化。部署侧只有一次环境指纹切换
动作，按既有节点协议执行。

## 风险

大范围移动文件可能误改 FD 顺序、协议映射、取消路径或资源释放时机，而这些错误在 macOS 上不可见。
把四阶段接口改成一次性调用会重写执行后端的调用面，取消与产物交付的时序是最容易出错的部分。
把结论逻辑提取为纯函数时，可能在搬运过程中丢失某个当前生效但未被测试覆盖的分支。
配置拆分会改变环境指纹，若与节点协议配合不当，会让已部署测试数据的回执失效而无人察觉。
错误消息改语言会使既有日志检索表达式失效。
按信任边界重切目录若只做机械移动而不收敛职责，会得到同样难读的代码和一次无收益的大规模 diff。

## 回归检查

- AC-001：构造一个从非特权服务子树引用特权服务实现包的改动，`go build` 必须失败；对 judge 引用
  sandbox 实现包同样失败。给出实际命令与报错原文。
- AC-002：分别用「仅 judge 段有效」与「仅 sandbox 段有效」的配置启动对应服务，两者都成功；对方
  服务的配置项取值不影响本服务启动。给出实际配置与启动记录。
- AC-003：环境指纹基准测试在固定输入下给出固定摘要；向服务配置新增一个字段后该测试仍通过，向
  指纹输入结构新增字段后该测试失败并提示需要更新基准。
- AC-004：终止原因的每个取值在结论映射处都有分支，由测试断言覆盖完整；新增一个取值而不更新映射
  时测试失败。
- AC-005：执行后端的一次性调用在正常完成、墙钟超时、请求取消、部分启动失败四条路径上，均在返回
  时完成回收；对应 Linux 回归无残留进程、挂载、cgroup 或临时文件。
- AC-006：结论推导的表驱动测试在非 Linux 平台通过，覆盖 WORK-049 已确认的正常、超时、取消、OOM
  与 init 失联路径，结论与重构前一致。
- AC-007：部署清单校验对「清单声明与实际不一致」「清单缺少应有条目」两类情况分别报错并指出是哪
  一条；代码中不再出现宿主路径、端点地址与条目数量的字面量。
- AC-008：跨层预算断言在人为配置为不满足关系时拒绝启动并说明是哪两项冲突。
- AC-009：全模块错误消息为英文，由检查给出证据；沙箱与判题两侧的运行日志可用同一套检索表达式。
- AC-010：与本工作开始前的基线比较，对外 HTTP 契约、判题结论、协议字节与安全不变量保持不变；
  WORK-050 固化的 CI 回归全部通过。发现的既有缺陷独立记录，不借本工作顺手更改。
- AC-011：按重写后的 `docs/engine.md` 与各服务包文档实走一次源码，不出现文档描述与实现不符之处。
- AC-012：环境指纹轮换在节点协议上表现为新增 `REGISTERED` 环境，未静默替换 `ACTIVE`；旧回执按既有
  规则保留。
