# DECISION-026：Linux 沙箱隔离与资源计量硬化

## 要决定什么

首轮 Linux 执行后端与权限分配、计量口径和 Ubuntu 服务部署形态。

## 背景

host 后端零隔离且 wait4 峰值受历史任务影响。用户要求承接 cgroup/namespace 硬化，并将提供 Ubuntu 服务器。

## 候选方案

- 原生 namespace + cgroup v2 + 最小特权 helper：沿用现有架构、学习路径直接；需要审查特权启动代码。
- 通过成熟 OCI/隔离执行器实现：复用启动隔离能力，需固定版本、审查配置和适配资源生命周期。
- 虚拟机级隔离：隔离边界更强，首轮部署和性能成本更高。

## 决定

提议采用第一种，Ubuntu 原生 systemd 托管，编译与执行均隔离；用户程序无特权，HTTP 服务不直接持有宿主 root。目标服务器能力探测为首个任务，具体 helper 启动机制、userns 和 seccomp 支持矩阵在编码前冻结。成熟执行器保留作为探测结果不支持可靠自研时的重审选项。意图闸已由用户签署，签署范围为 TASK-093 只读探测与实施边界冻结；具体实现边界见 DESIGN-042 的冻结结果，后续 TASK 保持 todo，不能据此直接安装或编码。

## 理由

保持 Go 层编排和 sandbox 单一职责，用每次独立 cgroup 解决资源计量根因，优先把现有 C++ 闭环做可靠。避免先发布只加 memory.max、没有文件与权限隔离的半成品。

## 影响与风险

共享内核不等于虚拟机安全边界；特权 helper 与文件交付路径必须独立复核。Ubuntu 原生服务与现有 Docker 开发模式分开交付；无能力时停服而不是退回 host。内存统计口径会变化，需重新标定。

## 重新考虑条件

无法建立无竞态启动和可靠清理、目标机缺少控制器或部署权限、需要多租户强隔离或更多语言兼容时重新决策。
