# ISSUE-002：统一登录空闲过期配置并修复提前掉线

## 问题现象

用户反馈在较短时间没有操作网站后登录状态消失，需要重新输入密码。当前部署入口没有一个明确的
“登录空闲过期时间”配置，无法仅凭配置判断或调整实际退出时点。

## 复现方式

1. 使用管理员预置账号登录 Web。
2. 不发起经过 Gateway 的认证 API 请求，等待当前实际空闲期限。
3. 刷新页面或进入需要认证的页面，触发 `GET /api/auth/session`。
4. 分别只修改 Gateway 的 `spring.session.timeout` 或 user-service 的 session idle 配置后重启，再重复。

用户报告的精确等待时长尚未以固定时钟复现；静态检查已经能稳定复现配置分散：Gateway 的
`@EnableRedisWebSession` 固定为 1800 秒，而 user-service 独立使用 30 分钟登录授权期限。

## 实际结果

默认情况下两层都试图使用 30 分钟，但 Gateway 注解直接写死 1800 秒，`spring.session.timeout` 不能
成为可信的唯一入口；user-service 又独立计算数据库授权的 `idle_expires_at`。只调整其中一层时，用户
仍会在较短的另一层到期后退出。另有 120 秒内部 JWT，会在 Gateway 后台交换，不应成为用户登录期限。

## 预期结果

部署者通过两个整数秒数和一个布尔配置控制 IDLE、绝对上限及认证操作是否刷新 IDLE。两层采用相同
配置，生效前后均有启动和时间边界证据；120 秒 JWT 自动刷新，不要求用户重新输入密码。主动撤销仍按
WORK-013 已确认模型执行。

## 影响与条件

影响使用 Redis Session 的 Gateway 和保存登录授权的 user-service。静态页面内没有发出认证请求的
滚动、停留或表单编辑不算活动；登录、Session 查询及后续受保护 API 请求会被识别为认证活动，是否
续期由刷新开关决定。问题不涉及 MySQL 表结构、密码摘要、资源服务 JWT 验签或用户角色。

## 原因

已确认的结构原因是同一用户语义由两个独立配置/硬编码实现，且没有自动化测试证明它们保持一致。
用户报告是否还包含“120 秒 token 交换失败”或本地 Redis 配置差异，需在实施时用短时固定配置与真实
Redis 回归进一步确认，不能在文档阶段臆断。

## 修复方向

采用两个秒数配置和一个布尔配置：IDLE 秒数、绝对上限秒数、认证操作是否刷新 IDLE。user-service
继续负责登录授权真值，Gateway 使用相同配置管理 Redis WebSession。移除分散的业务硬编码，并让启动
校验拒绝越界或不一致期限。测试分别推进 Redis Session、登录授权和 JWT 时间。

## 回归检查

- AC-001：未设置配置时，两层 IDLE 为 1800 秒、绝对上限为 43200 秒、认证操作刷新 IDLE，现有行为
  兼容。
- AC-002：设置 IDLE 7200 秒、绝对上限 86400 秒时，Gateway 已认证 Session 与 user-service 登录授权
  使用对应值，不再残留决定用户行为的 1800/43200 硬编码。
- AC-003：刷新开关为 `true` 时，期限到达前的认证请求把 IDLE 截止时间更新为“当前时间 + IDLE 秒数”，
  但不超过绝对截止时间；超过期限后的下一请求返回未认证并清理本地状态。
- AC-004：固定时钟跨过 120 秒 JWT 到期点但未跨过空闲期限时，Gateway 自动交换 token 且用户仍登录。
- AC-005：刷新开关为 `false` 时，认证操作不改变登录时生成的 IDLE 截止时间，JWT 仍可透明刷新。
- AC-006：越界/非整数秒数、非布尔开关，以及 IDLE 大于绝对上限时启动失败并指出配置名。
- AC-007：退出、改密、重置、停用、绝对到期与敏感字段负向测试保持通过。
