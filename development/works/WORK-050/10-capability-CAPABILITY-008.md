# CAPABILITY-008：将沙箱已验收回归固化为重构 CI

## 为什么需要

judge-engine 即将重构。现在代码测试会自动执行，但最关键的隔离、资源限制、故障回收和真实判题主要靠手工验证。需要把已经通过的场景变成每次改动都能重复执行的检查，及时发现重构造成的行为变化。

## 使用者

judge-engine 开发者、代码审查者与验收负责人。

## 能力

- REQ-001：建立已验收场景与自动检查的一一对应清单，显示每项实际执行、失败或缺失，不能把跳过算通过。
- REQ-002：在真实 Linux 内核上自动验证编译和运行隔离、整组计量、资源限制、并发、连续 1000 次回收以及故障恢复。
- REQ-003：自动验证原生安装、权限和资源配置、缺文件拒绝、服务崩溃、卸载及受控恢复；整机重启仍留置。
- REQ-004：使用独立后端、数据和新节点身份，自动完成部署、校准、发布、自定义运行、正式提交和代码回看。
- REQ-005：保留来源提交、测试版本、环境、逐项结果及清理证据；重构前后运行同一组断言，失败阻止认定重构完成。
- REQ-006：自动检查只操作一次性测试环境，不连接现有测试服务器、本机 IDEA、用户数据库或真实账号。

## 接入方式

沿用 GitHub Actions，在 pull_request、push main 和手动触发时运行。保留已有基础 CI，新增 Linux 隔离、原生部署及真实业务检查；提供仓库内同一入口用于排错。先在当前代码上跑通自动基线，再开始 WORK-049 的行为重构。

## 输入与输出

输入是精确提交、锁定工具链与仓库内合成用例；输出是逐项报告、原始测试日志、资源回收快照和稳定的汇总检查。身份、问题版本和部署回执每轮生成，不能复用 WORK-048 的业务 ID、校准或未跟踪 ZIP。

## 限制与失败

当前只计划自动验证 Linux/amd64；实际发行版、内核、LSM 和权限必须记录。能力不足、用例缺失、执行超时、清理失败都不能显示通过。其他平台仍按矩阵标待验证或不支持。测试通过不能证明所有潜在漏洞都不存在，不能代替独立代码复核与人工验收。

## 质量要求

- AC-001：每个 WORK-048 已验收场景都有清单 ID、现有入口、自动入口及断言，必需场景零静默跳过；独立复核和机器重启明确分类。
- AC-002：真实 Linux 隔离、资源、启动/文件边界、1000 次、并发与故障套件在自动运行中通过，保留最终资源快照。
- AC-003：一次性机器内的原生部署、七项权限及删减对照、24 项限额、缺文件拒绝、三服务崩溃、卸载恢复通过；当前服务器不被修改。
- AC-004：真实五服务与消息链连接本轮 Linux 节点，自定义全部状态、正式 AC/WA、版本/身份/数据/校准与代码回看通过；页面断言不模拟后端结果。
- AC-005：同一提交的基础、Linux、原生及业务检查均成功才汇总通过；通过可控失败、缺报告和取消场景证明汇总与清理不会假绿。
- AC-006：当前基线至少连续两次完整自动执行通过，交付 WORK-049 的精确提交与报告链接；后续重构候选须再次完整通过，不能沿用旧报告。

## 升级与迁移

先交付测试资产和基线，不改执行策略或业务实现。测试符号因重构移动时允许更新适配入口，预期行为和覆盖数量必须保持并可复核。真实缺陷另立精确修复任务，不通过放宽阈值或删除断言掩盖。

## 不做什么

不启动 WORK-049 源码重构；不恢复 TASK-108；不自动部署到现有服务器或切换其 ACTIVE；不扩展 arm64/其他发行版实现；不复制旧节点指纹或校准；不自动提交、推送、设置分支保护或签署人工闸。
