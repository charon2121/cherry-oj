# DECISION-028：CI 执行环境与覆盖边界

## 要决定什么

把已通过的沙箱与真实业务回归放到什么环境运行，以及哪些结果可作为重构通过条件。

## 背景

当前六项 CI 不包含完整特权隔离与真实业务，现有测试服务器已承担当前可用节点，不能用自动压力/卸载测试干扰它。

## 候选方案

1. 每个特权/业务 job 使用 GitHub 一次性 Ubuntu VM：无需用户服务器凭据，环境干净；实际内核可能不同，须探测并记录。
2. 现有服务器安装持久 runner：更接近历史环境，但固定资源冲突和公共仓库来稿风险明显。
3. 云端每次创建指定内核 VM：可固定历史条件，需要额外云资源、权限与生命周期管理。

## 决定

提议方案1，当前等待用户审核与意图闸。普通检查、真实内核、原生部署和真实业务全部纳入必需汇总，缺能力/缺用例/跳过/清理失败不通过。现有服务器及 IDEA 不进入CI；机器重启继续留置，独立审查不由脚本伪造。

## 理由

尽量复用现有 GitHub Actions、Go/Python/Playwright 和部署工具，将重构风险与当前用户环境分开，保持实际内核验证与接口结果验证同时存在。

## 影响与风险

托管 Ubuntu24.04 不等于原服务器实际6.8内核；需增加真实平台记录。全部业务自动化要准备独立Java/数据库/消息链，不能直接复用旧手工ID和已登录账号。运行时间预计高于当前CI，以首轮数据确认。

## 重新考虑条件

托管VM行为探测不满足要求，或资源/时长超出可接受预算时，提出独立临时VM方案供用户决定，不静默降级或改现有服务器。
