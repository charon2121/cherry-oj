# MEMORY-001：重建统一开发文档系统

## 背景

2026-08-24 以前，仓库使用 `product/` 管理 REQ/产品决定/版本验收，使用 `tasks/` 管理可认领的研发
任务。该模型在早期完成了任务编号、依赖图、验收证据和产品/技术验收分离，但随着协作范围扩大，
两套真源、状态机和反向引用成为主要复杂度。

## 决定与原因

根据用户提供的智能体协作开发规范，项目改为 `docs/` 与 `development/` 两层。所有具体工程工作以
WORK 为入口；产品定义与任务仍分层，但只作为同一工作项的不同文档存在。工具只负责确定性结构和
状态检查，智能体负责语义，人负责关键判断。

## 尝试与教训

- 旧系统中“所有 TASK 完成”不等于“产品已接受”是正确经验；新系统通过 implemented/verified/
  released/confirmed 继续保留，而不是合并成一个 done。
- 双向引用看似严格，实际增加漂移面；新系统只保存有方向的关系，反向关系由 `trace` 计算。
- 进行中工作天然会缺少后续产物。结构检查应在 todo/draft 阶段提示，在 ready 以后才阻断，否则流程
  工具会妨碍流程本身逐步建立。
- 编号不能按当前文件最大值复用，因此单独保存单调 `index.json`，归档和删除都不回退计数器。

旧 TASK-0001 至 TASK-0015 记录了 sandbox 上传限制、TTL、cgroup、容器 PATH、清理可观测性、PE diff、
架构/契约 v2、Java/Web 初始化与工具链、前端依赖和 CI、旧产品工作流等已完成工作。详细执行证据保留
在 Git 历史；当前全局结论已经分别进入代码、contracts、CLAUDE 和应用工具链文档。

## 已知问题

新工具当前只做结构和有限状态语义校验，不能判断需求是否真的清楚、方案是否擅自改变产品行为、测试
是否充分或路径声明是否与实际 Git diff 一致。这些仍需要复核智能体或人工检查。CLI 在单工作区串行
分配 ID，不解决多人离线同时创建相同编号后的 Git 冲突。

## 重新考虑条件

当受管理文档达到数百份、编号冲突频繁、需要实时多人审批或按代码变更自动执法路径范围时，重新评估
持久化索引、服务化协调或专门的语义审查工具。除非生命周期边界变化，不恢复产品/任务双中心。
