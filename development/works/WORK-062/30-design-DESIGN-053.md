# DESIGN-053：按任务类型组织可选开发流程与简短工作说明

## 背景

上游目标、重要代价与验收以 [WORK-062](./00-work.md) 为准。
用户希望主动选择何时使用文档流程，并保留此前讨论的五种工作语义；每个工作的人类入口应简短、通俗，
不能将代码审核负担替换成长篇文档审核负担。

已重读现行九章规范，并对照精简改动前的信息分层、分类流程、文档体系和责任边界。
保留定义、体验、设计、选择、执行、证据、记忆的职责；本次简化自动触发和管理机制。

## 目标与限制

仅在当前仓库创建 `.agents/skills/dev-work/`，明确调用名为 `$dev-work`。
未调用时不要求 WORK、TASK、两轮文档审核或工作闸；通用授权、架构边界、契约、编码、测试及提交规则仍适用。
涉及重大产品取舍或不可逆动作时，仍须按实际任务取得必要确认，不能把关闭文档流程解释为无限授权。

启用后的人工入口只有简短工作说明。技术材料可以较长，但默认由 Agent 阅读和维护。
人工确认覆盖说明中明确展示的目标、范围、解决思路与重要代价，不表示逐份批准全部技术附件。

## 整体方案

### 启动与范围

`SKILL.md` 只写共同约束、类型路由、人工说明写法和交付办法。五类流程与材料规则使用按需引用，
不在 skill 入口复制九章规范，也不在普通开发请求中加载整套规则。
`agents/openai.yaml` 使用 `policy.allow_implicit_invocation: false`，描述也明确仅响应主动调用。

有效启动包括 `$dev-work 修复……` 或用户明确要求本次使用该 skill。仅出现 feature、bug、基建等词不触发。
调用后允许在同一工作范围内继续调查、文档、实施和交付；新任务或范围变化不能自动继承调用与授权。
退出或取消时停止该工作的流程维护，保留已产生的材料和未解决事实。

### 五类任务的步骤与材料

每类启用工作都保留 `00-work.md`（人工说明）、对应类型定义和 VERIFY（结果证据）。
类型定义写细节，不能重新决定主文中的目标、范围、验收或关键代价。
具体过程按以下主线处理；步骤完成不要求额外造一份同名文档。

| 类型 | 流程主线 | 默认材料（除工作说明外） | 何时增加附件 |
|---|---|---|---|
| 功能 product / feature | 明确场景与规则 → 使用流程及失败状态 → 方案 → 人确认 → 实施 → 复核 → 场景验证 → 人接受 | FEATURE、VERIFY | 交互或权限流程较长时 EXPERIENCE；技术方案复杂或需独立评审时 DESIGN |
| 修复 fix / bug | 记录实际与预期 → 复现或说明证据限制 → 查明原因 → 修复思路 → 人确认 → 修复 → 复核 → 回归 → 人接受 | ISSUE、VERIFY | 跨模块、原因链复杂或改变技术路线时 DESIGN；无法确认根因时记录限制，不宣称根因已修复 |
| 基建 infra | 明确使用者与能力 → 接入、配置及失败恢复 → 边界与方案 → 人确认 → 接入实施 → 复核 → 集成和故障验证 → 人接受 | CAPABILITY、VERIFY | 接入或运维步骤较长时 EXPERIENCE；跨服务、数据所有权、权限或隔离方案复杂时 DESIGN |
| 维护 maintenance | 当前问题 → 目标及不变量 → 改动方案 → 人确认 → 调整 → 复核 → 行为回归 → 人接受 | CHANGE、VERIFY | 广泛重排、依赖或职责边界调整、兼容方案复杂时 DESIGN |
| 改进 improvement | 采集基线 → 确定目标和测量口径 → 方案 → 人确认 → 实施 → 复核 → 同口径前后比较 → 人接受 | IMPROVEMENT、VERIFY | 方案复杂时 DESIGN；确有后续观察环境与计划时写观察条件，没有则明确验证限制 |

产品与基建的体验职责始终要处理；简单流程可以写在对应类型定义中，独立 EXPERIENCE 是按长度和协作需要拆分。
微小修复或维护若所有定义内容能在简短工作说明中完整表达，可不另建 ISSUE/CHANGE，须说明采用最小材料的理由。
这个例外不能用于省略复现、预期、不变量或验证证据。

跨类型附件按实际用途增加：

- DECISION：会长期约束后续任务、存在重要备选或代价的选择。主文仍呈现需要人工接受的代价。
- PLAN：跨任务依赖、分批交付、兼容窗口或迁移顺序。单个任务也可能需要计划；任务数量不单独决定是否拆分。
- TASK：独立委派、并行工作或单独完成判断；每个任务写依据、产出、读写范围、禁区与验证条件。
- MEMORY：未来仍有价值的决定背景、失败方案或教训；不强制收尾生成，不复制执行流水账。

高风险加强独立复核与回退验证，系统级影响加强跨模块回归，安全、数据、可靠性等关注增加对应证据。
风险不自动生成完整文档包；同一 Agent 自查不能写成独立复核。

### 人最容易读的工作说明

未来新工作的 `00-work.md` 使用纯 Markdown，不带大段机器元数据、流程表或命令日志。
正文默认为四小节：`为什么做`、`打算怎么解决`、`范围和需要接受的代价`、`怎样算完成`。
没有重要未知时不另外生成问题表；存在阻塞或假设时直接写在相关小节，指出是否可以开工。

普通工作以 200–400 个汉字、几分钟能读完为目标，不设会截断关键风险的硬上限。
每段说明结果和原因，使用日常语言；文件路径、配置、调用链和测试命令放附件。
复杂工作先收窄当前交付范围；仍无法简写的关键代价必须展示，不能只给链接。

简短示例，仅用于展示文风：

> **为什么做**：题目保存失败时，页面把刚输入的内容清空，用户必须重新填写。
>
> **打算怎么解决**：保存成功后再更新页面。保存失败时保留当前内容，告诉用户失败原因，并允许重试。
>
> **范围和需要接受的代价**：只改编辑页面，不改接口或数据格式；离开页面时仍提醒未保存内容。
>
> **怎样算完成**：正常保存可用；失败后输入不丢失；重试成功后显示已保存。

交付时在同一说明末尾追加一段简短结果：实际完成什么、与承诺的差异、测过与未测部分、需要接受的遗留问题。
详细证据只写 VERIFY，结果段引用它。这个结果段不成为第二份可独立漂移的状态或证据。

引用与概述可以帮助阅读，独立维护相同事实则应避免。各附件写本层新增信息，引用上游，不完整复制上游要求。

## 模块与数据

skill 与仓库的开发说明一起保存。新工作建议保存在 `development/work-items/YYYY-MM-DD-short-name/`，
与历史 `development/works/WORK-xxx/` 分开，保留旧路径、编号与签署语义。
新工作不依赖 WORK/TASK 永久编号、JSON 状态文件或中央总览才能开工；同日同名目录须避免覆盖。
文件用 `00-work.md`、`10-feature.md` / `10-issue.md` / `10-capability.md` / `10-change.md` / `10-improvement.md`
及按需附件表达职责，证据使用 `70-verify.md`。

实施后更新 AGENTS.md、根 README、development 入口及规范，把文档系统的专属要求改为仅调用 skill 时适用。
同步 docs 中“所有工作先建 WORK”、强制 TASK 待办编号、设计变更必须生成 WORK/DECISION 等间接入口。
这些规则背后的确认、追踪和安全要求仍保留，不能用修改说明绕过实际工程约束。

现有 `scripts/work` 继续支持历史记录；结构检查识别新的记录目录，避免把新格式误当成缺少元数据的旧格式。
不另建新中央状态机或为每次普通代码改动自动创建记录。

## 接口与状态

在新 skill 工作中，人工确认从命令签闸改为聊天：

1. Agent 准备简短说明和必要技术材料，展示需要判断的内容。
2. 人明确同意并允许执行后，Agent 在说明末尾记录确认范围、时间和来源，再实施。
3. Agent 交付实际结果与证据。测试通过只表示技术结果，不表示人已接受。
4. 人明确接受后，Agent 如实记录；没有回复时保持待接受，不因沉默或新任务自动完成确认。

不强制为这些事实建立有限状态机。确认记录仍须可追溯；不得把 Agent 记录事实描述成人运行了旧 gate 命令。
如果出现改变用户行为、范围或重要代价的新决定，先更新工作说明并重新确认对应变化。
旧 WORK 的 gate 命令与状态语义继续保留，不将新的聊天记录追认成历史签署。

本 WORK-062 仍按变更前规则管理。这一方案的待审核内容不是对本轮实施的授权，也不能据此提前绕过旧闸。

## 安全与失败

不调用 skill 时也要遵守产品与架构规则、契约唯一来源、语言规范、测试要求和明确任务范围。
普通代码任务不必为了遵守这些规则先创建工作文档。
调用 skill 不自动授权提交、推送、部署、发送消息或修改原任务之外的文件。

未知根因、失败或部分通过的测试、未运行的环境必须如实记录；无法独立复核时说明限制，不用换角色替代。
必要的产品或权限取舍始终回到人工说明，不放在技术附件里默默生效。

## 监控与部署

无业务部署变化。现有 hooks 与 CI 的代码、契约和链接检查保留。
对已经存在的历史文档做只读结构检查，不等于为新代码任务启用文档流程；不能因缺少新 WORK/TASK 而阻止普通开发。
无需为调用 skill 增加常驻服务、监控或定时任务。

实施验证至少覆盖：

- skill 的 front matter、引用及显式调用策略有效，仓库能够发现它。
- 五种明确调用请求按各自流程准备材料，普通 feature/bug 请求没有隐式调用要求。
- 短说明有背景、思路、范围代价、验收；技术细节不挤入人工正文。
- 简单修复允许最小材料；复杂基建和分批维护按实际需要拆附件；改进必须有测量口径。
- 开工与接受均保留明确人类来源；没有通过测试或聊天沉默推导人工接受。
- 旧工具测试、真实历史记录及全局 Markdown 链接继续通过。

可发现性和行为需要真实使用检查；静态文本断言不能证明 Agent 一定遵守调用策略或文风。
本轮文档检查不计作上述实施验证通过。

## 迁移与兼容

先建立明确调用的 skill 及分类参考，再同步全局规则与新记录支持；这些改动在交付候选中一起验证。
历史 WORK、附件、flow.json、编号计数器和签署记录不批量迁移，不补造结论，不改变原验收标准。
新格式的路径规则与旧工具识别方式需同时交付，不能只改 AGENTS.md 而留下 README、TODO 或模板继续要求自动建 WORK。
新增 skill 的链接进入 Markdown 校验范围，引用要随仓库路径稳定；不复制完整规范形成两套要同步的正文。

## 备选方案

保留现有强制系统、只包一层 skill：改动小，但普通开发仍被全局规则启动，无法满足明确调用。
明确调用后继续完整命令状态机：保留机器约束，但人工签闸、元数据和状态维护的负担仍在。
全部任务只留一张工作说明：最短，但失去类型细节、独立交接和实际验证证据，不能满足已讨论的分层职责。
推荐主动调用、简短人工入口、按类型准备技术材料，以聊天保存人工确认，并保留历史工具兼容。

## 风险与重审条件

主文列出的代价是减少新工作流程的机器强制校验；本附件不增加另一个需要人工接受的代价。
Agent 必须检查依据、范围、未解决问题和证据，不能把省去状态机当成省去这些职责。
当多执行者协作确实需要独立状态或自动覆盖检查时，再针对那个工作添加 TASK 与必要工具，不能恢复为所有工作默认强制。
若真实使用仍让人读不懂背景和思路，优先改说明文风及交付范围，再判断是否调整文档结构。
