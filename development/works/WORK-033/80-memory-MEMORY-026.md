# MEMORY-026：重设计后台题目创建与编辑体验

## 背景

题目创建曾把管理、新建、题面、样例 JSON、起始代码、测试数据、校准、发布和危险操作堆成一个长页面。
这不是单纯的视觉密度问题，而是把后端字段顺序当作人的任务顺序：使用者必须自己记依赖、滚动找保存，
并在最后才知道发布缺什么。Textarea/Monaco/JSON 也各自形成不同录入习惯。

## 决定与原因

后台题目采用六步、可恢复 URL 的明确保存工作台；服务端版本仍由 Query 管理，草稿归 Form，步骤归 Router，
参考源码只留组件内存。长 Markdown/后台基础代码使用 CodeMirror 6 官方模块和本地薄适配，不 fork 上游；
Monaco 留给真正需要 IDE 级补全/诊断/多文件的用户端场景。重复业务对象用结构化 UI，序号和序列化归提交
边界。发布就绪只认服务端 publish-check，前端步骤完成度只负责导航。

## 尝试与教训

显式保存不能只放一个 boolean。若请求发出后用户继续输入，旧响应到达时直接 `form.reset(response)` 会
覆盖新内容；必须给提交快照配编辑修订号，只在提交后没有新编辑时更新基线。dirty 也不能手写成“一旦改过
永远 true”，应订阅 Form 元数据，使改回原值时离开保护自动消失。

CodeMirror 受控适配应长期保留一个 EditorView；主题/语言/read-only 用 Compartment 重配，外部值只在
文档确实不同且非用户更新时替换。Tab 不做缩进绑定，中文组合期间不触发保存。CodeMirror 的 dark facet
只是 color scheme 元数据，不代表组件可以写主题分支或 raw 色值。

测试数据上传与绑定是两个服务端动作，UI 必须承认“上传成功、绑定失败”的半成功状态并保留重试对象。
人输入秒/MiB，底层 ns/bytes 只在请求边界精确换算。发布、可见性、修订、归档和删除不是同一层动作；
危险操作不能再用 `window.confirm`。

## 已知问题

工作台 chunk 仍为约 754 kB / gzip 256 kB，虽然较 Monaco 基线分别下降约 71.6% / 62.5%，Vite 仍给出
500 kB 提示。自动化覆盖 Chromium；真实管理员数据、中文输入法候选窗、读屏器和 Node 24 CI 结果仍需在
验收/CI 中确认。

## 重新考虑条件

当后台需要 LSP、复杂诊断、多文件或超大工程编辑，重新评估 Monaco；当字段只剩几行简单备注，应退回
Textarea。当服务端提供协同编辑、保存队列或冲突合并合同，重新评估显式保存。当支持 CORE、多语言、
测试数据自动生成或多环境发布时，重审六步划分、完成度和校准单位，不能只向现有页面继续叠区块。
