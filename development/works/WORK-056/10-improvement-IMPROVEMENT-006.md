# IMPROVEMENT-006：固定沙箱软件包来源与长期留存

## 当前问题

自动测试依赖固定版本的软件包，但下载地址会随着上游更新失效。继续增加等待时间不能恢复已经不存在的文件。需要让每天的测试能够稳定拿到同一批依赖，同时保留从官方来源重新取得它们的能力。

## 当前数据

WORK-055 的两次 Linux 运行（34672937023、34672937009）均在约 6 秒后因三个 glibc 包返回 HTTP 404 失败；不是本次下载超时。当前包锁共 56 个包。2026-09-12 本地从官方快照 `20260910T000000Z` 取得这三个包，字节数与 SHA256 均匹配原锁；其余 53 个及 GitHub 环境尚未验证。证据与来源见 DESIGN-050。

## 目标指标

- REQ-001：固定官方快照，在原有准备期限内取得全部 56 个包，逐个匹配原锁；包锁和包内容不变。
- REQ-002：把已核验的包集及所需许可、对应源码作为可长期留存的固定资产；发布前展示完整清单和摘要并获得发布授权。
- REQ-003：日常 CI 使用固定资产，缓存只作加速；独立冷检查继续验证官方快照恢复能力。每次执行都重新验证包内容、构建当前代码和 rootfs。

## 影响范围

仅 CI 的依赖获取、验证、资产准备和相关工作流。承接 WORK-055 来源不可用阻塞，服务于 WORK-050。部署默认下载行为、判题代码、用户服务器及节点身份不在范围内。

## 主要风险

快照并非永久保存承诺；固定资产仍可能遇到 GitHub 故障。包集公开分发需要满足各包的许可及源码交付要求。固定旧版本不等于持续获得安全更新，升级仍需单独审查与校准。

## 验证方式

- AC-001：Linux 冷取 56/56 校验通过，原锁摘要不变，构建 rootfs 的清单与基线一致；缺包、错误摘要或不可用来源明确失败。
- AC-002：发布清单记录来源、包与源码摘要、许可、固定资产标识和不可变状态；使用者验证外层资产及内层每个包，拒绝篡改与路径攻击。
- AC-003：至少两次全新 GitHub 运行覆盖固定资产缓存未命中与命中，并有独立官方快照冷检查通过；三条消费者实际运行，记录剩余业务问题，不以跳过算成功。

## 持续观察

保留每次来源、缓存命中、耗时、HTTP 分类、包数量和内容身份。官方冷检查失败时可区分“官方恢复失败”与“日常资产不可用”；任何失败均保留原始记录。WORK-050 整体验收仍需全部测试通过。
