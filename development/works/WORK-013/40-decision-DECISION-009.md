# DECISION-009：建立用户身份与访问控制服务

## 要决定什么

确认 MVP 的账号开通、浏览器/内部会话模型、首个管理员初始化、密码与 JWT 基线，以及具体会话期限。
这些选择直接决定公开行为、数据库、安全失效上限和运维方式，是实现前的人工门禁。

## 背景

全局基线已选择 Gateway Session + user-service 自建认证 + 内部非对称 JWT，但 WORK-002 尚未确认开放注册
还是管理员预置，现有两张 user 表也不能表达可单独撤销、可续签的登录授权。若不先决定，Gateway、
user-service 和 Web 会各自补一套不兼容的会话假设。

## 候选方案

### 方案 A：管理员开通 + 服务端登录授权 + 短 JWT（推荐）

- ADMIN 创建普通用户并给出一次性临时密码；用户首次登录必须改密。
- Gateway 在 Redis 保存浏览器 Session；user-service 在 MySQL 保存登录授权摘要与撤销事实。
- Gateway 用授权换取 2 分钟内部 JWT，资源服务离线验签。
- 首个 ADMIN 用一次性离线命令初始化；密码从标准输入读取。
- 优点是无需先建设邮件验证/找回，浏览器不接触 JWT，单端退出与全端撤销都能表达。
- 代价是多一个登录授权表、刷新接口，并接受最长等于 JWT TTL 的资源侧撤销窗口。

### 方案 B：开放注册 + 同一会话模型

- 增加公开注册、反滥用、用户名抢注和未来找回路径。
- 演示更方便，但没有邮箱/短信验证时无法可靠证明账号归属，也显著增加公网攻击面。

### 方案 C：Gateway-only Session

- Redis 直接保存 userId/role，下游相信 Gateway 头，不建登录授权和 JWT。
- 实现最快，但资源服务无法独立验权，内部头可伪造，违背已确认架构，不能作为生产方案。

### 方案 D：外部 OIDC/IdP

- 复用成熟身份系统，适合企业 SSO；但改变“自建用户服务”的既定边界和部署依赖，不适合当前 MVP。

## 决定

推荐方案 A，并推荐以下参数：Argon2id（启动时校验、部署前实测成本）；RS256/RSA-3072；内部 JWT
120 秒、时钟偏差最多 30 秒；浏览器/登录授权空闲 30 分钟、绝对 12 小时；允许多端登录；退出只撤销
当前端，改密、重置、角色变化和停用撤销全部端；首个 ADMIN 使用一次性离线命令初始化。

**状态：已于 2026-08-26 人工确认，可以按 PLAN-010 实施。**

## 理由

方案 A 在不引入邮箱、短信或外部 IdP 的前提下完成账号归属、浏览器凭据保护、独立资源验权和明确撤销。
短 JWT 把离线校验的风险窗口压到可测试上限；服务端登录授权避免把长期 refresh token 交给浏览器。
管理员开通与当前“单管理员内部 MVP”一致，也直接解决 WORK-002 的账号开通阻塞项。

## 影响与风险

批准后需要新增 public OpenAPI、user-service 表与密钥、Gateway Redis/CSRF、资源服务 JWT 校验和 Web
登录页面，属于系统级安全与数据改动。最重要的剩余风险是 120 秒撤销窗口、Argon2 参数造成资源耗尽、
两个 Session 存储失配和密钥轮换顺序错误；DESIGN-010 与 VERIFY-013 给出控制与反例。

请人工逐项确认：

- [x] MVP 不开放注册，由 ADMIN 创建 USER。
- [x] 首个 ADMIN 使用一次性离线命令初始化，不使用默认密码或 migration seed。
- [x] 采用 Gateway Redis Session + user-service 登录授权摘要 + 120 秒内部 JWT。
- [x] 接受 30 分钟空闲、12 小时绝对期限和允许多端登录的推荐策略。
- [x] 接受“当前端退出、全端安全撤销”语义和最多 120 秒的资源侧撤销窗口。
- [x] 接受 Argon2id 与 RS256/RSA-3072 基线，具体哈希成本由目标环境实测冻结。
- [x] 安全边界与权限影响已经由负责人确认，并允许按 PLAN-010 实施。
