# MEMORY-028：设计系统四轮返工的根因与本次的对策

## 背景

Cherry OJ 的 Web 设计系统在 WORK-036 之前经历了四轮返工：GitHub 下载的 Linear 风格系统 →
Claude Design 重做 → codex 按原始材料重写 → codex 按 Claude Design 导出重构。每轮产出都"材料
合规"，但用户始终觉得页面"不像"。

WORK-035 的 git 考古揭示了一件此前没人核对过的事：`eb3c7a3`（2026-08-28）先建立了整套 token
结构、主题合同、adapter 与校验器，`ec260bd`（2026-09-03）才引入被文档称作"直接视觉来源"的
Claude Design 下载版，且只对既有文件打补丁——`themes/cherry-black.css` 相对初版累计仅
`+19/-12`。**所谓"基于来源重建"实际是改装。**

冻结来源自带 14 份 `*.prompt.md`、20 张 guidelines specimen 卡片、一份 adherence lint 配置和
4 个 app UI kit 页面。这些在 WORK-035 之前全部未被使用，项目另写了一份 619 行组件 manifest
和两个各 1336 行的校验器。

## 决定与原因

**根因是系统里一直缺少构图层**，不是执行质量。只有 token 和基础组件、没有"一个列表页长什么样"
的成品模板时，页面只能从零件现拼，而现拼必然拼出不同的东西。

因此 WORK-036 的对策不是再补 token，而是补第 3、4 层（DataList / Toolbar / 页面模板）并把页面
语法写成能在截图上判定的构图合同。

配套的三个判断：

- **只迁一个样板页**（DECISION-020 C-2）。人只能判断"像不像"，所以要尽早让人判断；
  样板被否时返工面是一个页面加一份合同，而不是整个 Web。
- **合同里的一个字段可以毁掉整个视觉层级。** `--ds-fg-disabled` 被定为 `contrastClass: text`，
  强制它满足 4.5:1，连带把 muted / meta / disabled 三档压成同一个灰。改合同前先问：
  这个对象真的属于这一类吗？WCAG 对失效控件本来就是豁免的。
- **补 alias 必须与加 lint 同批交付。** 只补不拦，两套写法会长期并存，比现在更乱。

## 尝试与教训

**样板页被否了两次，两次的根因相同：我从参照的形态出发，而不是从本项目的内容出发。**

- 第一版被判"居中卡片、筛选像后台表单、有表头太像表格"——我照着规则做对了每一条，
  却没意识到规则本身描述的是一张数据表。
- 第二版被判"很一般、为何占满页面宽度"。量化后发现 1440px 的行里真正有内容的只有约 375px，
  空掉约 1000px。根因是把参照的 issue 行（一句长英文 + 几个小图标）套在了表格型内容上
  （短标题 + 难度 + 标签 + 语言）——两簇布局把元信息推到两端，6 个汉字的标题后面必然空一大半，
  **换多宽都一样**。

**规则会被用来给错误背书。** 我写下"空白是内容"，然后拿它解释那 70% 的空白。那条的前提是
"内容本来就填不满时别硬填"，不是"让内容稀疏地摊在过宽的容器里"。规则修正后加了判据：
**这一行的内容本来就撑不满，还是被人为推开的？**

**文档漂移三次，每次都是人工核对才发现的。** 改实现不改文档，`PROMPT.md` 三度与代码矛盾
（七处、六处、六处）。最危险的一次是它写着"一行只有两簇，中间是空的"——新会话读到会把刚
拆掉的东西重做一遍，而 token 校验、lint、测试全都会通过。**代码有自动防线，文档没有。**

**目测不能替代测量。** "列对齐"这条判据我看着截图以为达成了，量 x 坐标才发现三行的尾部列
分别在 348 / 454 / 321。同样，"70% 是空的"也是量出来才有说服力的。

**字符串替换必须断言。** 有两次改动因 prettier 重排后未匹配而**静默丢失**，脚本照常输出成功，
我拿着旧构建量了半天。

**检查脚本本身也会说谎。** 有三次 grep 报"✗"，实际是引号转义或匹配到了注释与测试断言本身。
报错时先问：是被测对象错了，还是我的检查写错了。

### 更早的通用判据

- **判断一个设计系统是否可用，不要只看 token 是否齐全，看能不能"选模板 + 填数据"写出一个页面。**
  如果每个页面都要从 Button 和间距变量现拼，这个系统还差一层，再补多少 token 也不会变像。
- **收到"重建设计系统"这类请求时，先做考古再动手。** 查 git 历史确认现有结构何时、基于什么
  建立；查外部来源包里已经自带了什么。四轮返工里有两轮在重写来源已经提供的东西。
- **副本增殖会自我掩护。** token、合同、校验器期望值在两棵树各存一份，校验器还手抄了一份答案，
  于是"校验通过"只证明两份手抄本一致。发现这类结构时，先删副本再谈改进，
  否则新增的东西会变成第四份副本。

## 已知问题

- 除题库列表外，其余页面尚未迁移到新模板，仓库会处于新旧两种列表写法并存的过渡状态。
- `components.manifest.json` 中 `editor-workspace`、`submission-lifecycle`、`verdict`
  三个合同仍无实现。
- 冻结来源自带的 `_adherence.oxlintrc.json` 逐组件 prop/variant 白名单仍未接入项目 lint；
  推迟到组件层稳定之后，避免 prop 表变动导致写两遍。

## 重新考虑条件

- **样板页被用户判断为"仍然不像"**：说明"缺构图层"这个诊断不完整，本记忆的核心结论需要修正，
  应重新识别"像"的构成要素，而不是继续按现有合同迁移其余页面。
- 若未来再次出现设计系统返工，先回到本记忆核对：是不是又在既有结构上叠加，
  而没有先判断既有结构是否成立。
- 若 WCAG 后续版本对失效控件提出对比度要求，`fg-disabled` 的豁免前提消失，四档结构需重新设计。
