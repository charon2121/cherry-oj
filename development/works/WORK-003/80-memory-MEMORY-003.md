# MEMORY-003：按工作项聚合开发文档

## 背景

开发文档系统最初按文档类型建全局目录，虽然便于按类型浏览，却把一个工作项的上下文拆散。2026-08-24
由用户明确调整为“一个工作项一个独立目录”。

## 决定与原因

`development/works/WORK-xxx/` 是过程文档的聚合边界。00 至 80 的固定前缀表达从工作入口、定义、
体验、设计、决策、计划、任务、验证到记忆的信息层级；永久 ID 仍是引用和生命周期管理的唯一身份。
这样既能直接阅读单项上下文，也保留 CLI 跨工作查询能力。

## 尝试与教训

- 仅靠 front matter 关系可以让机器聚合，但不能改善文件树中的人工阅读和交接成本。
- 不应同时保留旧类型路径和新 WORK 路径的兼容副本，否则同一 ID 会出现两个真源。
- 移动 Markdown 后必须检查相对链接；WORK 入口相对 `SPECIFICATION.md` 的层级会改变。
- 层级前缀是展示顺序，不是编号系统；任何时候都不能据此回收或重排永久 ID。

## 已知问题

当前没有阻断问题。CLI 仍通过全量文件扫描建立内存索引；在文档规模达到数百或数千前，这比引入
额外数据库更简单可靠。

## 重新考虑条件

单个 WORK 文件数长期大到扁平目录难以浏览、出现必须表达的多级子工作树，或全量扫描成为可测量的
性能瓶颈时，重新评估受约束的子目录或持久索引；不能回到按类型拆散工作上下文的结构。
