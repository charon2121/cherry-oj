# DESIGN-003：按工作项聚合开发文档

## 背景

CHANGE-002 定义了由按类型分目录改为按工作项聚合的要求。现有 Markdown front matter 已包含永久 ID、
类型和所属 WORK，因此无需改变数据模型，只需让物理位置与工作归属一致。

## 目标与限制

目标是通过文件树直接获得一个 WORK 的完整上下文和稳定阅读顺序，同时保留现有状态机、引用图、
模板、查询能力和 Git 可读性。`docs/` 仍是跨工作项全局事实层，不能被并入工作项目录。

## 整体方案

`development/works/` 下只放 `WORK-xxx-slug/` 目录。每个目录以 `00-work.md` 为入口，附属文档按
`<两位层级>-<小写类型>-<永久 ID>.md` 命名。CLI 从这些目录的直属 Markdown 文件发现文档，生成时
先确定 WORK 目录，再将整套所需文件写入其中；不再创建类型目录。

固定层级为：00 工作、10 定义、20 体验、30 设计、40 决策、50 计划、60 任务、70 验证、80 记忆。
PRODUCT、FEATURE、CAPABILITY、ISSUE、CHANGE、IMPROVEMENT 都属于 10 定义层。同层的自然文件名
顺序由类型名和永久 ID 共同稳定下来，不额外表示层级关系。

## 模块与数据

- `scripts/work`：集中维护类型到层级的映射、路径生成、发现和结构校验。
- `development/works/`：持有按 WORK 聚合的全部受管理 Markdown 文档。
- `development/templates/` 与 `schema/`：继续定义正文骨架和元数据，不承担物理分组。
- `development/index.json`：继续单调分配永久 ID，不受目录前缀影响。
- `scripts/work_test.py`：在临时目录验证生成结构及非法放置。

## 接口与状态

命令名称、文档 ID 和状态机不变。`new` 创建工作项目录；`new-doc --work WORK-xxx` 根据已有 WORK
定位目录，不再接受文件 slug；`archive` 原地更新状态。`check` 新增目录名、文件名层级和同 WORK
共置约束。`show/list/trace/context/overview/refresh` 通过统一发现逻辑适配新位置。

## 安全与失败

变更只涉及仓库文件，不触碰运行时数据或权限。生成前继续执行完整的预期文档校验；非法目录、错误
文件名或跨 WORK 放置会产生明确错误。现有文件迁移保持正文与 front matter，失败时可由版本控制恢复。

## 监控与部署

无需业务部署。CI 继续运行工具测试、文档链接测试和 `scripts/work check`；失败信息是结构回归的直接
观察信号。

## 迁移与兼容

将每个现有 WORK 入口改为对应目录的 `00-work.md`，再按文档 `work` 字段和类型层级移动所有附属
文件。修复受影响的相对链接后删除空的类型目录。旧物理路径不保留兼容副本，避免同一永久 ID 出现
两个真源；CLI 命令与元数据格式保持兼容。

## 备选方案

1. 保持按类型分目录，仅提供上下文查询：机器可聚合，但文件树和人工浏览仍然拆散。
2. 在 WORK 目录内再建 `features/`、`designs/` 等子目录：类型清楚，但小型工作产生大量空层级，且
   无法通过一次扁平排序表达阅读顺序。
3. 把类型写进正文而不拆文件：适合极小工作，却失去独立审批、引用和复用能力。

选择扁平工作项目录加层级前缀，兼顾单项聚合、直接排序和永久 ID。

## 风险与重审条件

扁平目录在单个 WORK 拥有大量同层文档时可能变长；当前可由稳定 ID 和 CLI 查询解决。若单项文件
规模达到人工难以浏览的程度，或出现必须嵌套表达的子工作树，再评估在不破坏 WORK 聚合原则下增加
受约束的子目录。若调整层级，必须同步更新规范、映射和回归测试。
