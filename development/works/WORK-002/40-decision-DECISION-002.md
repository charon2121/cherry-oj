# DECISION-002：首轮正式提交的范围与技术取舍

## 要决定什么

确认六任务范围、公开结果边界、异步恢复机制、服务身份方案与验收环境。本文件已由 WORK-002 意图闸签署确认；实施状态与验收证据分别见任务和 VERIFY。

## 背景

旧方案涵盖从建题到自测、正式提交与历史列表，且技术、任务文档是占位内容。WORK-025/040/041
已交付主要前置能力；当前新增工作集中在正式提交服务链，不能把全局目标架构当作现成实现。

## 候选方案

| 问题 | 推荐 | 其他选择及代价 |
|---|---|---|
| 本轮范围 | 正式提交、真实判题、单次结果恢复 | 运行/完整历史一起做会扩大接口、状态与验收规模 |
| 编排 | 既有 Kafka + 本地事务 Outbox/Inbox + 租约 | 同步 Gateway 等待违背架构基线且响应丢失难恢复 |
| 身份 | 可信内网下每调用链独立服务 token，限定端点 | 复用用户 token 会过期且混淆权限；所有服务共用一个密钥扩大泄漏影响；PKI/新认证中心超出 MVP |
| 题面更新 | 客户端只传预期版本作前置条件，服务端解析当前快照，不符拒绝 | 静默按新版本判题违背用户正在阅读的题意；任意指定历史版本增加产品范围 |
| 结果公开 | 总判定、允许的统计与安全 CE 诊断 | 单点判定可后续开放；正式输出可能直接回显隐藏输入 |
| 验收 | 隔离栈故障测试，现有环境经部署确认后人工冒烟 | 仅隔离验收也可，但不构成现有环境验证 |

## 决定

2026-09-07 负责人已确认 WA 汇总展示与隔离验收、现有环境另行确认部署后人工冒烟两个选项，详见 FEATURE-001。
随后负责人签署意图闸并明确允许实施，覆盖 DESIGN 的技术选项与六任务范围。验收闸仍须负责人另行签署。

## 理由

沿用已确认架构，把必要的数据安全与故障恢复做好；将“整个产品最终应具备什么”与“本轮可以亲手验收什么”分开。
六任务都给出完成标准，不以文件数量或打开提交按钮作为交付结果。

## 影响与风险

新增服务凭据需要配置、轮换和失败测试；新增数据库记录不能用删除迁移回滚；消息链需要重试及乱序测试。
已受理任务固定旧环境，如果旧环境撤走会明确 SE，不能偷偷借用新环境得到不同结果。

## 重新考虑条件

出现已部署事件消费者、需要复杂调度/多语言、对外部署网络边界变化、结果公开策略扩大，或真实负载显示
默认执行预算不足时，先重审设计和任务范围；不能顺带建设通用平台。
