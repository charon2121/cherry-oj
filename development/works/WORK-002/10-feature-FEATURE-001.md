# FEATURE-001：交付 C++ ACM 正式提交闭环

## 为什么做

现在用户已经能登录、看题和写代码，但写完以后还不能真正交给系统判题。本轮让用户点击一次
“提交”，拿到这次答题的记录，并看到正确、答案错误、编译错误或平台故障的明确结果；刷新页面
后仍能继续查看同一次提交。

先把这一条流程做实。自定义输入运行、完整的“我的提交”列表以及通过题数统计留到后续，避免
一次加入太多尚未体验过的功能。题目管理、登录和编辑器沿用已经交付的能力。

## 当前基线与旧方案调整

核对基线：2026-09-07，仓库提交 `42c181d`。这是代码事实核查，不代表现有部署环境的健康检查。

| 原范围 | 当前事实 | 本轮处理 |
|---|---|---|
| 管理员创建、部署数据、校准、发布题目 | WORK-025 已交付，WORK-040 补齐节点注册与数据交付 | 用作前置条件与回归，不重建后台 |
| 用户登录与会话 | WORK-013、WORK-014、WORK-037 等已建立 | 复用；补齐提交资源的权限检查 |
| 左题面右编辑器、本地草稿 | WORK-041 已交付 | 只增加正式提交和结果区 |
| 创建提交、查询结果 | submission-service 只有应用与安全骨架，Gateway 无提交接口 | 新建 |
| 异步正式判题 | 契约和架构已有定义；judging-service 当前只有就绪、校准、节点与数据能力 | 新建任务与结果链路 |
| 自定义运行、完整历史列表 | 尚未交付 | 从本轮验收移出；运行按钮保持“暂未开放” |

旧编号保留以便追溯：REQ-003、REQ-010、AC-002 改为本轮不开放自定义运行的边界检查；
AC-003 原“我的提交列表”改为可恢复的单次提交结果入口。以上是本次意图闸已确认的范围变更，
不表示旧版的自定义运行或历史列表已经完成。全局产品目标不因此删减。

## 使用者

已登录 USER 与 ADMIN 都可以按普通用户身份提交自己的代码，并只查询自己的提交；ADMIN 不因此
取得查询他人源码的能力。游客可以看题，提交时引导登录。沿用强制改密和会话失效规则。

## 入口

入口为已发布的 C++ ACM 题目页；结果显示在答题工作区，可复制当前提交的链接，刷新或重新打开
链接查询同一条记录。保留本地草稿，提交后继续编辑不会改变已提交的代码。

## 正常流程

登录并写代码 → 明确提交 → 获得唯一记录 → 查看判题结果 → 刷新或重开链接继续查询。
详细交互与异常恢复见 EXPERIENCE-001。

## 业务规则

- REQ-001：只接受用户自行处理标准输入输出、包含完整程序入口的 ACM 代码。
- REQ-002：本轮正式提交只开放已经验证的 C++；其他语言与 CORE 在服务端也必须拒绝。
- REQ-003：本轮自定义运行保持暂未开放，不产生运行记录或正式提交；原自测能力移到后续工作。
- REQ-004：提交成功即冻结实际题目版本、原始代码、语言、测试数据版本、校准、环境与限制，之后不可漂移。
- REQ-005：复用已发布版本不可覆盖的约束；用户所见题面版本过期时要求刷新确认，不能悄悄按新题意提交。
- REQ-006：正确为 AC、编译失败为 CE、答案错误为 WA；超时等程序结果正常呈现，平台故障为 SE，不能误报 WA。
- REQ-007：隐藏输入、标准答案、正式运行的输出和差异内容不向普通用户返回，包括接口与错误提示。
- REQ-008：排队、判题、结果和故障都有文字说明；键盘、读屏和窄屏可以完成提交与查看。
- REQ-009：重复点击、刷新、请求超时重试不会重复创建同一次提交；修改代码后明确发起的新提交独立记录。
- REQ-010：正式提交入口及记录语义明确，不把正式送判当作自定义运行；不增加完整历史页与通过状态统计。
## 要求

- REQ-011：每次提交可以追溯处理状态，消息重投、服务重启和旧任务迟到不能导致结果回退或多次生效。
- REQ-012：公开结果采用允许字段清单；编译诊断有大小限制、移除内部路径与控制字符，系统错误仅返回安全摘要。
- REQ-013：区分尚未提交、创建中、创建结果待确认、排队、判题、终态、查询失败、无权限；查询失败保留已有结果。
- REQ-014：用创建数、完成数、SE 数和创建到终态耗时建立本轮验证基线，记录窗口与分母，不新增监控平台或虚构达标率。

## 验收标准

- AC-001（既有基线回归）：管理员以既有流程准备 C++ ACM A+B；题目公开可见，版本不可覆盖，节点在线、数据就绪、校准 VALID。缺任一条件不能以默认限制创建提交。
- AC-002（范围收敛）：运行按钮明确暂未开放；触发它不请求送判、不新增提交，既有草稿与编辑器可正常使用。
- AC-003（正式 AC）：提交正确完整代码得到唯一提交编号；结果区能显示排队/判题状态并最终得到真实 AC（快速完成允许直接看到终态），刷新和复制链接仍查询同一提交，能确认实际题目版本和语言，内部记录可追溯环境。
- AC-004（CE）：提交有语法错误的程序得到 CE 与安全编译诊断，不是 WA 或平台故障。
- AC-005（WA）：提交可编译的错误程序得到 WA；尝试输出隐藏输入时，浏览器及 API 都拿不到隐藏内容。
- AC-006（恢复）：创建响应丢失后同键重试只生成一条提交；查询短暂失败后可恢复，刷新不发送新的创建请求。
- AC-007（隔离）：未登录、会话失效、普通用户访问他人提交、用户凭证请求内部送判源码均被拒绝；切换账号不显示前一账号结果。
- AC-008（冻结）：题目发布新版本、校准更新、环境切换不改变已受理输入；旧题面提交被提示刷新，旧环境不可用时明确 SE，禁止静默换环境。
- AC-009（故障与幂等）：消息重复、乱序、Worker 崩溃、租约过期、Kafka 短暂不可用后恢复；仅当前有效尝试能生效，终态不回退，重试耗尽得到 SE。
- AC-010（人能理解）：可用键盘完成提交与查询，窄屏结果可读，读屏不被轮询反复打断；附人工操作步骤、独立复核与实际验证证据。

## 待确认项

2026-09-07 负责人确认：普通用户只看到总判定、实际返回测试点的通过数量和资源用量，以及提交编号、时间、语言和题目版本；不展示单点名称、输入、标准答案、
stdout/stderr、diff 或内部地址。若提前结束或没有测试点结果，明确“未完成全部测试”或省略数量，
不能把已执行数假装成全部测例数。CE 显示经过处理的编译诊断，SE 仅显示安全提示和请求编号。

负责人同时确认：隔离测试栈承担真实 Linux Judge、数据库、Kafka 与故障测试；现有使用环境只在另行确认部署后
做人工冒烟。本轮文档不授权改动现有运行环境。两项阻塞已澄清；整份方案仍待负责人签署意图闸。

## 不做什么

不实现自定义运行、完整提交历史列表、他人提交管理、CORE、其他语言、排行榜、比赛、讨论、
做题统计、自动校准、通用任务平台或新的可观测平台。不重构 Judge/sandbox 算法、节点注册、
题目生产和编辑器草稿架构。

## 边界与失败

尚未受理与受理后查询失败必须分开；详细状态见 REQ-013 与 EXPERIENCE-001。

这是新增跨服务持久化与公开接口的高风险工作：主要风险是重复提交、任务永久挂起、版本漂移和
隐藏数据泄漏。按 PLAN 的六个任务逐步验证；发现必须改变既有架构或 Go 协议时先修改本方案与边界。
