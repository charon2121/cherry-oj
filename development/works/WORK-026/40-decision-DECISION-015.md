# DECISION-015：为 Java 服务提供可直接启动的本地默认配置

## 要决定什么

怎样让 user-service 在不 export 三项 RSA 配置时可本地启动，又不向仓库提交一把任何人都知道的固定
私钥；以及哪些空配置应补默认、哪些必须按语义保留为空。

## 背景

CAPABILITY-007 要求零 export 的本地启动。WORK-013 同时确定私钥只存在于 user-service，并来自部署
Secret，不能进入应用配置仓库。配置扫描还发现 Redis 空密码和关闭状态下的 provision 空字段是有效
状态，不能用“所有值非空”的机械规则处理。

## 候选方案

1. 提交固定开发 RSA 密钥：直接但会产生可伪造 token 的已知私钥。
2. 默认本机文件路径：不提交密钥，但开发者仍要先生成文件。
3. 本地缺省时进程内随机生成，production 强制 PEM：无需准备文件，不产生已知私钥，但重启会换钥。
4. 所有 profile 都随机生成：最省配置，但多实例和重启不稳定，不能满足生产可靠性。

## 决定

建议选择方案 3，并同时采用语义分类：只补启动必需项；Redis 密码等可选空值保留；Spring 内部占位符
不纳入环境变量规则。最终决定等待负责人确认。

## 理由

方案 3 是唯一同时满足本地直接启动、仓库无固定私钥、现有生产 PEM 配置兼容的方案。随机密钥重启
失效的代价局限于单机本地模式；production 通过显式拒绝消除该路径。固定开发私钥的误用后果远高于
本地重启重新登录成本。

## 影响与风险

需要为“本地生成”和“production PEM”建立不可混淆的模式校验，并覆盖 profile 漏配风险。数据库
默认口令属于公开开发约定，生产若未覆盖会有弱凭据风险。决策不改变 JWT 算法、HTTP 契约或数据。

## 重新考虑条件

引入统一 Secret manager、容器启动器能够安全生成每开发者独立密钥、user-service 开始多实例本地
运行，或 production profile 不能成为可靠部署不变量时重新评估。
