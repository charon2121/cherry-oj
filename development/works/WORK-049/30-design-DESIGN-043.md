# DESIGN-043：沿命令生命周期组织源码

## 背景

本方案落实 [CHANGE-013](10-change-CHANGE-013.md) 的阅读性目标。用户明确的理解顺序是：
“一条命令进来，到执行完毕”。架构介绍和包列表只能辅助这条路线，不能代替它。

本文是待审方案；所有“应当”“建议”描述拟议重构，不表示代码已经调整或全局规范已经生效。

## 目标与限制

先让源码呈现可追踪的主流程，再进入阶段内部的安全、协议和错误细节。
允许为职责清晰调整同包文件、私有类型和函数，允许在 Go 模块内部明确本机协议归属。
不改变进程模型、权限、协议、限额、错误分类和运行行为；不以文件行数、包数或常量数量衡量成果。

### helper 的定位与本次边界

现有方案让 HTTP sandbox 使用非特权账号，将创建隔离环境所需的权限集中在本机 helper。
独立进程是权限边界；Go 包的划分不能提供同样的权限隔离。helper 实际承担特权执行监督，名称中的
“帮助”不能准确解释它管理启动、资源计量、回收及文件交付的职责。

代价是多一个服务及本机协议、文件传输、断连恢复和生命周期协调。当前文档不把用户提出疑问解释为
同意长期保留或同意删除 helper；本次等价重构以现状为基线。职责命名可以改进，进程合并另行决策。
可替代的权限与执行器路线及重审条件见 [DECISION-027](40-decision-DECISION-027.md)。

## 整体方案

### 1. 主阅读路线：一次 POST /run

下表是正常 Linux 执行的阶段导航，不表示所有动作严格串行。输入输送、输出收集、资源监督本来并发，
重构必须显式标出启动位置、等待条件及收尾位置，而不能把它们伪装成同步函数链。
路径以下均相对 apps/judge-engine。

| 顺序 | 读者要理解的动作 | 当前代码锚点 | 必须清楚表达的完成条件或交接 |
|---|---|---|---|
| 1 | 接收、解码和校验命令 | internal/sandbox/api/run.go: handleRun | 进入执行接口；接口实际实现由 cmd/sandbox 组装为 Pool |
| 2 | 接纳请求并等待名额 | internal/sandbox/pool/pool.go: Run | 排队可取消；拒绝、取得名额和归还名额是不同事件 |
| 3 | 解析输入和预算 | internal/sandbox/runner/runner.go: Run、putInput、resolve | 输入 ref 转为受控流，显式零值和缺省已区分 |
| 4 | 准备客户端暂存并请求特权执行 | internal/sandbox/container/isolated.go: Start、execute | Start 返回的是在途句柄；通过 helper.Call 交接，尚不意味着用户命令已启动 |
| 5 | helper 接收请求并建立执行资源 | internal/sandbox/helper/server_linux_amd64.go: serveConn；execute_linux_amd64.go: execute、prepare | 明确 socket 对端；建立 cgroup、通道并启动可信 init，启动各 I/O 任务 |
| 6 | init 建立隔离文件环境并启动 exec 阶段 | internal/sandbox/launcher/init_linux_amd64.go: Dispatch、initSession.run、startPayload | re-exec 是同一 helper 二进制的新进程角色；输入到位后执行最终启动准备 |
| 7 | 完成权限准备与双向放行 | launcher: RunExecStage、releasePayload；helper: handleEvent | exec ready → init ready → helper 检查预算并发 GO → init 转发 GO → execve 用户命令 |
| 8 | 等待命令、监督时限与收集输出 | launcher: reportExit；helper: monitor | 命令退出或某个终止条件成立；所有监督/收集任务有明确所有者 |
| 9 | 终止后代、取得最终事实并回收执行环境 | internal/sandbox/helper/execution.go: finish、wait、collectOutputs、release | 整组停止、直接子进程等待、I/O 收尾得到确认；打开受控产物句柄后才能释放相关环境 |
| 10 | 交付结果和产物并确认传输完成 | helper: serveConn、executionResult.WriteFiles；client.go: Call | 元数据 → 文件流 → 文件句柄关闭 → Completion；缺少确认不能当成功 |
| 11 | 保存产物并确定最终响应 | container: Wait/GetFile；runner: classify/collect；pool: Close 路径；api: writeJSON | 暂存工作区关闭成功；失败回滚；最终结果此后才允许发送 |

### 2. 次阅读路线：一次判题如何使用命令执行

cmd/judge 组装 judgeService → judge/api.handleJudge 解码请求 → flow.Judge 加载测例、上传源码 →
需要时编译 → 逐点准备输入、调用 Sandbox.Run、比较输出 → 汇总并清理引用 → 返回判题结果。

这条路线引用上面的单次命令执行入口，不在 flow 中复制隔离内部知识。
node 的注册/心跳和数据安装是旁路，应有独立入口，不能迫使读者先理解节点控制面才能读懂一次判题。

### 3. 每一阶段的源码表达

- 顶层编排按生命周期排列，函数名表达动作和对象。启动进程不能只叫 prepare；发请求、启动进程、最终执行命令应当可区分。
- 每个入口先用短注释说明运行在哪个角色、接收什么、成功意味着什么。跨进程处指向真实接收符号；接口组装处说明具体实现。
- 关键交接在发起方说明传递什么与何时完成，在接收方说明接收对象；详细协议与常量只在协议所有者处维护。
- 正常路径上决定最终结果的回收/确认应显式出现。defer 仍承担异常兜底，不为了“线性”删除 panic 时的清理。
- 启动的每个 goroutine 或子进程都能找到停止触发者和等待者。阶段函数不得悄悄启动没有归属的后台任务。
- 不要求所有辅助函数返回 error；但关键失败不要只通过修改若干字段表达，让调用处看不出为什么提前结束。

## 模块与数据

### 文件调整建议

名称是职责提案，TASK-104 根据冻结基线列出最终旧符号到新符号映射；不为凑目录机械迁移。

| 区域 | 拟议组织 | 目的 |
|---|---|---|
| sandbox/api、pool、runner | 保留接收、名额管理、执行编排边界；runner 按输入准备、执行、结果收集组织 | 上层可以从请求顺读到返回，不必先研究内核接口 |
| sandbox/container | Container 契约说明 Start/Wait/Close 的阶段语义；isolated 文件明确为 helper 客户端适配；host 单独保留 | 不把异步请求句柄误认为已开始运行的程序 |
| sandbox/helper | 请求处理、启动、监督、回收、交付分别有明确文件；核心编排直接列出这些步骤 | prepare/finish 不再成为隐藏大量不同动作的入口 |
| sandbox/launcher | 分清 dispatch、init、exec；平台专用文件保留真实平台后缀 | 读者知道切到了哪个进程角色，以及下一条控制消息去哪 |
| helper 本机协议 | 请求、响应、版本、帧、完成确认有单一轻量归属；可信 init 的 StageSpec/Event 仍明确独立边界 | 消费协议无需导入整个特权服务实现；不混淆两层协议 |
| judge/flow | flow.go 展示主流程；compile.go、case.go、result.go 承载相应阶段 | 把共享判题状态放到每请求私有对象，缩短 runCase 的重复参数 |
| judge/node | node.go 生命周期，identity.go 身份，control.go 注册心跳，http.go 安装入口，install.go 安装事务 | 读者可以按一个入口追踪，避免一个文件混合无关路径 |
| config | 加载与环境变量解析、judge、sandbox、logging、duration 各按职责归属 | 本次可移动校验实现但保持调用与接受/拒绝行为不变 |

同包文件优先；只有依赖方向或协议边界确实需要时才新增包。
通信类型不直接绑定 cgroup 内部可变实现类型；如引入转换，保留全部序列化字段、名称和数值。
不改变源数据、数据库、外部 JSON Schema、部署文件或公开配置键。

### 数字与固定值的处理

先清点再命名。每项记录：所在符号、实际含义、单位、原值、依据、定义所有者、关联约束、处理方式。
没有查到依据时明确记录“现有值，依据待确认”，保留原值，不编造性能或安全理由。

| 类别 | 当前例子 | 处理方式与边界 |
|---|---|---|
| 继承 FD | init 的 3/4/5，exec 的 3/4/5 | 按角色定义具名 FD；同一数字在两个进程角色中指代不同通道，不得混用。ExtraFiles 的数组顺序与子进程接收定义一起核对 |
| 协议与握手 | Version: 1、'R'、'G'、退出记录长度 8 | 协议所有者定义具名常量/类型；发送与接收共享定义。裸 JSON 中的版本也要纳入清点，保留线格式 |
| 错误阶段 | terminalFailure 的 1～7 | 定义带明确数值的阶段类型，报告与解码按同一映射；不能用会随插入重排的隐式顺序改变协议值 |
| 总传输期限 | helper 两端 150s、HTTP 写出 160s、交付写出 10s | 名称表达限制的操作，单位可读；注明多个计时起点/覆盖阶段。先核对已有关系，不默认它们已经满足所有最坏情况 |
| 容量和资源预算 | 128 个文件、4MiB 结果帧、64MiB 输入、128MiB 工作区 | 区分请求预算、节点硬上限和协议大小；仅真正同一约束共用定义。默认值不等于最大值 |
| 权限和系统值 | 0o700、0o600、syscall 数字 | 常见权限位保留八进制，补充所有者与访问目的；有平台常量时使用平台常量。不要把正常系统表达全部包成无信息量的新名字 |
| 字段索引与位标记 | Limits 的 index == 3、values[3]、present 位 | 用具名字段索引或统一字段描述保证映射；不能只把 3 换成另一个仍需记顺序的名字 |
| 特殊状态值 | ExitCode=-1、ReadyFD=0、limit=0 | 说明尚未退出、无握手测试模式、显式零预算等各自含义；缺省和显式零的语义原样保留 |
| 普通计算 | 循环初值、计数加一、min/max | 含义直接可见时保留字面量，不做机械提取 |

常量默认放在最窄的实际所有者旁边，不建立全模块 constants.go 大杂烩。
配置只承载部署方确实需要选择的策略；本次不因发现硬编码就扩大配置面。
不能在安全策略安装后的最终 exec 段引入新的格式化、分配或普通 Go 调用来替换裸值；该段的命名重构仍须保持调用约束。

## 接口与状态

把状态分成可解释的阶段：接纳、输入准备、隔离启动、已放行、终止监督、回收确认、交付确认、响应完成。
这是阅读模型，不要求新增一套与现有执行状态并行的状态机。

资源所有权至少覆盖：执行名额、输入文件/流、控制/存活通道、init/payload 进程、cgroup、挂载目录、
工作区句柄、产物文件、已写入 store 的 ref。每项指出取得、转移、正常释放、失败释放和结果发布条件。
TASK-104 在本节后补充冻结基线的逐项资源表；当前示例不是已完成的实施交接记录。

任何返回值都要说明其完成含义：Start 返回在途执行，Wait 确认哪一层结束，Completion 确认哪一层资源交付，
Close 是否允许重复调用，以及失败是否使服务停止接单。不要让不同阶段都只被叫作“完成”。

## 安全与失败

保留入组先于用户 exec、隔离根与权限准备先于 GO、超时终止整组、清理失败不发布成功、产物完整交付确认、
取消后独立清理等既有约束。提取函数时不改变运行线程、goroutine、FD 生命周期与因果顺序。
未知状态不得放宽；上下文取消仍必须传到实际阻塞边界。

审查发现的环境探测与 Linux 后端不兼容、错误原因丢失、配置跨服务校验耦合等记录到基线遗留清单。
本次不混入修复。如果某问题阻止等价重构或验证，先提出范围升级，而非顺手变更行为。

## 监控与部署

沿用当前日志和部署方式，不增加本机常驻服务、不改 socket/身份/单元文件、不远端安装或切换。
解释现有错误链的归属可以写入注释；新增日志或改变错误正文需另列行为变更并获得相应授权。

## 迁移与兼容

按阶段形成可审阅、可编译的改动单元；符号迁移与必要引用调整同批完成。
数字提取先保留原值并对照协议/配置，再处理文件和函数组织，避免同一 diff 同时改变意义和位置。
依赖或 helper 通信类型迁移须比较序列化结果。基线由 TASK-104 固定，不能使用会继续变化的当前工作区替代。

## 备选方案

只补 README：可辅助导航，但不能解决 prepare 隐藏启动、defer 改写结果或数字含义不明。
全部合并成大文件：减少跳转，却混淆权限、平台与生命周期；只适合合并本来就一起变化的小碎片。
全局常量表：减少裸数字却失去上下文；采用按所有者定义的局部常量和必要的协议共享。
更换/合并执行进程：可能缩短路线，但属于架构变更，见 DECISION-027。

## 可用于未来编码规范的候选规则

本节是候选规则的唯一草稿来源。本轮不复制到 docs/engineering；不改变现有规范的效力。
后续经人工确认长期适用并明确授权后，分别迁入 conventions.md 的通用约定和 go.md 的 Go 专项，原处改为引用。

| 候选 | 规则 | 适用范围与例外 | 检查方式 |
|---|---|---|---|
| C-01 | 主流程按使用者关心的生命周期表达 | 请求、命令、作业；纯算法不必套阶段模板 | 从入口追到输出，能说出阶段顺序 |
| C-02 | 跨接口/线程/进程交接说明实现入口、对象和完成条件 | 异步或无法直接跳转的边界；普通直接调用无需重复解释 | 交接两端可定位，后台任务可找到收尾者 |
| C-03 | 函数名准确表达动作及返回时的进度 | 所有代码；领域中已有精确定义的简称可保留并解释 | prepare 是否偷偷启动，Start 是否说明仍在途 |
| C-04 | 文件按阶段或一起变化的职责组织 | 不设机械行数限制；平台后缀与构建约束优先 | 改一个阶段不需遍历无关文件，避免万能 utils/constants |
| C-05 | 有业务/协议/资源含义的数字必须可解释 | 普通计数、常见八进制权限表达可保留 | 用途、单位、依据、所有者、关联约束能回答 |
| C-06 | 同一协议定义共用，不同含义不因同值合并 | 协议值固定映射；独立安全边界可重复校验但解释归属 | 核对两端与旧值，不仅检查是否使用常量 |
| C-07 | 关键资源有明确所有者及完成条件 | 文件、连接、锁、进程、异步任务；Go 的 defer 仍保留异常兜底 | 正常、取消、失败各走一遍释放路径 |
| C-08 | 注释解释原因、约束和交接 | 教学项目可说明必要背景；不逐句翻译代码 | 去掉注释会丢失哪些有用知识，TASK 引用不代替说明 |
| C-09 | 共享上下文有明确生命周期 | 多参数反复出现时考虑私有对象；不机械按参数数目重构 | 不引入全局可变状态或万能 Context |
| C-10 | 阅读性变更验证行为等价 | 移动、重命名、提取；发现 bug 独立修复 | 对照契约、默认值、错误/取消及平台回归 |
