# CHANGE-013：按命令执行顺序重构 Go 判题引擎源码

## 为什么做

阅读源码的人希望从一条命令进入开始，跟到它执行完毕、返回结果，理解每一步为什么存在。
现在读者经常在不同文件之间来回寻找，却不知道命令是否已经开始运行、谁在等待谁、什么时候才算结束。
代码中的一些数字也没有解释用途，需要依靠猜测或翻找其他材料。

本次整理要让执行顺序和关键限制直接体现在源码里，降低理解、修改和复核的成本。
其中经过实际检验的做法，可以在后续确认后成为其他代码也适用的规范。

## 当前状态

审查对象是 apps/judge-engine 当前工作区，包含 WORK-048 尚未收束的 Linux sandbox 实现。
本工作只编写重构文档，尚未实施；文档通过不由智能体代签，不能把本次创建文档视为实施授权。

## 当前问题

已定位的阅读断点：

- POST /run 经接口、容量池和 Container.Start 后转到 Unix socket，缺少清楚的对端入口说明。
- helper.prepare 实际启动 init 进程以及多个后台任务；名字不能说明已经发生的动作。
- ready/GO 握手在 helper、init、exec 三个角色间往返，按单个文件阅读不能看清顺序。
- 用户命令退出、资源组清空、产物交付确认、最终响应是不同节点；部分结果修改隐藏在 defer 中。
- node.go 混合身份、注册、HTTP 与安装协议；flow.runCase 有 11 个参数，共享上下文靠调用方记忆。
- FD 编号、握手字节、失败阶段、数组下标、数量及时间上限包含缺少用途或依据的字面量。

具体符号与重构办法见 [DESIGN-043](30-design-DESIGN-043.md)。以上是阅读性审查事实，不能推导所有现有行为正确。

## 目标状态

- REQ-001：以命令从进入到返回为阅读主线；各入口、跨进程交接、并发启动和回收都有明确的下一站及完成条件。
- REQ-002：文件和函数按执行阶段或明确的独立职责组织；名称反映实际动作；读者无需全局搜索猜测下一步。
- REQ-003：具有协议、资源、权限或状态含义的数字在使用位置可理解用途与单位，并能追溯定义、依据和关联约束。
- REQ-004：代码明确区分命令退出、执行环境回收、产物交付和响应完成，正常路径与失败路径都能追踪资源归属。
- REQ-005：整理可迁入未来编码规范的候选规则，说明适用范围、例外和检查方式；本轮不直接修改全局规范。

## 不变条件

- REQ-006：保持对外契约、判题结论、零值/缺省语义、配置默认值、既有校验规则、协议字节、资源预算及隔离与回收保证。结构调整不夹带已知缺陷修复。
- REQ-007：保留 judge 与 sandbox 的职责边界。本工作不自行决定移除特权 helper、合并进程、改用其他执行器或改变权限模型；如需这些变化，先另行提出架构决策。

## 影响范围

预计涉及 Go 模块内 sandbox 执行链、judge 编排与 node、配置与限额的代码组织，以及对应的测试和包内阅读说明。
不涉及 Java/Web 业务、外部 JSON Schema、部署切换、数据库迁移或依赖升级。

实施边界按 TASK 明确；WORK-048 仍在修改的路径必须先交接并记录基线，不能覆盖在途改动。

## 风险

低层代码的移动和命名调整可能误改 FD 顺序、协议映射、取消路径或资源释放时机。
为追求线性阅读而删除实际必要的并发和握手，会改变隔离行为。
把同值数字合并可能混淆不同限制；把内部安全上限变成配置会扩大行为范围。
仅补长文说明、机械拆文件、机械提取常量，可能让代码更碎而没有改善阅读。

## 回归检查

- AC-001：按设计中的两条阅读路线实走源码，记录每一阶段对应符号；从 handleRun 到实际 exec 再到最终响应，不出现没有对端或下一步说明的交接。
- AC-002：读者能解释一个正常执行、一次超时和一次取消的事件顺序，指出由谁回收进程/FD/临时文件、何时允许发布产物；结论与代码及测试一致。
- AC-003：数字清单逐项给出用途、单位、所有者、原值、处理方式和依据；协议固定值与资源预算无意外变化，不同含义不因同值合并。
- AC-004：适用的格式、静态检查、race 测试和 Linux 隔离/故障回收回归有实际证据；未执行、跳过和失败分别记录，不能互相替代。
- AC-005：候选规范包含适用范围与例外，人工明确哪些可提升为长期规则；提升动作通过后续明确授权执行，本工作内保持候选状态。
- AC-006：与冻结基线比较，对外行为、配置与协议及安全不变量保持不变；发现既有缺陷独立记录，不借本工作顺手更改。
