用户明确的问题不是单个文件太长，而是无法按“一条命令进来，到执行完毕”追踪源码；同时不知道硬编码数字的用途。
本记录保存需求来源和本地实施所得；R8 独立源码阅读与完整 Linux 回归已完成，身份与证据见 VERIFY-050。

## 决定与原因

2026-09-13 等价重构范围已随意图闸确认，具体边界见 DECISION-027。候选规范只在 DESIGN-043 维护，未经长期适用性确认不进入全局规则。
保留当前 helper 是本次等价重构边界，不表示该架构无需未来重审。

## 尝试与教训

先前对话先从文件职责和维护性解释问题；用户进一步指出执行顺序、helper 的理由和数字含义，重构目标因此具体化。
仅拆文件、加常量或补架构说明不足以证明源码可读；最终判断要来自沿真实入口走通流程。
B0～B4 的拆分未解决用户提出的结构问题；R0～R7 已改为所有权和生命周期对象，本地测试与 R8 独立阅读均通过；阅读者能直接回答七项结构问题并走通四条路径，无阻塞卡点。

## 对象重构的本地实施所得

预算、进程协议与产物交付具有不同完成条件。execution 负责停组和最终结论，isolatedProcess 负责 P3 持有的进程/FD/I/O，rootFilesystem 只在 P4 准备挂载。对象不能跨进程共享状态，也不能用一个 Close 掩盖这些边界。

正常返回后仍需交付的产物必须显式移交；此次用测试确认关闭原 execution 不影响结果句柄，结果关闭保留第一次失败。独立阅读尚未执行，这些测试只支持所有权合同，不证明增加对象后源码一定更容易理解。候选处置仍以 DESIGN/VERIFY 为准，未迁入全局规范。

验证分支用完整模块快照绑定提交，逐字节核对当前工作区，同时保留其他工作的未提交改动。下载后用原有校验器重算同批汇总，能避免把历史成功、部分 job 绿色或补丁摘要误作最终候选证据。首次本地 TLS 测试受监听权限限制，保留错误并在正确环境重跑，没有修改测试掩盖限制。
