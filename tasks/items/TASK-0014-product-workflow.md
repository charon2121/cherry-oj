# TASK-0014：建立产品需求与交付工作流

## 背景

`PRD.md` 已经定义目标用户、产品链路、优先级和验收场景，`tasks/` 也能严格管理研发任务的认领、
依赖和技术验证，但两者之间没有以用户结果为单位的产品需求层。产品负责人目前需要阅读多个按服务、
契约或工具拆分的技术任务，才能重新拼出一条完整用户链路；`review` 也同时承载技术审核和产品验收，
导致审核对象、证据和通过标准不清楚。

本地 `docs/product-requirement-delivery-workflow.md` 已形成 v0.1 评审稿。用户确认按该方案实现，
需要把它落成进入 Git、可复用、可校验的产品文档体系。

## 目标

建立 `PRD → REQ → TASK → 产品验收` 的双层需求与交付工作流，使产品负责人可以围绕可独立演示的
用户能力审核 REQ，研发人员继续围绕技术任务执行 TASK，并通过稳定 ID 追踪两者关系。

## 范围

包含：

- 新建进入 Git 的 `product/` 产品文档中心，明确 PRD、REQ、PD、TASK、技术设计与版本验收的职责。
- 提供产品需求、产品决策和版本验收模板，以及必要的元数据约束。
- 将“C++ ACM 答题闭环”整理为第一份正式 REQ，保留尚未确认的产品问题，不提前创建业务任务。
- 为研发任务增加可选的产品需求与里程碑关联；新任务默认生成这些字段，历史任务无需强制回填。
- 提供无第三方依赖的一致性检查，校验产品文档字段、状态、ID、文件名、本地引用和 REQ/TASK 双向关系。
- 更新任务工具测试、任务中心说明、仓库核心说明和 CI，使新克隆能够发现并校验产品文档体系。
- 同步本地方案稿，说明正式规范已经迁入 `product/`。

不包含：

- 实现登录、题目、提交、判题或任何其它业务能力。
- 为 REQ-0001 拆分或认领后续业务研发任务。
- 回填所有历史任务的产品需求归属，或把纯技术债强行关联到产品需求。
- 引入 Jira、Linear、Notion 等外部项目管理平台或第三方 Python 依赖。
- 代替产品负责人确认 REQ-0001 中仍待讨论的产品决策。

## 验收标准

- [ ] `product/` 进入 Git，并提供清晰的文档导航、真源边界、状态流转、审核职责和变更规则。
- [ ] REQ、PD 和版本验收模板可直接复制使用，REQ 模板以用户能力而非技术模块为中心。
- [ ] REQ-0001 能独立说明目标用户、流程、规则、体验状态、范围、产品验收场景、成功信号和未决问题。
- [ ] 新建 TASK 可以关联 `requirement_ids` 与 `milestone`，未关联产品需求的历史任务仍能通过校验。
- [ ] 产品文档检查能够拒绝非法字段、重复或失效 ID、错误状态、断裂引用和 REQ/TASK 单边关联。
- [ ] 产品检查与任务检查均有自动化测试，并接入现有 CI 的任务边界。
- [ ] `scripts/product check`、`scripts/task check`、相关 Python 测试和 `git diff --check` 全部通过。
- [ ] 没有创建 REQ-0001 的业务交付任务，也没有修改运行时代码或业务契约。

## 产品影响

产品负责人将以 REQ 的用户流程和场景证据为主要审核入口；技术 TASK 仍保留完整实现与验证信息，
但不再要求产品负责人通过阅读所有技术任务推断产品是否可交付。
