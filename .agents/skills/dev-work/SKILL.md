# 按需开发工作流程

这个 skill 只用于 cherry-oj。普通开发请求不自动启用，即使请求中出现 feature、bug、重构等词。仓库的 `AGENTS.md`、契约、编码规范和必要验证始终有效。

## 先判断这次要做什么

从 skill 所在目录向上三级是仓库根目录。读[开发记录入口](../../../development/README.md)和[五类任务流程](../../../development/specification/04-workflows.md)，只取当前类型的要求。

- 功能：谁使用，前后有什么变化，正常、失败与权限行为是什么。
- 修复：实际与预期、复现或证据、原因是否已经确认。
- 基建：谁接入、使用合同、限制、失败与恢复。
- 维护：要解决的结构问题、必须保持的行为和职责边界。
- 改进：当前基线、目标、比较方式与容许代价。

混合任务补相关检查，不重复建工作。继续已有工作时先看当前短说明和必要旧依据，历史状态和闸不再是执行条件。

## 准备人能快速看懂的说明

每项工作必需一份 `development/works/YYYY-MM-DD-短名/00-work.md`；已有工作沿用原目录。可直接写文件，或可选地使用 `scripts/work new TYPE SLUG --title '标题'`。不申请新 WORK/TASK 编号，不建阶段表、关系数组或签闸数据。

按[文档写法](../../../development/specification/05-documents.md)，先用日常语言回答四个问题：为什么做、打算怎么解决、范围和代价、怎样算完成。普通工作以一屏为目标；会影响决定的未知和重要取舍必须留在这里。给人看前删除写作提示，别为了凑模板补空章节。

类型要求的定义和验证方向写在这份说明中。技术细节写在末尾或按实际需要拆附件；复杂方案用 design，独立依赖或委派才用 plan/task，较长证据才用 verify。不要为同一目标另造 FEATURE/ISSUE 等第二份定义，不预先生成空证据或经验文档。必要附件必须从主说明可达，关键代价不能只藏在附件。

## 确认、实施与交付

1. 展示短说明，等用户确认目标、范围、关键代价并允许实施。不要让用户逐份审核技术附件。已有明确授权或针对本次的确认豁免按其范围生效，不重复询问。只要求规划或文档时，交付到这里结束。
2. 按授权范围实施，运行与改动有关的验证。范围或关键取舍变化时，更新短说明并解决相应授权；不要先扩大改动再补材料。复核方式与风险和现有授权相称，skill 不自动授权委派其他 Agent。
3. 在主说明补“结果与验证”：实际结果、验证、未执行/失败的检查、遗留问题和需要人判断的效果。少量证据直接写，较长记录才拆文件并链接。
4. 展示交付结果供用户接受。可以报告实施完成或测试通过，不能据此写“用户已接受”。实际确认可以记录用户原意，不伪造或推导签署。通过聊天完成确认，不运行旧 gate/refresh 命令。

## 依据与历史

上游事实链接 `docs/` 与契约，不重复抄写。已确认且会影响多个后续工作的结论才进入全局文档，并保留来源。

历史 `90-history-WORK-xxx.md`、原附件和 `flow.json` 是只读原件。新增结果写当前入口或新附件；不修改原件、补签旧闸或修正旧状态以假装工作已收束。工具 `list/show/check` 只负责导航与完整性，检查通过不是执行授权或验收结论。迁移范围见[历史说明](../../../development/history/README.md)。
